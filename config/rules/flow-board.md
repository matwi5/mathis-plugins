# Lots de tickets (plugins `mattpocock-skills` et `flow-board`)

Les lots de tickets passent par `/implement` et `/implement-spec` du plugin mattpocock-skills ; le plugin flow-board en tient le tableau de bord.

- **Un commit par ticket**, toujours, sans qu'il faille le redemander : après les contrôles du projet (règle « Contrôles ») et la revue du ticket par `/mattpocock-skills:code-review` (point fixe : le commit d'avant le ticket ; c'est elle que désigne le « use /code-review » de `/implement`, pas la revue intégrée de Claude Code ; en cas de doute sur la revue voulue, le dire à l'utilisateur au lieu de choisir en silence), au format de commit du projet (règle « Commits ») ; puis le ticket coché dans le suivi des tâches (règle « Suivi Asana » quand le plugin asana-board est installé), avec un commentaire qui cite le hash du commit.
- **Revue** : pour un diff de moins de 100 lignes ou de documentation seule, hors des zones sensibles (confidentialité, suppression de données, chiffrement, concurrence), les deux axes de `/mattpocock-skills:code-review` (Standards, Spec) se relisent dans un seul sous-agent, pas en parallèle (Opus, effort xhigh, comme toute revue). Les scripts jetables de `travail/tasks/` se relisent sur leur justesse (données écrites, contrôles), sans la liste d'odeurs de code.
- **Texte soumis à l'accord de l'utilisateur** (spec, plan, piège de `CLAUDE.md`) : avant de le lui montrer, consulter l'advisor (règle « Consulter l'advisor », moment (a)), pas un sous-agent de revue ; sans outil `advisor`, le relire soi-même dans la discussion. Sa conformité au code reste à la charge de celui qui l'écrit (règle « Vérifier avant d'écrire »).
- **Ordre et contenu des revues** d'un ticket et d'un groupe (axes Standards et Spec, passe « bogues », revue du groupe, revue de sécurité) : ceux des étapes du tableau de bord flow-board, dont les consignes arrivent avec `/implement` et dans le brief des sessions liées.
- Tout choix fait sans que l'utilisateur l'ait demandé ni validé est signalé aussitôt au tableau de bord (champ `decided` de l'outil, avec sa raison) : ticket traité hors de la file, approche choisie parmi plusieurs, travail reporté ou abandonné, périmètre changé, correctif au-delà du ticket. L'utilisateur relit ces choix ; ils reviennent dans le compte rendu.
- Un groupe fini n'est pas la fin du lot : tant que des tickets du parcours restent ouverts, la suite est le groupe suivant, que l'utilisateur lance depuis le tableau de bord. Une fois tous les tickets faits et relus, l'utilisateur lance `/flow-board:compte-rendu` : un rapport à valider (fait, décidé sans lui, mal passé, bloqué par lui, trouvé, documentation, ce que la livraison enverra ; la documentation manquante est complétée avant le rapport). Ne proposer `/project:version` qu'une fois ce rapport validé dans le tableau de bord.
- **Pas de push ni de PR en cours de parcours** : tant qu'un parcours flow-board a des groupes ouverts, ne proposer ni `/project:push` ni `/project:pr`, même pour mettre un correctif en ligne ; les groupes se fusionnent dans la branche de travail et l'envoi se fait une fois, à la fin du parcours. Les essais sur l'appareil réel (téléphone, service) se proposent aussi seulement après la livraison : le service ne sert que la branche livrée, et un correctif encore sur la branche de travail n'y est pas. Entre deux groupes, attendre la consigne de l'utilisateur avant de lancer le suivant.
