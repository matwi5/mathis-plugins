# flow-board

Tableau de bord en direct du workflow [mattpocock-skills](https://github.com/mattpocock/skills) dans Claude Code. Il suit chaque travail sous la forme d'une **mission**, de l'idée jusqu'à la pull request, et l'affiche dans un panneau et dans un bandeau au-dessus du prompt.

- **Il s'adapte au skill de départ.** `/grill-with-docs`, `/to-spec`, `/diagnosing-bugs`, `/triage` ou `/implement` n'ouvrent pas la même mission.
- **Il se remplit tout seul.** Il suit les skills chargés, les tickets Asana, les spécialistes, les tests, les commits et les livrables.
- **Il garde les missions par projet.** Plusieurs discussions peuvent travailler sur le même projet sans se marcher dessus.
- **Il suit les conventions de livraison du plugin `project`** : `/project:sync`, `/project:version`, `/project:push`, `/project:pr`.

Version actuelle : **0.80.0**. Historique des versions : [CHANGELOG.md](CHANGELOG.md).

## Installation

Le mod est distribué par la marketplace `mathis-plugins` (dépôt GitHub `matwi5/mathis-plugins`, source dans `plugins/flow-board/`). Installation d'un poste et protocole de développement : README à la racine du dépôt.

```bash
claude plugin marketplace update mathis-plugins
claude plugin install flow-board@mathis-plugins
```

Pour une nouvelle version : modifier la source dans le clone de travail (`plugins/flow-board`), monter `version` dans `.claude-plugin/plugin.json` et dans l'entrée du mod de `.claude-plugin/marketplace.json` à la racine du dépôt, commiter et pousser, puis :

```bash
claude plugin marketplace update mathis-plugins
claude plugin update flow-board@mathis-plugins
```

Une mise à jour s'applique aux discussions démarrées après elle, ou après `/reload-plugins`.

**Prérequis**
- Claude Code avec les *function hooks* : mods de la version 2.1.286 ou plus récente.
- Le plugin `mattpocock-skills`, fourni par cette marketplace en copie figée (`plugins/mattpocock-skills`, version 1.3.1 de Matt Pocock).
- Facultatifs :
  - le plugin `project`, pour la phase de livraison ;
  - le connecteur Asana, pour suivre les tickets ;
  - un dépôt git avec un distant, pour la synchronisation.

**Workers : Desktop et CLI** (depuis la 0.35.0). Les boutons « worker » mettent dans le prompt une demande valable dans les deux ; Claude choisit selon ses outils :

| | App Desktop (onglet Code) | CLI |
|---|---|---|
| Lancement | `start_session` (`context` « fresh », `wake_when_done`) | `claude --bg -n '<titre>'` par le shell, avec `-w '<nom>'` dans un dépôt git (titre et nom cités pour le shell) |
| Id relevé | dans la réponse de `start_session` (`local_…`) | dans la sortie « backgrounded · <id> · <titre> » |
| Note de fin | l'app relance le manager quand la fille finit un tour | la fille envoie son message final par `SendMessage` au manager, ce qui la réveille même inactive ; depuis la 0.56.0, le brief ne donne que la référence stable de la discussion (« [ref] ») : la fille la retrouve toujours dans `ListAgents` et envoie à « <nom du moment> [ref] » (avant, le nom d'abord et la référence en repli, depuis la 0.45.0) ; une session de groupe dépose son compte rendu complet au relais et n'envoie qu'une ligne qui y renvoie ; depuis la 0.56.0, plus de filet `notify_when_idle` (cinq réveils pour un groupe, dont quatre pour rien) : le message final de la fille réveille la discussion, et le relais rattrape un message perdu |

Côté CLI, le dossier doit avoir été approuvé dans le CLI (sinon « Workspace not trusted ») ; la combinaison `--bg` + `-w` n'a pas pu être essayée (à confirmer). Les deux discussions doivent être sur la même machine : le fichier des missions est local.

## Concepts

| Terme | Définition |
|---|---|
| **Mission** | Un travail suivi de bout en bout. Le skill qui l'ouvre fixe ses phases. Une mission est **en cours**, **en pause** ou **terminée**. Une mission **mise de côté** est en pause par ta décision : seul « Reprendre » la rouvre. |
| **Phase** | Une étape de la mission, tenue par un skill : Cadrage, Spec, Tickets, Implémentation, Version et push, Pull request… Certaines phases sont facultatives (en pointillé). |
| **Étape** | Une étape interne au skill de la phase. Par exemple, pour `/diagnosing-bugs` : boucle de feedback, reproduire, hypothèses, instrumenter, correctif, nettoyage. Une étape enjambée sans être faite est marquée *sautée*. |
| **Détour** | Un skill lancé hors du fil de la mission (`/prototype`, `/research`, `/handoff`…), affiché en bulle au-dessus de la phase en cours. |
| **Ticket** | Une unité de travail du lot, identifiée par son GID Asana, avec son statut et ses dépendances. |
| **Dépendance externe** | Une tâche hors du lot dont un ticket dépend : une décision à prendre, ou le travail de quelqu'un d'autre. |
| **Décidé sans toi** | Un choix que Claude a fait sans que la personne l'ait demandé ni validé : ticket traité hors de la file, approche choisie parmi plusieurs, travail reporté, périmètre changé. Il reste « à relire » jusqu'à « ✓ Relu ». |
| **Trouvé en route** | Une tâche créée dans le tracker pendant la mission, hors du lot : constat de revue, anomalie découverte, action pour la personne. Elle s'affiche à part, sans compter dans la progression ni retenir la livraison. |
| **Manager** | La discussion qui lance les autres : celle qui porte la mission, ou, sans mission, la discussion où l'on regarde. |
| **Worker** | Une discussion lancée par le manager pour lui confier un travail (un groupe de tickets, dont ceux des pistes d'une rétro, un bug), qui tourne à côté de lui (`start_session` dans l'app desktop, `claude --bg` dans le CLI). |
| **Spécialiste** | Un agent lancé à l'intérieur d'une discussion (manager ou worker) par l'outil `Agent`, qui travaille pour elle et lui rend un rapport. |
| **Frise, piste** | Dans l'onglet Agents, la frise montre le temps de gauche à droite ; chaque agent (le manager, un worker, un spécialiste) y a sa piste, une rangée faite de segments (réflexion, rédaction, appel d'outil, attentes) et de repères (échec, départ et retour, commit…). |

## Utilisation

Dès le début d'une discussion, sans mission active, un bandeau d'accueil d'une ligne dit « Aucune mission sélectionnée ». Si le projet a une mission en pause ou suivie dans une autre discussion, il propose la plus récente, avec son glyphe, son titre et un bouton « ↻ Reprendre ». Le « x » et `/flow hide` le masquent comme le bandeau normal.

**Boutons sans commande** (depuis la 0.70.0). Aucun bouton n'écrit la commande qu'il prépare : « ▸ Ouvrir » ouvre le panneau depuis le bandeau (avec ou sans mission active), et le bouton principal de la carte « Ensuite » dit seulement l'étape (« ▶ Compte rendu », « ▶ Version et push », « ▶ Pull request »). Ce que le bouton met dans le prompt ne change pas. Le texte gris à côté d'un bouton (« /to-spec · rédiger la spec »), la commande de la carte de phase et les notifications gardent la commande, pour qui préfère le clavier.

Le bandeau s'ouvre sur l'étiquette « ▍ Flow », comme ceux de git-board et d'asana-board ; il tient sur une ligne (depuis la 0.40.0). Empilé sous le bandeau d'un autre mod, il se place juste en dessous.

1. **Lancer un skill mattpocock**, par exemple `/mattpocock-skills:grill-with-docs export CSV`. La mission démarre et le panneau s'ouvre tout seul quand la place le permet ; sinon, taper `/flow` (ou `/flow-board:flow` en tout premier message, voir [Commandes](#commandes)).
2. **Suivre l'avancement.** Le bandeau au-dessus du prompt résume, sur une ligne :
   - la mission et sa feuille de route ;
   - la phase en cours ;
   - le mode auto de la mission, quand il est allumé ou en pause (« ⚡ Auto · en cours », « ⚡ Auto en pause : <raison> », depuis la 0.74.0, voir « Mode auto ») ;
   - les tickets faits, et l'avancement de chaque groupe dans un worker (« ↗A 2/5 ») ;
   - les spécialistes au travail, et les choix « ⚑ à relire » ;
   - le **bouton de l'étape suivante** (depuis la 0.70.0), juste avant « ▸ Ouvrir » : le même que celui de la carte « Ensuite » du panneau, tiré du même calcul, même libellé et même effet (la demande va dans le prompt). C'est le lancement de groupes quand il y en a un (« ↗ Groupe B · worker », « ⇉ A ∥ B en parallèle · workers »), sinon, l'étape en cours finie, la suite principale (« ▶ Compte rendu »), sinon « ✓ Clore la mission » quand la mission est bouclée. Rien en pleine étape, ni quand la carte n'a aucun groupe à lancer : un ticket en cours ici, des groupes dans un worker sans autre groupe prêt (un groupe prêt qui n'a ni fichier ni ressource en commun avec eux est proposé, comme dans la carte), des revues qui attendent ; ni « Compacter d'abord », ni la rétro, ni « ↗ xhigh ». Sur l'ordinateur, il prend le style « principal ». Quand la largeur manque, la feuille de route et le titre tombent avant lui ; il ne tombe que quand le reste du bandeau (étiquette, phase, pastilles des tickets, des workers, des agents et des choix à relire, « ▸ Ouvrir », « x ») n'aurait plus sa place.
   L'état de la session (« Claude travaille », « À toi de jouer ») et l'étape sont dans l'en-tête du panneau (`/flow`), plus dans le bandeau (depuis la 0.40.0).
3. **Passer à la suite.** La carte « Prochaine étape » propose le skill suivant. Son bouton met la commande dans le prompt sans la lancer : on la complète, puis Entrée. Tant que des tickets restent ouverts, ni le compte rendu ni la livraison (version, push, pull request) n'y sont proposés. Dans l'Implémentation d'une mission à groupes (depuis la 0.42.0), la carte « Ensuite » recommande plutôt quoi lancer : le lot de groupes indépendants en parallèle (« ⇉ B ∥ C en parallèle · workers »), sinon le prochain groupe prêt (« ↗ Groupe D · worker »), le groupe commencé ici d'abord. Un groupe prêt qui partage un fichier ou une ressource avec un groupe dans un worker attend : la carte dit alors quel groupe on attend. Une fois tous les tickets faits, elle dit quels groupes attendent leur revue ; les revues restent sur la ligne de chaque groupe, et le compte rendu vient en tête une fois toutes faites.

   **Suggestion grisée de la suite** (depuis la 0.47.0). À la fin de chaque tour du manager, la commande du bouton principal de la carte (par exemple `/mattpocock-skills:to-tickets`, ou `/flow-board:compte-rendu` une fois tous les tickets faits et relus) se propose en gris dans le prompt vide : Tab (ou la flèche droite) la prend, rien ne part sans toi. Rien n'est proposé quand une question t'attend (question du grilling, réponse qui finit par « ? »), dans un worker, quand la suite n'est pas une commande (lancer un groupe, attendre un worker, revue sur la ligne d'un groupe) ni pour la rétro d'une mission à workers, qui part avec sa consigne. Tant qu'une mission est active, la suggestion `/project:push` de git-board est écartée (pas de push en cours de mission) ; elle revient hors mission.

   **Compaction** (depuis la 0.64.0). La compaction remplace l'histoire de la discussion, dans son contexte, par un résumé ; le transcript (le fichier `.jsonl` de la discussion sous `~/.claude/projects/`) garde tout.
   - **Quand compacter** : une fois `/to-tickets` fini dans une mission à groupes (ou une rétro, une fois ses pistes découpées en tickets ; rien avant la rétro), tant qu'aucun groupe n'est lancé et que la discussion ne s'est pas compactée depuis, `/compact` se propose en gris à la fin de chaque tour, et la carte « Ensuite » offre « ⇣ Compacter d'abord ». En auto, le mod l'envoie lui-même à ce moment (`$.command.run`), une seule fois par découpage, quand ce découpage a fini sous l'auto (allumé après, la suggestion grisée s'est déjà proposée) et que la discussion ne s'est pas compactée depuis : son action est marquée et écrite avant l'envoi, comme toute action de l'auto (une écriture ratée met l'auto en pause), et compte démarrée dès l'envoi ; rien d'autre de l'auto ne part pendant qu'elle tourne ; finie (sans tour à elle), l'auto reprend et lance la première vague. Le manager ne fera plus que lancer et suivre des workers : le cadrage, la spec et le découpage, déjà écrits dans les fichiers, n'ont plus à peser sur chaque tour. Rien n'est proposé pour un lot fait dans la discussion, ni dans un worker.
   - **Consignes de compaction** : à chaque compaction de la discussion (tapée, automatique au seuil, ou calculée à l'avance), flow-board ajoute après ton texte ce que le résumé doit garder, selon le rôle de la discussion. Le manager garde des renvois : la mission et sa phase, ses groupes et leurs workers, les chemins des décisions, de la spec et des plans, les questions encore ouvertes, et le chemin de son transcript pour la rétro. Un worker de groupe garde de quoi reprendre son ticket (tâche en cours, étape de revue, commits, fichiers, contrôles, branche et worktree), les questions envoyées au manager encore sans réponse et les choix déjà déclarés, les constats de revue pas encore appliqués (ou le chemin du fichier qui les tient ; depuis la 0.80.0), les chemins du brief, de `DECISIONS.md` et de la procédure, et de quoi joindre le manager ; après la compaction, il recharge d'un seul appel à ToolSearch les outils différés qu'il employait (SendMessage, TaskCreate, TaskUpdate, Monitor). La discussion qui tient le siège du COO garde des renvois, jamais un état recopié : la feuille de route et le fichier de coordination, les missions suivies par leur seul id, les questions encore ouvertes avec toi mot pour mot ; elle se compacte d'elle-même quand elle est au repos, qu'aucune question (la sienne, une question de sa dernière réponse : finie sur « ? », une ligne « needs input », ou un « ? » de question ailleurs hors code, comme une question suivie de ses options, d'une phrase ou dans un tableau ; ou celle d'une mission) ni mission ne t'attend, qu'aucun lancement (carte, vague) ni livraison (une mission dans sa phase « Version et push ») n'est en cours et que son contexte dépasse 450 000 tokens, le seuil d'un worker entre deux tickets (une discussion du COO démarre déjà vers 150 000), jamais deux fois en 30 minutes, rechargement compris. La compaction automatique reste permise partout. La compaction d'un spécialiste, et une discussion sans mission qui ne tient pas le siège du COO, ne reçoivent rien.
   - **Compaction d'un worker entre deux tickets** (depuis la 0.79.0, en manuel comme en auto) : quand un ticket du groupe passe « done » (revue rendue, correctifs commités, statut relayé : Asana, ligne `Status:` d'un ticket local ou `set` de l'outil) et que le contexte du worker atteint 450 000 tokens (`WORKER_COMPACT_TOKENS`, d'après une étude des seuils sur 317 sessions Claude Code du 02/11/2026), la réponse de l'outil lui dit de finir son tour avant le ticket suivant. Au repos qui suit (tour fermé, aucune revue ni tâche de fond en cours, aucun ticket « doing » à son relais ; une tâche de fond qui dure se revérifie chaque minute, et au-delà de 10 minutes la compaction est abandonnée et le worker relancé), son mod pose une marque dans `$.store` (clé `worker-compact:<session>:<mission>:<ticket>`, relue avant l'envoi : écriture ratée, rien ne part), compacte la discussion une fois (`$.session.compact`, qui refuse pendant un tour : rien ne part derrière un tour qui commencerait un ticket ; abandonnée au bout de 15 minutes sans réponse), avec des consignes qui gardent le ticket suivant, la place dans la procédure et, pour le compte rendu, les pistes du ticket fini, sans le reste de son détail, puis relance le worker par un message qui nomme le premier ticket du groupe qui peut commencer, ni bloqué ni en attente d'un ticket pas fait (une relance refusée se dit par un toast ; un tour ouvert entre-temps la reporte à la fin de ce tour). Seul le passage d'un ticket à « done » compte, depuis un statut que le worker a déjà relayé, dans son fil principal : un ticket déjà fait que redit un fichier relu ou une commande, ou l'outil d'un spécialiste, n'annonce rien. Un même ticket ne compacte jamais deux fois ; un simple commit ne déclenche rien ; un autre ticket déjà commencé fait passer le moment, sans annonce (souvent le cas d'un ticket hors zone sensible, commité avant sa revue : le suivant démarre pendant qu'elle tourne), et le dernier ticket du groupe n'en déclenche pas quand la mission est connue du worker. La compaction automatique au seuil (600 000 tokens, `autoCompactWindow`) reste le filet.
   - **Repère ⇣** : sur la piste du manager, il ne se pose que pour une compaction de la discussion qui a eu lieu : ni pour un résumé calculé à l'avance, ni pour celle d'un spécialiste, ni pour une compaction refusée.

### La barre « À tout moment »

En bas de l'onglet Mission, qu'une mission soit en cours ou non, un cadre « À tout moment » réunit neuf outils dans l'ordre où on s'en sert, et un dixième pendant les phases de code et de revue. Chaque bouton met la commande dans le prompt sans la lancer, et aucun ne clôt la phase en cours (ce sont des détours ou des événements).

| Famille | Bouton | Commande | Ce qu'il fait |
|---|---|---|---|
| Comprendre | ? Reformulation | `/wait-what` | Le dernier message reformulé, plus simplement ; part tel quel |
| Comprendre | ✧ Recherche | `/research` | Sources primaires, un rapport Markdown ; ajouter le sujet |
| Comprendre | ✦ Tester une idée | `/prototype` | Une question de conception qu'on ne tranche pas en discutant (une logique, un modèle d'états, une interface), réglée par du code jetable ; souvent pendant le cadrage. Sans mission, il ouvre la sienne ; ajouter la question |
| Comprendre | ≡ Questionnaire | `/to-questionnaire` | Une décision qu'on ne tranche pas seul, mise en questionnaire ; ajouter le sujet |
| S'orienter | ✱ Et maintenant ? | `/ask-matt` | Quelle suite, quand on est perdu. Pendant une mission, la question est préremplie avec la mission, la phase, l'étape et le détour en cours ; sans mission : « par où commencer ? ». Part telle quelle, ou complétée |
| S'orienter | ◇ Challenger | `/grilling` | Une décision ou un plan mis à l'épreuve par des questions, sans quitter la phase ; ajouter le sujet |
| S'orienter | § Préciser un terme | `/domain-modeling` | Un terme flou ou une règle métier précisés par des questions (écarts avec le glossaire, cas limites, contradictions avec le code), puis écrits dans le glossaire ou, pour une décision difficile à défaire, dans les décisions du projet. Le cadrage l'appelle déjà : le bouton sert surtout en implémentation ; ajouter le sujet |
| Contexte | ⇣ Compact | `/compact` | Commande de Claude Code qui allège le contexte ; tes consignes sont facultatives, flow-board ajoute les siennes pendant une mission et dans la discussion du COO (voir « Compaction ») |
| Contexte | ➜ Passation | `/handoff` | La discussion résumée en document de passation pour une autre session ; ajouter son but |
| Déléguer | 🐞 Bug · worker | `/diagnosing-bugs` | Depuis la 0.26.0, seulement pendant Implémentation, TDD, Revue ou Compte rendu. Met dans le prompt une demande à Claude, à compléter après « Bug : ». Claude lance un worker dans ce dossier (pas de worktree : il doit lire le même fichier de mission), qui reprend la mission (`resume`), diagnostique le bug en détour de la phase en cours, le corrige selon le `CLAUDE.md` du projet, puis clôt le détour (`complete`). Une fois le correctif vérifié et commité, comme après un échec (avant de proposer la deuxième tentative, une nouvelle session, ou de replanifier), Claude arrête la session (`claude stop <id>`, sa conversation gardée ; dans l'app, l'archivage après ton accord pour cette session, demandé chaque fois : celui de `/flow archive on` ne vaut pas ici, la demande étant écrite au lancement ; ou le geste dit à la personne), seulement si elle ne travaille plus et qu'aucune question n'attend ; rien n'est noté au tableau de bord. Depuis la 0.55.0, la session est lancée en effort high, et xhigh pour une deuxième tentative sur un bug toujours là après la première ; pas de troisième session : on replanifie. À sa note de fin, Claude vérifie son travail ; si le bug est toujours là, il le dit et propose la deuxième tentative, sinon il reprend la mission |

### Le panneau

| Onglet | Contenu |
|---|---|
| **Mission** | En-tête de la mission choisie dans la discussion (anneau de progression, feuille de route animée) ; sans mission choisie (aucune, mise de côté, en pause ou suivie ailleurs), l'en-tête dit « Aucune mission sélectionnée » et n'en montre aucune, carte de la phase (tickets en cours, étapes, éléments suivis, tickets, tests, revue, détour), une ligne de résumé des spécialistes (« ◉ N agents au travail · ▸ Agents ») qui mène à l'onglet Agents, prochaine étape, « ⚡ Auto » (voir « Mode auto »), « ‖ Mettre de côté ». Sans mission en cours, le lanceur « Démarrer une mission », dans l'ordre du flux : Cadrer une fonctionnalité, Rédiger la spec de ce qu'on a discuté, Découper un plan en tickets, Implémenter un ticket ; puis Diagnostiquer un bug, Relire une branche ou une PR, Trier les issues, Explorer un grand chantier, Santé de l'architecture. En bas, toujours, la barre « À tout moment ». |
| **Agents** (depuis la 0.58.0) | Le suivi du manager, de ses workers et de leurs spécialistes, pendant une mission comme sans. En tête : un sélecteur d'historique (« Ici, maintenant », les missions archivées compris, les discussions sans mission du projet qui ont lancé des agents), une pastille par worker avec son état (au travail, rendu, échoué, fermé) qui montre sa propre frise, et un résumé (agents, durée, gain par rapport à une exécution en série, coût estimé « ≈ » d'après ccusage). Puis la frise : une piste pour le manager, une par worker, une par spécialiste (type en couleur et en glyphe, enfants en retrait, Workflow repliés ; depuis la 0.66.0, l'effort relevé d'un worker et d'un spécialiste sous son nom, jamais celui du manager), segments de réflexion, rédaction, outil et attentes, repères, pauses compressées. Au-dessus des pistes, une barre de navigation zoome et déplace la frise comme un montage vidéo : `−` (raccourci `s`) double la fenêtre affichée, `＋` (`z`) la divise par deux, `◀` (`q`) et `▶` (`d`) la décalent d'une demi-fenêtre (les touches ZQSD d'un clavier AZERTY : le moteur n'accepte comme raccourci qu'une lettre ou un chiffre, pas les flèches), « dernière heure » et « tout » (`t`) sont des préréglages ; chaque bouton affiche sa lettre, et les raccourcis marchent quand le volet a le focus. Le zoom porte sur la frise affichée, pauses déjà compressées : chaque appui double ou divise ce que tu vois, d'une minute à tout. Une fenêtre qui finit au bout de la frise suit le direct (le zoom garde alors sa fin) ; décalée vers le passé, elle se fige et montre toujours le même moment. Une règle graduée en heures (hh:mm) court au-dessus des pistes, son pas choisi selon le zoom (1, 5, 15, 30 min, 1, 3 ou 6 h) et coupée aux pauses. La fenêtre est propre à la discussion et repart de « tout » à chaque ouverture de l'onglet ; elle vaut aussi pour l'historique et la frise d'un worker choisi. Une **pause** est un moment de plus d'une minute où personne ne travaille : ni le manager, ni ses spécialistes, ni ses workers. Attendre ta réponse (question, autorisation) ou ton prochain message en est une ; réfléchir, rédiger, lancer un outil, attendre un spécialiste ou une tâche de fond, c'est travailler. Un spécialiste compte par ses segments, pas par toute sa période (un spécialiste tout juste lancé, encore sans segment, compte comme au travail). Chaque pause prend une largeur fixe et affiche sa durée, 24 % de la frise au plus pour toutes ; une attente de ta réponse y reste visible, écrasée et hachurée ambre. Une **attente** est une barre hachurée qui dit ce qu'elle attend : gris « attend un spécialiste », ambre « attend ta réponse », bleu « attend une tâche de fond ». Une **pause** n'est pas une barre : elle coupe le rail, deux traits verticaux et sa durée entre eux (`┊ 2 h ┊`), légendée « pause : personne ne travaillait » (au terminal aussi, `┊` à la place de l'ancien `⫽`). Sous la ligne de légende compacte, « ▸ légende détaillée », repliée par défaut, liste chaque famille d'outils avec ses outils (lecture `⌕` : Read, Grep, Glob… ; modification `✎` ; commande `❯` ; web `🌐` ; spécialistes `⇢` ; autres `•`), chaque type d'agent avec son glyphe et sa couleur, et chaque repère. Le texte de remplacement de chaque piste nomme ses attentes et ses pauses avec les mêmes mots. Quand la discussion ou un de ses spécialistes consulte l'**advisor** (le modèle relecteur), une ligne advisor apparaît juste sous le manager, une seule pour toute la discussion : or, glyphe ✦, nom « advisor · relecteur », une barre cerclée par appel. Le moteur ne signale l'appel qu'à la fin de l'étape du modèle qui l'a fait : la barre arrive alors, avec ses vraies heures, et la piste de l'appelant montre au même moment une attente or en pointillés (`┄` au terminal), « consulte l'advisor », qui coupe sa réflexion : des pointillés, pas des hachures, pour ne pas la confondre avec l'ambre de « attend ta réponse ». La carte de la ligne liste les appels, leur heure, leur durée et qui les a faits. Dans la frise du manager, les appels d'un worker ne s'y ajoutent pas : on les voit en choisissant ce worker. Le modèle, les tokens et le coût de chaque appel arrivent après coup, par le rattrapage : le direct ne les donne pas. Le transcript (de la discussion ou du spécialiste appelant) porte, pour chaque réponse qui a consulté l'advisor, une entrée `advisor_message` dans `usage.iterations` (modèle, tokens) ; ses tokens ne sont pas dans le compte de la réponse, et le mod ne les ajoute jamais à l'appelant. Le contenu de la réponse de l'advisor, chiffré, n'est jamais lu. Le coût est tiré des prix de ccusage, comme celui des spécialistes, et compté une seule fois : à part dans le résumé (« ✦ advisor ≈ 1,89 $ »), sur la carte de la ligne advisor (modèles, appels, tokens, coût), et sur la carte d'un agent appelant en une ligne « ✦ Advisor : 2 appels, ≈ 0,42 $ », hors de son coût et de la somme avec ses spécialistes. Sans prix connu pour le modèle de l'advisor : « coût inconnu », avec les tokens. Depuis la 0.66.0, un appel que le transcript donne sans résultat ni entrée d'usage, dans une réponse qui appelle aussi des outils de la session et une fois une ligne écrite après lui (posé après ces outils, il n'est jamais parti), ne coûte rien et ne se montre pas, ni sur la ligne advisor ni en attente sur la piste de l'appelant : il ne fait plus passer toute la ligne en « coût inconnu ». Un appel encore en vol ne se lit pas, des chiffres arrivés ensuite lèvent la marque, et une réponse interrompue pendant l'advisor reste un appel sans prix. Les appels d'un worker lui-même se relisent dans son transcript quand on le choisit dans l'onglet du manager (dans son fichier à part) : un worker n'ouvre presque jamais son propre onglet Agents, et leur coût restait vide. La ligne advisor existe aussi dans l'historique d'une discussion passée et dans la frise d'un worker choisi. Le bouton d'une piste ouvre sa carte de détail (prompt, tokens, outils, lignes, coût, transcription). Depuis la 0.66.0, une exécution de `/code-review`, que le moteur nomme d'après sa commande coupée (« /code-review high refs/worktree/flow-board/120000… »), prend un nom standard d'après sa cible : « Passe bogues · E2 » (instantané d'un ticket : la lettre de son groupe et son rang, quand la mission est connue ici), « Revue du groupe E » (`--fix` ou plage jusqu'à `HEAD`), « Revue · <plage> » ou « Revue de code » ; sa carte garde la commande entière, et le niveau se lit dans l'effort. Les relecteurs que Claude lance reçoivent eux aussi un nom standard par la consigne d'`/implement` : « Standards+Spec · E2 », « Sécurité · groupe E ». Sur une discussion passée, « ✗ Oublier » l'efface après confirmation. Ouvert dans un worker, l'onglet dit de qui il est le worker. |
| **Activité** | Chiffres (fichiers, commits, merges, termes du glossaire, ADR, tests), livrables écrits, journal des événements. |
| **Historique** | Les missions du projet, avec « Reprendre », « Reprendre ici », « ◆ Agents » (ouvre l'onglet Agents sur cette mission, archivées comprises) et « ▣ Archiver ». Les missions archivées sont cachées par défaut, sous « ▸ Archivés (N) », avec « ▢ Désarchiver » et « ✗ Supprimer ». La suppression demande une confirmation (« Supprimer définitivement cette mission ? ») et ne se défait pas : depuis la 0.58.0, elle efface aussi ses agents, ses workers, son relais et ses choix ; les autres discussions du projet l'oublient aussi. |
| **Commandes** | Les points de départ, les 18 autres skills groupés par famille, les commandes de livraison et les commandes `/flow`. |

Les dessins (feuille de route, anneaux, barres) sont en SVG sur le desktop, VS Code et le mobile, et en glyphes sur le terminal. Sur la feuille de route du terminal, chaque phase a un nom court (depuis la 0.65.0) : « Code » pour Implémentation, « Rapport » pour Compte rendu, « Push » pour Version et push, « PR » pour Pull request, etc. ; le desktop garde les noms entiers. Une mission à une seule phase (apprentissage, configuration, grilling, prototype, design de module…) a pour stations ses étapes, qui ont elles aussi un nom court depuis la 0.67.1 : « Problème », « Options », « Comparer » pour le design de module. La rétro, qui a depuis la 0.72.0 la suite du Triage, montre ses phases : « Rétro », « Code », « Rapport », « Push », « PR ». Chaque nom affiché tient en 9 caractères.

| `/triage` | Triage | Triage → Implémentation³ → Compte rendu² → Version et push¹ → Pull request¹ |

¹ Phase facultative.
² Facultatif tant qu'on n'a pas codé, obligatoire dès que l'Implémentation démarre (depuis la 0.30.0) : un triage ou un examen de l'architecture sans code se clôt sans compte rendu.
³ Facultative tant que le lot n'a aucun ticket à faire, due dès qu'il en a un (depuis la 0.73.0 ; avant, seulement pour la rétro, depuis la 0.72.0) : un triage, un examen de l'architecture ou une rétro dont la discussion finit avec un lot pas lancé passe en pause, pas « terminé », que le lot soit arrivé avant ou après la fin de sa phase.

Depuis la 0.63.0, `/implement-spec` et `/wayfinder` ne sont plus suivis : ils ont quitté la copie `mattpocock-skills` (1.3.1-mathis.1), sans jamais avoir été lancés. Au chargement, une mission enregistrée avant change de skill : une phase ou un départ `/implement-spec` devient `/implement` (mêmes tickets, étapes d'`/implement`), une phase ou un départ `/wayfinder` devient `/grill-with-docs` (ses éléments restent des décisions, ses étapes sont faites si la phase l'était), et l'ancienne alternative `implement-spec` de la phase Implémentation disparaît. Aucune mission n'est supprimée, le journal reste tel quel.

**Compte rendu.** Avant toute livraison, la phase « Compte rendu » (`/flow-board:compte-rendu`, lancé par toi) fait écrire à Claude un rapport à lire et à valider :
- sections fixes : En bref, Fait, Décidé sans toi, Ce qui s'est mal passé, Bloqué par moi, Trouvé, Code antérieur au lot, Pistes, Documentation, Ce que le CHANGELOG devra dire, Ce que la livraison enverra ; une section vide dit « Rien. » ; le tout tient en 60 lignes au plus ;
- trois rubriques reprennent, dans tous les cas, ce que rend un worker (depuis la 0.77.0) : les constats sur du code antérieur au lot, que les revues ont classés à part, pour que tu décides d'un groupe « durcissement » ; les pistes (les constats des passes « bogues » qui ne violent pas l'invariant, et les cas limites relevés en route) ; ce que le CHANGELOG devra dire, par plugin ou paquet, que `/project:version` reprend. Avec des groupes, Claude les reprend des comptes rendus des workers ; sans groupes, il les rédige d'après les revues de la discussion ;
- « Documentation » donne une ligne par document que le projet tient (état du projet, décisions, CLAUDE.md, specs, plans, tracker…) : à jour, complété avant le rapport, rien à changer, ou à faire. Claude complète ce qui manque avant d'écrire, et ne laisse « à faire » que ce qui demande ta décision ;
- Claude part des faits du tableau de bord (tickets, trouvailles, choix faits sans toi, plans, tests), qu'il vérifie et complète par git et le tracker ; il copie aussi le rapport dans le fichier de suivi `travail/tasks/…` s'il y en a un ;
- toi seul valides, dans le panneau : « ✓ Valider le rapport » clôt la phase, marque les choix « décidé sans toi » comme relus et propose Version et push ; depuis la 0.67.0, il envoie aussi à Claude un message, au nom du mod, qui dit que tu as validé le rapport : Claude n'attend plus sans le savoir ; depuis la 0.70.0, dans un dépôt git, ce message porte aussi la suppression des branches des workers fermés de la mission, et « ↺ Rouvrir » disparaît (voir « Cycle de vie ») ; « ✎ À reprendre » met « Rapport non validé : » dans le prompt. Le rapport se lit et se valide aussi chez le COO (voir « Rapport chez le COO »). Claude ne peut pas clore la phase, mais chaque réponse de l'outil `flow` (et de `/flow`) lui donne l'état du rapport : « rapport : validé (date UTC) », « en attente de validation », « non validé (sauté) » ou « pas encore rédigé » ;
- tant que le rapport n'est pas validé, la livraison n'est pas proposée ; lancer `/project:version` quand même saute le compte rendu, et le journal le dit.

Les missions existantes reçoivent la phase à leur chargement, avant leur « Version et push » à venir.

Une mission en plusieurs groupes passe souvent par plusieurs discussions ; le compte rendu se rédige dans la dernière. Il couvre quand même tous les groupes : le tableau de bord, partagé, lui donne l'état de chaque groupe (fait, relu) et la liste des fichiers de suivi `travail/tasks/…`, un par discussion, enregistrés comme livrables « Suivi » avec leur groupe. Claude les relit tous, avec `git log` depuis le début de la mission, et écrit « Fait » groupe par groupe.

La rétro (`/retro`) n'est pas une phase : elle reste proposée à tout moment dans la carte « Ensuite ». Une mission créée par une version antérieure est mise à niveau à son chargement : sa rétro à venir disparaît, un « Corps de PR » à venir devient « Version et push » puis « Pull request », et, depuis la 0.72.0, une rétro pas terminée qui n'a que sa phase reçoit la suite d'une rétro neuve (Implémentation, Compte rendu, Version, PR), sans rien changer à sa Rétro, à ses pistes ni à sa session de pistes. Tant que cette session n'est pas fermée, la rétro garde sa seule phase (elle reçoit sa suite dès que la fermeture est enregistrée), ses pistes ne se découpent pas en tickets (l'appel est refusé), et la carte « Ensuite » d'une phase dont les pistes sont chez un worker ne propose aucune suite : quitter la Rétro avant la note de fin la rangerait dans une autre phase, et la session ne serait plus fermée d'office.

**Rétro d'une mission à workers** (depuis la 0.43.0). Quand la mission a eu des workers (un groupe confié ou rendu, des pistes confiées), le bouton Rétro, dans la carte « Ensuite » comme dans « Autres commandes », met dans le prompt `/retro` suivi d'une demande à Claude, dans le manager :
- retrouver les workers d'abord par leurs fichiers de relais (`~/.claude/flow-board/relais/<parcours>.<id>.report.md`, `<id>` étant celui de leur transcript : une session fermée d'office n'est plus dans ListAgents), puis par ListAgents, d'après le début de leur titre (« <mission> > », « › » avant la 0.61.0) et les ids relevés à leur lancement ;
- lancer un spécialiste par worker, en parallèle et en lecture seule : chacun lit le transcript de son worker et en fait la rétro selon les étapes et les sept axes de `/retro`, que le manager lui transmet, puis rend ses pistes par sévérité. Le transcript se lit même quand le worker est fermé ou compacté, en entier ; s'il commence par une compaction, il continue un autre fichier, que le lecteur retrouve par le `logicalParentUuid` de la marque (depuis la 0.64.0). Le manager ne se charge pas de sa lecture ;
- faire en même temps la rétro du manager ;
- une fois tous les comptes rendus reçus, faire le compte rendu global : pistes fusionnées et sans doublon, par sévérité, chacune avec ses sessions d'origine. Cette liste devient les pistes de la rétro au tableau de bord.

Sans worker, le bouton met `/retro` seul. Une session de diagnostic de bug ne laisse pas de trace dans la mission : elle n'est retrouvée que par son titre, si la mission a aussi eu un autre worker.

**Rétro d'une discussion compactée** (depuis la 0.64.0). Quand `/retro` se lance, tapé ou par le bouton, avec ou sans mission, flow-board ajoute au skill une consigne de transcript : un spécialiste en lecture seule relit le transcript de la discussion du début jusqu'à la dernière compaction (la marque `compact_boundary`) et en fait la rétro ; la discussion fait la partie qui suit, puis fusionne. Quand flow-board a vu la compaction (repère ⇣), la consigne est directe ; sinon Claude vérifie d'abord par grep si le transcript porte une marque, car une discussion reprise après une compaction, dans un nouveau fichier, n'a pas de repère. Un transcript qui continue un autre fichier est suivi jusqu'à lui. Le skill `/retro` lui-même ne change pas.

**Pistes de la rétro : leur découpage en tickets** (depuis la 0.73.0 ; de la 0.33.0 à la 0.72.0, elles partaient dans un seul worker, voir « Affectations anciennes » plus bas). Une fois les pistes présentées, chacune a sa case (○ / ●) dans la carte de la phase, avec « Tout sélectionner » au-dessus de la liste. Avec au moins une piste choisie, « ✂ Découper N pistes en tickets » met dans le prompt une **demande de découpage**, n'enregistre rien au tableau de bord et vide la sélection : un clic dont la demande s'est perdue se refait, en recochant les pistes. La demande, écrite au clic, fait à Claude :
- signaler l'étape « Découpage », puis sauter (et te le dire) une piste devenue faite ou écartée entre ton clic et son envoi ;
- régler d'abord avec toi les pistes qui attendent une information ou une décision de ta part (un accès, un choix entre options), en un seul tour de questions ;
- sortir les pistes qui touchent un autre dépôt (plugins, config commune, autre projet) dans une liste de corrections prête à confier à un agent de ce dépôt : elles ne vont pas en ticket et restent à ton choix ;
- découper les autres : un ticket regroupe 1 à 3 pistes voisines (mêmes fichiers, même sujet), une piste en zone sensible fait un ticket à elle seule ; pour chaque piste, le problème constaté, la correction attendue, les fichiers touchés et un critère de fin à cocher ; le ticket porte la ligne « Pistes : r12, r27… », ses lignes « Zone sensible », « Logique » et, au besoin, « Lecteur », et, en zone concurrence ou suppression, l'invariant fixé avec toi. Un ticket qui modifie un fichier chargé dans toutes tes sessions (tes règles communes, un `CLAUDE.md`) dit que sa session l'écrit et cite dans son compte rendu chaque phrase ajoutée ou retirée, et que tu relis avant la fusion ;
- grouper : 5 tickets au plus par groupe ; deux groupes qui touchent un fichier ou une ressource en commun s'enchaînent, les autres partent dans la même vague ; un lot de rétro peut n'avoir qu'un seul groupe (exception à « pas de groupe seul ») ; chaque groupe prend un id que la mission n'a pas encore. Les consignes de découpage de `/to-tickets` (fichiers, « Zone sensible » et « Logique », « Lecteur », champ ajouté à des données persistées, taille d'un groupe (3 à 4 tickets quand tous sont sensibles), ordre d'un ticket sensible (en premier quand il bloque le suivant, ou quand il est lourd et indépendant), chevauchement avec les autres missions, ordre réel d'une procédure et cycle de vie d'un champ gardé, écriture hors du dépôt, fragments de l'ancienne formulation d'une règle recopiée mis dans `termes-retires.txt`, cadrage d'un ticket sensible et lecture de son code, pas de ticket de version) y sont reprises telles quelles ; celle qui garde `CLAUDE.md` hors des tickets de groupe n'y est pas (la règle précédente la remplace pour les pistes), et la forme du plan des groupes y est dite par la demande elle-même ;
- écrire les tickets dans le suivi que `/to-tickets` utilise pour ce projet : en fichiers locaux, dans le dossier `travail/` de la mission étudiée par la rétro, en continuant sa numérotation, sinon dans `travail/retro-<sujet>/` ;
- te faire valider le découpage par une question à boutons, avec la liste des écritures du suivi, puis écrire les tickets et tout envoyer en un seul appel : la liste complète des pistes lue au moment de l'envoi (celles mises en ticket « faites »), les tickets, le plan entier des groupes (ceux déjà enregistrés compris : un plan remplace le précédent, et un groupe pas encore confié qu'il omet en sort) et `complete` ; sans aucun ticket, seulement la liste des pistes et `complete`. Un appel refusé n'enregistre rien, et la réponse dit pourquoi.

La Rétro se clôt alors, le curseur reste sur elle, et la carte « Ensuite » propose le premier groupe ou la première vague ; le lancement d'un groupe fait passer la mission à sa phase Implémentation. Chaque groupe tourne dans un worker, dans son worktree, selon la procédure de groupe et ses revues (voir « Groupes dans un worker »), et se ferme d'office une fois rendu et clos ; après les groupes, la mission passe au compte rendu, à la version et au push, comme un lot ordinaire. Une rétro dont aucune piste n'entre dans un ticket se termine sans ces phases.

**Ids et libellés des pistes** (depuis la 0.73.0). Un id de piste nouveau a la forme d'un id de groupe (lettres et chiffres ASCII, 12 au plus) ; hors forme, il prend un id dérivé de lui (« p » puis son empreinte en base 36, puis un rang quand cet id est déjà pris dans l'envoi ou enregistré pour une autre piste) : une piste renvoyée sous son id d'origine retrouve le sien tant que son libellé ne change pas, et un id généré n'est jamais donné à une autre piste tant que la sienne reste dans la liste (rien n'est enregistré de plus : une piste sortie de la liste libère son id) ; la réponse de l'outil dit à Claude sous quel id renvoyer chaque piste, nommée par son libellé (rien pour une piste que la borne coupe) ; la description de l'outil dit cette forme. Un id déjà enregistré (par une version d'avant, ou cité par un lien de pistes) reste tel quel, même hors forme ; renvoyé sous la forme que la demande en a montrée (ci-dessous), il se lit comme cet id quand un seul id enregistré donne cette forme (plusieurs : aucun n'est choisi, la piste prend un id généré, et la réponse le dit avec leurs ids exacts, échappés en JSON, sous lesquels Claude renvoie chaque piste ; un id enregistré renvoyé exact se garde toujours, et la réponse dit les autres ids de même forme). Les éléments des autres phases (les issues « #12 » du Triage…) gardent leurs ids. Dans les demandes mises dans le prompt (découpage, et pour un lien ancien « ↻ Redemander » et « ↻ Reprendre les pistes »), chaque piste se recopie « n) [id] « libellé » », et le titre de la mission, les ids et les libellés y perdent leurs caractères de contrôle et invisibles, et montrent leurs crochets en ( ) et leurs guillemets « » (et leurs sosies) en “ ” : une piste ne peut ni fermer la liste ni y glisser une consigne.

**Affectations anciennes.** Un envoi de pistes à un worker fait avant la 0.73.0 reste suivi comme avant (étape « Modifications en cours », « ↗ Worker… », « ↻ Redemander », « Annuler », « ↻ Reprendre les pistes », fermeture et « ↺ Rouvrir ») jusqu'à la fermeture de sa session ; d'ici là, aucune piste ne se coche (la carte d'une session terminée le dit : « fermer d'abord la session précédente avant un nouveau découpage »), et un appel de découpage envoyé quand même est refusé en entier, avec ce qui ferme la session. Le bouton n'en crée plus.

**Comment un skill s'insère dans la mission en cours**
- Un skill **déjà prévu** dans la mission fait avancer celle-ci jusqu'à sa phase.
- Un **sous-skill** déclaré par la phase fait avancer l'étape correspondante, par exemple `/tdd` pendant `/implement`.
- Un skill **hors du fil** devient un détour.
- Un **autre point de départ** ouvre une nouvelle mission et met la précédente en pause. La mission en pause reprend toute seule quand on relance un de ses skills dans la discussion où elle est née, sauf si elle a été **mise de côté** (voir plus bas) : le skill ouvre alors une nouvelle mission. Depuis la 0.80.0, une mission née dans une autre discussion, en pause ou muette depuis plus de 30 minutes, n'est jamais reprise par un skill : il ouvre une nouvelle mission, et l'autre se reprend par « ↻ Reprendre ici » (avant, un skill de cadrage lancé dans une discussion neuve reprenait la mission d'une autre discussion et y écrivait). Une mission reprise par « ↻ Reprendre ici » reste née dans sa première discussion : tant que l'autre discussion la tient, même muette, un skill de la première ne la reprend pas ; remise en pause, elle se reprend de nouveau par ce bouton. Une mission d'avant la 0.60.0 ne dit pas où elle est née : seul ce bouton la reprend.
- Exception : `/diagnosing-bugs` pendant Implémentation, TDD, Revue ou Compte rendu devient un **détour** (liste `detourIn` du catalogue). Le bug reste dans le lot qui l'a fait apparaître. Ailleurs (cadrage, spec…), il ouvre toujours sa « Chasse au bug ».

| Asana (`update_tasks`) | Ticket coché ou ligne « Statut : » (en cours, en attente, à trancher), et levée des dépendances externes. Pour un blocage, le texte de la ligne devient sa raison. |
| Asana (`create_tasks`), `gh issue create` | Hors des skills qui publient le lot (`/to-tickets`, `/to-spec`, `/triage`), la tâche créée va dans « Trouvé en route », avec le statut de sa ligne « Statut : ». |
| Réponses de Claude | Questions du grilling (`❓ **Qn**`) ; une synthèse de revue (`## Standards`) fait avancer l'étape. Les chiffres de revue viennent du champ `review` de l'outil, que Claude remplit après chaque revue : la carte affiche le nombre de revues, les constats (Standards, Spec) et les corrigés, cumulés sur la phase. Dans la discussion de la mission, ses champs `bugs` (constats d'une passe « bogues ») et `group` (la revue d'un groupe) ne s'écrivent que dans le journal (« Revue du groupe A : … · 2 bogues (passe « bogues ») »). Envoyé par un worker, `bugs` part aussi au relais, et le retour de son groupe le cite au journal, avec la même alerte quand constats et bogues dépassent les corrigés ; une revue sans `bugs` n'en compte aucun, jamais « 0 bogue ». Un `bugs` qui n'est pas un entier de 0 à 10 000 est ignoré des deux côtés, sans toucher aux autres comptes, et la réponse le dit (« bugs ignored: … » ici, « NOT kept in the relay: the bug count (…) » dans un worker, quand le reste de la revue est en forme : une revue refusée à l'envoi pour un autre compte hors forme, ci-dessous, ne dit que ce refus) ; un compte de bogues gardé illisible dans l'entrée d'une session n'est jamais réécrit, ni poussé au-delà de 10 000 : la revue qui en ajouterait est refusée, sa revue de sécurité part seule, et la réponse dit quoi faire (renvoyer la revue sans `bugs`, ou ne pas la renvoyer quand le reste est déjà relayé, et donner le compte dans le compte rendu). Dans un worker, `standards`, `spec` et `fixed` suivent la même borne (un entier de 0 à 10 000, sans arrondi ; absent, un compte vaut 0) : une revue dont l'un sort de là (texte, `null`, négatif, décimal, trop grand) est refusée en entier, rien n'en est relayé, sa revue de sécurité part seule, et la réponse le dit (« review: refused, counts out of range ») ; une revue qui pousserait un compte de l'entrée de la session (le nombre de revues compris) au-delà de 10 000 est refusée de même, et la réponse dit de donner les comptes dans le compte rendu ; relu du relais, un compte hors forme ne compte pas pour sa session, sans faire tomber ses autres comptes ; un compte gardé illisible dans l'entrée de la session (un fichier modifié à la main, ou des comptes qui ne sont pas un objet) n'est jamais réécrit : la revue qui y ajouterait est refusée de même, et un compte gardé absent vaut 0. Dans la discussion de la mission, ces comptes gardent leur règle : un compte non numérique ou négatif y vaut 0, un décimal y est arrondi. Dans la discussion de la mission, chaque réponse de l'outil rappelle les tickets bloqués avec leur raison, et un ticket passé « fait » ici sans revue dans le même appel (une revue envoyée plus tôt le rend sans objet) ; un groupe rendu sans revue dit le `reviewed` à envoyer une fois ses tickets faits. Dans un worker, le paragraphe qui dit comment joindre le manager (ListAgents, `[ref]`) n'est que dans la réponse à `delegate` ; les relais n'en gardent qu'une ligne. |

## Tickets, dépendances et lancement

**Tickets**
- Les tickets sont identifiés par leur GID Asana, avec un lien « Asana ↗ » ; au terminal, qui écrivait l'adresse entière, un bouton « ⧉ Asana » la copie à la place (un toast le confirme).
- Une liste envoyée par Claude **ajoute ou met à jour** des tickets, sans jamais en retirer.
- Les tickets d'une rétro naissent du découpage de ses pistes (depuis la 0.73.0, voir « Pistes de la rétro : leur découpage en tickets ») : chacun nomme les siennes sur sa ligne « Pistes : … », et suit ensuite le chemin de tout ticket.
- Un ticket envoyé par erreur se retire explicitement (`remove`) : il quitte aussi les groupes, la file et les dépendances des autres tickets.
- Une discussion sans mission active n'enregistre rien tant que le projet a une mission en pause ou suivie ailleurs : l'outil renvoie à Claude la liste de ces missions, et `/flow` les nomme, pour qu'on reprenne la bonne avec « ↻ Reprendre ici » au lieu d'ouvrir un autre lot.

**Ouvrir ou corriger une mission sans skill (depuis la 0.32.0)**
- Quand tu le lui demandes (« fais une mission pour ces trois tickets »), Claude ouvre une mission par l'outil, champ `open` (`{"title": "…", "entry": "implement"}`), même si une autre est active dans la discussion. L'autre est mise en pause avec ses tickets, comme quand un autre skill de départ ouvre une mission (son détour en cours se clôt, et elle est terminée s'il ne lui reste rien d'obligatoire) ; tout le reste du même appel (tickets, groupes…) va à la nouvelle. `entry` donne la forme de la mission (un skill de départ : `implement` par défaut, `to-tickets`, `grill-with-docs`, `diagnosing-bugs`…).
- Il corrige la mission active par `fix` : le titre, même déjà posé ; la phase en cours, en arrière (les phases d'après redeviennent à faire) comme en avant (celles d'avant sont closes ou sautées, et un compte rendu non validé passe « sauté », jamais « fait ») ; l'étape, en arrière comprise. Les tickets et les groupes se corrigent par `tickets`, `set`, `remove` et `groups`. Un `title` simple ne remplace toujours pas un titre posé.
- La description de l'outil le borne : seulement à ta demande ou pour réparer une erreur, jamais de sa propre initiative. Sans mission active, la réponse de l'outil nomme les missions à reprendre et rappelle que `open` n'est qu'à ta demande. Pour sortir des tickets d'une mauvaise mission, Claude envoie `remove` dans un appel d'abord, puis `open`.

**Titre de la mission et de la discussion (depuis la 0.60.0)**
- Le titre d'une mission ne vient plus jamais du texte tapé après la commande (souvent un long prompt) : une mission ouverte par un skill porte le nom de son flux, « non titré », jusqu'au premier `title` de Claude. La consigne du premier appel lui demande un titre court qu'il choisit, qui résume tout le chantier, dans ta langue, jamais ton message lui-même. Une suite garde « <libellé> · <titre du parent> ». `open` et un lot de tickets sans skill prennent le `title` de Claude.
- La mission retient la discussion où elle est née (`bornIn`), à sa création, sans jamais l'effacer, même à la mise en pause. À son premier titre, cette discussion prend le même nom, si aucune autre mission n'y est née (active, en pause, finie ou archivée ; une mission supprimée ne compte plus, une mission d'avant ce changement non plus), si ce n'est pas un worker et si aucun worker n'a été demandé par la mission (son brief nomme la discussion). Sinon, seule la mission prend le titre. La réponse de l'outil le dit à Claude : « name this discussion "<titre>" » ou « this discussion keeps its name ».
- Trois chemins renomment la discussion : Claude appelle tout de suite l'outil de l'app qui la renomme quand il l'a (`set_session_title`) ; sans cet outil (le CLI, une session de fond), le mod lance `/rename <titre>` lui-même, juste après la fin du tour où le titre est né (pas d'un tour interrompu), quand la session liste `/rename` comme commande de Claude Code (pas une commande du même nom venue du projet, d'un serveur MCP ou d'un autre plugin), le titre mis sur une ligne sans caractère invisible ni bidirectionnel, puis efface le titre en attente (essai du 02/11/2026 : `/rename` lancé par un plugin renomme la session, Claude Code 2.1.316 au terminal) ; et, en filet, le mod renvoie le titre au moteur (`sessionTitle` du hook `UserPromptSubmit`) à ton prochain message, ou à la reprise de la discussion (`SessionStart`), une seule fois, et seulement si la discussion ne le porte pas déjà (`session_title`). Le titre en attente est gardé pour la seule discussion de naissance (`$.store`, clé `discussion-title:<session>`), hors du board partagé : une autre discussion ne peut pas le ramener. L'essai du 27/10/2026 a vérifié le chemin `UserPromptSubmit` au terminal (Claude Code 2.1.311, et 2.1.308 embarqué par l'app) et dans l'app desktop ; le chemin `SessionStart` d'une reprise (`--continue`) a été vérifié au terminal le 28/10/2026 avec Claude Code 2.1.312, par la sonde (`docs/evenements-moteur.md`, « Titre de la session »).
- `/flow rename` et `fix.title` renomment aussi la discussion, aux mêmes conditions, tant qu'aucun worker n'est demandé ni n'a été lancé par la mission (« Annuler » une demande avant le lancement la libère) : son brief donne le nom de la discussion qui porte la mission, qui ne doit plus bouger ensuite. Les workers gardent le titre fixé à leur lancement. Un titre donné à la main avant la première mission est écrasé (le mod ne distingue pas un titre donné à la main d'un titre automatique).
- Les consignes qui te demandaient de renommer la discussion à la main (au début d'`/implement`, avant le premier worker) ont disparu.

**Mettre de côté (depuis la 0.32.0)**
- « ‖ Mettre de côté », sous la carte « Ensuite », ou `/flow pause` : la mission active passe en pause telle quelle (étapes, détour, tickets en cours), sans être close même si tout est fait, ni archivée, et la discussion n'en a plus d'active. Tu peux alors en ouvrir une autre.
- Elle s'affiche « ‖ mise de côté » dans l'Historique. Seuls « ↻ Reprendre » (Historique, bandeau d'accueil) et le champ `resume` de l'outil la rouvrent, dans l'état où tu l'as laissée ; relancer un de ses skills ouvre une nouvelle mission au lieu de la reprendre.
- Un rapport de l'outil sans mission active n'écrit rien dessus : Claude reçoit sa liste avec l'état « set aside by the user » et te demande lequel reprendre.

**Mode auto (depuis la 0.74.0)**
- Le mode auto se règle mission par mission : deux missions du même projet peuvent avoir chacune le sien, allumé ou non. Allumé, il envoie lui-même la phase suivante, les vagues de groupes et leurs revues (voir « Envoi de la suite » et « Vagues, revues et relances ») et donne ses consignes à Claude.
- « ⚡ Auto », sous la carte « Ensuite », dans la discussion qui porte la mission : un premier clic montre ce que l'activation vaut (ton accord, pour cette mission seulement, sur ses validations à boutons et ses écritures Asana, chacune inscrite dans « Décidé sans toi » ; l'arrêt au rapport du compte rendu ; la question en zone sensible tranchée seule à sa condition ; les six catégories de décisions qui restent à toi), puis « Confirmer » et « Annuler ». Seul « Confirmer » l'allume, pour la discussion du clic. Allumé, le bouton devient « ⚡ Couper l'auto » et le coupe d'un clic ; en pause posée par le mod, le même bouton l'éteint pour de bon, et le bandeau n'en dit plus rien.
- Allumé aussi par le bouton ▶ « Lancer en auto » d'une carte de lancement du COO (voir « Lancer une mission ») : la nouvelle discussion lancée pour elle l'allume en son nom en consommant le lancement, avec la date du clic du COO gardée comme celle de « Confirmer » ; le clic du COO ne sert qu'une fois, à la seule discussion lancée pour lui, dans les 10 minutes ; un lancement périmé, déjà pris, inconnu ou perdu ouvre la mission en manuel (« Accord de lancement périmé : la mission est en manuel, allume l'auto ici si tu veux ») ; un lancement dont les 10 minutes passent pendant sa consommation rattache la mission à sa carte sans allumer l'auto (« Auto non allumé : le lancement a dépassé ses 10 minutes ; allume l’auto ici si tu veux »). Le mode auto d'une mission n'est jamais allumé sans l'un de ces deux clics ; une fusion, une reconstruction ou une lecture ratée laisse l'auto éteint ou l'éteint, jamais l'inverse. Pour une mission lancée en auto, le COO recueille lui-même le tour d'intention (le but, le périmètre, ce qui est hors sujet) dans `travail/<sujet>/demande.md`, et la consigne du cadrage en auto fait sauter ce tour à son manager quand ce fichier existe ; ensuite, le `DECISIONS.md` de la mission fait foi.
- L'état est gardé dans la mission : « allumé à » et « allumé par » (la discussion du clic), « éteint à » et la raison de l'arrêt. L'auto est actif quand « allumé à » est plus récent que « éteint à ». À la fusion des copies de deux discussions, chaque date prend la plus récente, quelle que soit la copie gagnante pour le reste : une copie en retard ne le rallume jamais, une date illisible le dit éteint, une date future est ramenée à maintenant, et une raison hors de la liste se lit « raison inconnue ».
- La mise de côté, la clôture, l'archivage, la fin de la mission (sa dernière phase finie) et la fin de la discussion qui porte la mission l'éteignent (un `/clear` ne l'éteint pas) ; l'effacement de la mission l'emporte avec elle. Une mission mise en pause parce qu'une autre s'ouvre dans la discussion garde l'auto allumé, et reprend quand elle redevient active ici.
- Il n'agit que depuis la discussion qui l'a allumé, quand la mission y est active. Ailleurs, la pause se déduit, sans rien écrire : « discussion changée » (après un `/clear`, qui donne un nouvel id à la discussion, ou une reprise dans une autre discussion), « mission en pause ». Deux clics sur « ⚡ Auto » le rallument pour la discussion du moment ; « ⚡ Couper l'auto », à côté, le coupe d'un clic. Après `/reload-plugins`, il est tel quel.
- Le bandeau dit « ⚡ Auto · en cours », « ⚡ Auto · en attente de <tâche> » quand il ne reste qu'à attendre une tâche externe pas faite (le nom de la première, neutralisé, et le compte des autres), « ⚡ Auto · attend ta réponse (N) » quand des questions t'attendent pendant que la mission avance encore ailleurs (un worker au travail, une tâche de fond ; sinon, à la fin du tour, l'auto se met en pause « plus rien ne peut avancer sans toi »), ou « ⚡ Auto en pause : <raison> » quand l'auto s'est arrêté sans un geste de ta part (fin de la discussion, lecture de la mission ratée, Claude pas prévenu) ou que la pause se déduit ; rien quand tu l'as coupé, mis de côté, clos ou archivé, ni quand la mission s'est terminée. Le bouton de l'étape suivante du bandeau reste : quand la place manque, la pastille de l'auto se coupe avant lui. Une mission qui n'est pas active ici le dit dans sa carte (« ⚡ Auto en pause : mission en pause », « ⚡ Auto allumé, la mission est suivie dans une autre discussion »).
- **Questions bloquantes.** Claude déclare chaque question qui t'attend par l'outil (`waiting` : un id, ce qu'elle bloque, une phase, un groupe ou un ticket, et son texte), et la retire une fois que tu as répondu (`answered`). Elles se déclarent en auto comme hors auto ; un worker n'en déclare pas, sa question remonte par message au manager. L'onglet de la mission les liste sous « ❓ Questions qui t'attendent », chacune avec ce qu'elle bloque. Une question ne bloque que ce qu'elle concerne : une phase, par les siennes ; un groupe, par les siennes, celles de ses tickets et celles de l'Implémentation ; un ticket, par les siennes, celles de son groupe et celles de l'Implémentation ; une question à la cible illisible bloque tout. 50 questions ouvertes au plus : au-delà, l'outil refuse la nouvelle, sans jamais en couper une. À la fusion des copies de deux discussions, les questions s'unissent une par une, et chaque retrait laisse une trace datée (les 100 plus récentes) : une copie en retard ne fait pas disparaître une question, ni revenir une question retirée (sauf une copie en retard de plus de 100 retraits, qui pourrait en faire revenir une : elle bloque alors, le sens sûr). Une question reposée sous le même id passe après la trace de son retrait. Depuis la 0.74.0, pour une mission dont l'auto est allumé au nom de la discussion, l'entrée ouverte d'ici d'une question l'emporte à la fusion sur celle de même id de l'autre copie, même plus récente : une copie forgée ne la recible pas ; les ids qui ne sont pas ouverts ici s'ajoutent. Une entrée relue abîmée n'est jamais reconstruite ni retirée par une fusion : sans date lisible, seule la trace de son retrait explicite l'efface ; sans cible lisible, elle bloque tout ; une liste qui n'est pas un tableau se lit comme une seule question, qui bloque tout et garde la valeur entière. Une nouvelle question à l'id de plus de 60 caractères est refusée, jamais rognée ; un id en chiffres est admis.
- **Envoi de la suite.** À la fin d'un tour répondu de la discussion qui porte la mission (ni un spécialiste, ni un tour interrompu ou en erreur), quand la phase en cours est finie, l'auto envoie lui-même la suite du bouton de l'étape suivante, si c'est une des phases qu'il lance (`/to-spec`, `/to-tickets`, `/implement`, `/flow-board:compte-rendu`) : jamais la version, le push, la PR, la rétro, la clôture, le durcissement ni la validation du rapport ; la compaction, une seule fois après un découpage fini sous l'auto (voir « Compaction »). La commande part par `$.command.run`, au nom du mod (le moteur refuse un `$.prompt.submit` qui commence par « / »), un peu après la fin du tour, sans que le hook l'attende ; une fin de tour suivie d'un nouveau tour (un message de ta part) attend la fin de celui-ci. Avant l'envoi, le mod relit le fichier de mission : une lecture ratée n'envoie rien et éteint l'auto (« lecture de la mission ratée ») ; puis il y écrit la marque « envoyée » de l'action, sa clé stable (la phase et son rang parmi les phases de ce skill), et seulement alors envoie ; une écriture ratée n'envoie rien, retire la marque (avec une trace, comme « ↻ Renvoyer », pour qu'une copie qui l'aurait reçue ne la fasse pas revenir) et met l'auto en pause (« écriture de la mission ratée »). Rien ne part tant qu'une marque attend son démarrage, ni quand une question bloque la suite. La marque passe « démarrée » au retour de l'envoi, au `prompt.submit` de la commande ou au chargement de son skill. Une marque restée « envoyée » (envoi refusé, ou deux minutes sans démarrage, la discussion au repos depuis 30 s) devient la question bloquante « envoi resté sans suite », avec « ↻ Renvoyer » (Claude ne la retire pas : l'outil le refuse) : le clic efface la marque, en garde une trace datée, et l'auto renvoie l'action, une fois, tout de suite si la discussion est au repos et que Claude a reçu la consigne de l'allumage (sinon, d'abord cette consigne : voir « Claude prévenu de l'allumage »). Une même action ne part jamais deux fois, même après `/reload-plugins` : les marques ne se coupent jamais (seuls « ↻ Renvoyer », le retrait d'une marque qui n'est pas partie et l'effacement de la mission en retirent), s'unissent marque par marque à la fusion des copies (« démarrée » l'emporte), et les 100 traces de retrait les plus récentes empêchent une copie en retard de faire revenir une marque retirée (une marque démarrée de la même clé, elle, reste) ; une liste de marques illisible n'envoie rien et éteint l'auto. Quand des questions attendent et que rien n'avance plus (aucune action prête, aucune tâche de fond, aucune marque en attente), l'auto se met en pause (« plus rien ne peut avancer sans toi »). Le rapport écrit (étape `validate` du compte rendu) l'arrête (« rapport prêt ») sans rien valider ; une erreur de quota en fin de tour (`rate_limit`, `billing_error`) le met en pause (« quota atteint »). Une pause se lève par deux clics sur « ⚡ Auto ».
- **Claude prévenu de l'allumage.** Aucune étape ne part d'un allumage (le second clic, rallumage compris) avant que Claude en ait reçu la consigne dans la discussion. Il la reçoit par la consigne d'un skill chargé après le clic dans son propre fil, qui porte alors aussi la consigne de relecture ci-dessous et le bloc de la phase en cours (appelé par Claude ou tapé par toi ; jamais un skill forké ni un skill intégré à Claude Code, comme `/code-review`, ni un skill chargé dans un spécialiste), ou par l'avis « auto allumé » de la réponse suivante de l'outil, donné une fois par allumage, à Claude lui-même (l'appel d'un spécialiste ne le reçoit pas et ne compte pas, comme pour l'avis de la coupure) ; l'avis porte le bloc commun du mode auto et celui de la phase en cours, et demande à Claude de relire son dernier message : chaque question encore ouverte des six catégories se déclare en `waiting`, les autres se tranchent par sa reco déclarée, sauf les questions d'intention d'un cadrage, qui t'attendent, et le travail que tu as déjà accepté (tickets, groupes) s'envoie au tableau de bord ; donné en plein tour, l'avis lui dit ensuite de poursuivre la phase, et le message du mod, de rendre la main sauf s'il reste à faire dans la phase. Tant que Claude n'est pas prévenu, la fin d'un tour n'envoie rien, ne pose aucune marque et ne décide rien (une lecture ratée du fichier éteint l'auto, comme toujours). Au repos (le second clic, « ↻ Renvoyer »), ou à la fin d'un tour où Claude n'a pas été prévenu, le mod lui envoie lui-même cette consigne, par un message à son nom (`$.prompt.submit`), un seul par allumage ; la fin du tour de ce message fait décider l'auto. Parti d'une fin de tour, une question que Claude y déclare et qui bloque la suite met l'auto en pause « plus rien ne peut avancer sans toi » ; parti d'un geste (le second clic, « ↻ Renvoyer »), cette décision garde le sens du geste : elle n'envoie que ce qui peut partir, sans cette pause, et la question attend ta réponse, que la fin de tour suivante prend en compte. Tant que ce message attend son entrée (le moteur le met en file pendant un tour), rien d'autre ne part, ni second message ni avis. Un message n'est soumis qu'au repos, et ne prévient que l'allumage pour lequel il est parti : coupé ou rallumé pendant qu'il attend, il ne compte pas pour le suivant. Un message refusé met l'auto en pause « Claude pas prévenu », avec sa notification, et plus aucun message ne part pour cet allumage ; deux clics le rallument et renvoient un message. L'état « prévenu » vit en mémoire du mod, rien sur disque : après `/reload-plugins` ou un redémarrage, Claude est prévenu une fois de plus. Une fois prévenu, la consigne de la coupure suit comme après un skill (« Auto mode is OFF for this run now »).
- **Vagues, revues et relances.** Dans une phase à tickets découpée en groupes, la suite que l'auto envoie est celle des boutons des groupes, par le même texte, construit à l'instant de l'envoi et au nom du mod (`$.prompt.submit` : ce n'est pas une commande) : d'abord, au retour d'un groupe fini, la demande de sa revue (« ◆ Revue du groupe · worker ») quand sa session ne l'a pas faite (et un seul `/code-review` pour les groupes finis ici, sans worker), puis celle de sa revue de sécurité quand elle est conseillée et pas lancée, chacune une fois (sa marque, `review:<groupe>#<envoi>`, `security:<groupe>#<envoi>`) ; ensuite, quand aucun groupe n'est en vol ni rendu fini sans être clos (rendu, relu, sécurité tranchée), la vague prête : tout le lot parallèle (« ⇉ en parallèle »), ou le seul groupe prêt (« ↗ Worker »), sans les groupes bloqués par une question ni une phase qu'une question retient (seulement l'implémentation, ou le découpage une fois fini) ; ses groupes passent « worker à lancer » dans la même écriture que sa marque (`groups:A#1+B#1`), et « ↻ Renvoyer » sur une vague restée sans suite les rend à lancer avant de la renvoyer. La demande d'une mission en auto (celle de l'auto comme celle des boutons « ↗ Worker » et « ⇉ en parallèle ») dit que chaque session est un worker autonome quel que soit son effort, à l'effort de la règle (medium, high pour un groupe délicat), jamais xhigh, sans la question « xhigh (Recommandé) / high » : Claude déclare qu'il ne l'a pas proposé ; un besoin de ta part (une décision, un accès) devient une question bloquante sur son groupe, qui reste de côté ; les failles retenues se corrigent d'office. Hors auto, ces textes ne changent pas. Un groupe rendu avec des tickets ouverts repart une fois (avec ce que la session précédente a trouvé) ; revenu deux fois de son worker (un envoi annulé ne compte pas), l'auto ne le relance plus : une question bloquante le bloque (`relance:<groupe>#<envoi>`, posée une fois, reposée seulement si elle a disparu sans réponse donnée dans cette discussion), et, quand plus rien d'autre n'avance, l'auto se met en pause (« deuxième échec du groupe <id> »). Depuis la 0.74.0, Claude ne peut pas retirer cette question tant que le groupe attend sa relance (des tickets ouverts dans le plan, sans être confié de nouveau) : l'outil le refuse et dit de relancer le groupe ou de répondre autrement (ses tickets ouverts faits, ou retirés du lot par `remove` : un groupe confié garde ses tickets contre un plan renvoyé), puis de la retirer. Un groupe déjà relu qui part dans un worker, confié de nouveau après un envoi rendu ou, depuis la 0.74.0, confié pour la première fois après une revue faite ici, perd cette revue et son avis de sécurité (le journal les cite) : son envoi demande sa propre revue et, si elle est conseillée, sa propre revue de sécurité, chacune une fois sous la clé de cet envoi ; la revue faite ici d'un groupe jamais rendu a la sienne, `review:<groupe>#<n>`, n les envois commencés (0 pour un groupe jamais confié) : confié, annulé puis fini ici, le groupe demande une nouvelle revue d'ici ; un avis de sécurité envoyé pour un groupe en vol confié de nouveau, ou, depuis la 0.74.0, dont la revue ou l'avis ont été remis à zéro à un envoi pas encore revenu (le groupe porte alors la marque `isReset`, effacée seulement au retour d'un envoi : une annulation ou un « ↻ Renvoyer » de vague la gardent, une revue d'ici lancée avant pouvant finir pendant l'envoi suivant), est refusé, il peut être celui d'avant l'envoi : il s'envoie avec son retour ; pour un premier envoi en vol d'un groupe parti sans revue ni avis, l'avis envoyé d'ici reste gardé, comme avant. Les boutons « ◆ Revue du groupe » (et « · worker ») et « ⛨ Revue de sécurité » posent, sur une mission qui a été en auto, la marque de l'envoi auto de cette revue, déjà démarrée (le mod ne voit pas ton Entrée) : l'auto ne redemande pas une revue lancée à la main. Un lot à groupes que plus rien ne fait avancer sans un geste de ta part (un groupe relu sans avis de sécurité envoyé, un groupe fini ici avec une revue de sécurité conseillée et pas lancée, un groupe gardé vide après un envoi annulé ou un plan changé), sans rien en vol, sans question ni revue lancée dont le résultat est attendu, met l'auto en pause « plus rien ne peut avancer sans toi », avec sa notification, une fois la discussion au repos depuis 30 s, et 30 s après ton dernier geste sur l'auto (Claude envoie parfois l'avis au tour suivant ; rallumé, l'auto te laisse le temps de répondre). Une tâche externe pas faite (`kind` « task », ou sans type) n'est pas un blocage : dans l'implémentation (ou le découpage fini), quand sa levée ferait avancer le lot (l'auto, rejoué sur une copie de la mission où elle est faite, enverrait quelque chose, ou ouvrirait la relance d'un groupe revenu deux fois ; `awaitedExternals`), l'auto l'attend sans se mettre en pause, et repart seul quand elle est marquée faite (par l'outil flow, ou une mise à jour Asana faite par Claude : le mod ne lit pas Asana lui-même ; à la fin du tour, ou au guet des 5 s après un tour interrompu, tour fermé, trois essais au plus ; un lot sans groupes, lui, ne fait que le dire au bandeau : Claude y reprend lui-même ses tickets) ; une décision externe pas tranchée qui bloque un ticket ouvert (même quand une tâche est attendue ailleurs), ou un bloqueur que la mission ne connaît pas, garde la pause. Un `/code-review` lancé ici ne marque relus que les groupes finis ici, jamais un groupe confié (sa revue se fait dans son worker) ; `reviewed`, comme un avis de sécurité, est refusé pour un groupe en vol après une remise à zéro, et un `/security-review` lancé ici ne vise aucun groupe en vol. Un worker au travail (ou un groupe confié dont la session n'est pas encore lancée) compte comme un travail en vol : l'auto ne se met pas en pause tant qu'un groupe n'est pas rendu. Relancé par toi (« ↗ Worker »), le groupe voit sa question de troisième envoi retirée. Une vague ne part que si chacun de ses groupes se lie dans la même écriture que sa marque (un groupe lancé entre-temps par un bouton la retient). Une fois chaque ticket fait et chaque groupe rendu, relu et clos, l'auto lance le compte rendu, dont le lancement clôt l'implémentation.
- **Lancement refusé par l'app Desktop.** L'app ne lance une session (`start_session`) que sur un message que tu as tapé : le tour d'une vague que l'auto soumet au nom du mod est pour elle un événement automatique, et elle y refuse le lancement. Un `start_session` en erreur dans ce tour (reconnu à son texte, pas au premier tour venu : un message d'une autre session peut passer avant), sauf un lancement que tu as refusé ou interrompu, remet la même demande de lancement dans le prompt (une fois par tour, même pour plusieurs groupes), avec un toast : Entrée la lance, depuis un tour à toi. Claude lit après l'erreur de ne rien relancer lui-même, ni plus tard sur un message qui ne demande pas ce lancement, et de ne pas te demander de taper un message pour cela. La vague garde sa marque (ses groupes restent « worker à lancer ») ; ta session lancée se lie à son groupe comme d'habitude. Le CLI (`claude --bg`) n'a pas ce refus.
- **Relance du lot sans groupes (depuis la 0.77.0).** Sans groupes, pendant l'Implémentation, qu'elle soit encore active ou déjà finie (un `{"complete": true}` envoyé trop tôt), l'auto envoie lui-même la revue du lot à relire (`/code-review`, sans `--fix` quand un ticket est sensible ou ne l'a pas dit), une fois par passage, sous la clé `review:lot@<date de la dernière revue du lot avant elle, 0 sans revue, ou sa date négative pour une revue à refaire>~<dernière fin de ticket, 0 sans>~<empreinte des tickets faits>` (la revue d'un lot qui a vu d'autres tickets a une autre clé : après une revue refusée à la fusion, la marque que l'autre copie a posée sur la même revue de base ne retient pas celle d'ici ; « ◆ Revue » pose la même clé), avant le compte rendu ; puis, le lot relu, la demande de sa revue de sécurité quand son avis la conseille et qu'elle n'est pas lancée, une fois par revue du lot, sous `security:lot@<date de cette revue>` : un `/code-review` rechargé fait tomber l'avis (il doit suivre la dernière revue), et l'avis de cette revue fait relancer la sécurité sous sa clé ; la marque d'une autre revue ne la couvre pas. Un ticket ajouté puis fini après la revue change la clé : la revue du passage suivant part, l'ancienne marque ne la retient pas. Ni l'une ni l'autre ne part tant qu'une tâche de fond tourne (un spécialiste de sécurité que Claude a lancé ne pose aucune date de lancement), ni quand une question bloque la phase Implémentation ; elles partent au tour suivant si elles sont toujours dues. Un lot dispensé n'envoie rien, même avec un avis de sécurité explicite (son bouton reste), et passe au compte rendu une fois sa sécurité tranchée. Une fin de ticket datée de plus d'une minute dans le futur se relit maintenant : sinon chaque revue, datée avant elle, laisserait le lot à relire. « ◆ Revue » et « ⛨ Revue de sécurité » lancés à la main sur le lot posent la même clé, déjà démarrée : l'auto ne redemande pas ces revues ; la demande de sécurité du lot fait envoyer d'abord l'avis du passage (`"advised": true`), au lancement, puis les comptes sans lui (l'envoi qui ouvre un nouveau passage ne prend pas les comptes qu'il porterait : ils viennent d'une revue de sécurité lancée avant lui) : des comptes arrivés après une nouvelle fin de ticket ou une nouvelle revue du lot restent sur l'avis d'avant, et la réponse de l'outil demande de relancer la revue de sécurité. Les marques du lot se posent, démarrent, passent « sans suite » (question sur la phase Implémentation) et se fusionnent comme les autres. Avec des groupes, l'auto ne change pas.
- **Date du clic.** Le second clic garde aussi sa date dans le stockage du mod (`$.store`), une entrée par mission, avec la discussion du clic et le processus Claude Code qui l'a gardée : l'auto n'agit d'ici que si l'« allumé à » fusionné la vaut, dans ce processus (gardé après `/reload-plugins`, pas après un redémarrage de l'app ou un plantage, où il se met en pause « allumage non confirmé ici »). Un fichier de mission seule, forgé ou rejoué, ne le rallume donc pas : il s'affiche « ⚡ Auto en pause : allumage non confirmé ici », et deux clics le rallument. Si le stockage refuse l'écriture au clic, l'auto ne s'allume pas et un message le dit. L'entrée s'efface dès que la discussion du clic voit l'auto de cette mission éteint (l'entrée d'une autre discussion, d'un clic plus récent là-bas, reste), et à l'effacement de la mission, quelle que soit la discussion du clic. Rallumé au repos, l'auto envoie d'abord à Claude la consigne de l'allumage (voir « Claude prévenu de l'allumage »), et la suite part à la fin du tour de ce message.
- **Consignes à Claude.** Quand la mission est en auto et agit depuis la discussion (pas en pause ici), la consigne que flow-board ajoute à chaque skill finit par un bloc « mode auto », qui l'emporte sur les demandes de validation qui précèdent. Le bloc commun : ton clic (« Confirmer », ou « Lancer en auto » chez le COO) vaut accord pour cette mission ; chaque reco prise se déclare avec l'origine « reco prise », chaque validation sautée (accord du cadrage, spec, découpage, plan, écritures Asana de la mission) avec « validation sautée » et le chemin ou le lien du texte validé, au lieu d'une question à boutons ; une question en zone sensible se tranche seule quand l'option recommandée respecte l'invariant déjà validé (quand il y en a un) et qu'elle est la plus prudente (elle ne perd rien, n'expose rien, ne supprime rien sans retour) : Claude la code et la déclare comme une reco prise, le texte du choix commençant par « Zone sensible : », et le compte rendu la range à part dans « Décidé sans toi » ; sinon, elle reste une question bloquante ; une violation de l'invariant que trouve encore la passe high d'après les correctifs de la passe « bogues », corrigée de la façon la plus prudente, s'écrit en test et part en une ligne d'information, déclarée comme une reco prise « Zone sensible : … », pas en question ; six catégories restent des questions bloquantes (`waiting`), jamais des choix déclarés : un choix d'expérience (ce que tu vois et fais : mise en page, maquette, libellés, boutons, notifications ; ou toute question où les options se valent techniquement et ne diffèrent que par ta préférence), fixer ou affaiblir un invariant, ou un changement qui contredit une décision déjà prise, une suppression sans retour ou une exposition de tes données hors du poste (une publication), laisser une faille de sécurité sans correctif, l'effort xhigh d'un worker (Claude reste en high et déclare ne pas l'avoir proposé), une dépense ou une action externe hors de la mission ; le worker d'une mission en auto suit la même règle (section « Worker autonome » de sa procédure) ; chaque question bloquante déclarée part aussi en `PushNotification`, au texte exact « Mission <titre> : N question(s) t'attendent ». Puis le bloc de la phase : au cadrage, un seul tour de questions d'intention avec toi (but, périmètre, hors sujet), sauté pour une mission lancée en auto par le COO quand `travail/<sujet>/demande.md` porte déjà tes réponses (Claude lit ce fichier et ne le réécrit jamais), puis chaque question tranchée par la reco, écrite au fichier de décisions comme « acceptée en auto (reco) », et l'accord final déclaré ; à la spec, les coutures tranchées par la reco (écrites au fichier de décisions et déclarées « reco prise ») ; à la spec et au découpage, la validation déclarée, les écritures du suivi faites sans te les redemander, fixer ou affaiblir un invariant, et les questions de zone sensible qui ne remplissent pas la condition pour se trancher seules, en questions bloquantes ; en implémentation et aux revues, l'effort de la règle sans xhigh, toutes les failles retenues corrigées d'office (seul le choix d'en laisser une te revient), les constats sur du code antérieur listés pour le rapport, sans groupe « durcissement » ; au compte rendu, l'arrêt au rapport écrit, que tu valides. Allumé en cours de phase, Claude reçoit la même consigne (le bloc commun et celui de la phase en cours) dans l'avis « auto allumé » de la réponse suivante de l'outil, ou dans le message du mod (voir « Claude prévenu de l'allumage »). Hors auto, la consigne ne change pas ; coupé ou mis en pause après une consigne qui portait le bloc, la réponse suivante de l'outil le dit une fois à Claude, et les règles habituelles reviennent (validations à boutons, accord avant une écriture du suivi). Le texte de la notification est le même que celui du mod, titre compris.
- **Notifications.** En auto, le mod lève une notification sur le poste (`$.ui.notify`) quand une question apparaît, « Mission <titre> : N question(s) t'attendent », et quand l'auto se met en pause sans un geste de ta part, « Mission <titre> : auto en pause (<raison>) ». Jamais le texte d'une question ni du code ; rien hors auto, ni quand tu le coupes. Une notification qui ne part pas (pas de canal, l'app desktop, une discussion qui se ferme) ne bloque rien.
- **Traces de retrait écrites ici (depuis la 0.74.0).** Une trace « ↻ Renvoyer » (une marque d'envoi retirée) ou « répondue » (une question retirée) que la discussion d'où l'auto agit n'a pas écrite ne fait jamais repartir une action ni retirer une question pour l'auto de cette discussion. Chaque trace qu'elle écrit (« ↻ Renvoyer » cliqué ici, marque retirée faute d'envoi, question retirée par Claude ici, question d'un groupe relancé ou « envoi resté sans suite » qui démarre) se garde aussi dans le stockage du mod (`$.store`), avec la discussion et le processus, comme la date du clic, les 100 plus récentes de chaque sorte. Tant que l'auto de la mission est allumé au nom de cette discussion, avec la date du clic gardée ici (qu'il envoie d'ici, ou qu'il y reprenne sans nouveau clic, la mission mise en pause par l'ouverture d'un autre), la fusion des copies d'ici ne lui applique que ces traces : une marque en attente ou une question qu'une trace d'ailleurs (copie forgée, rejouée, ou allumage précédent) aurait retirée reste dans la copie d'ici, et dans ce qu'elle réécrit au fichier ; la question reste affichée et bloque, la marque suit « envoi resté sans suite » puis « ↻ Renvoyer » ; et l'entrée ouverte d'ici d'une question l'emporte sur celle de même id de l'autre copie (voir « Questions bloquantes »). Les traces gardées dans la mission restent l'union, et les autres discussions, ou celle-ci une fois l'auto éteint (coupure, arrêt, pause posée par le mod), les appliquent toutes. Ces traces gardées s'effacent avec la date du clic (aux mêmes arrêts de l'auto) et avec la mission ; elles restent reconnues après `/reload-plugins`, pas après un redémarrage. Une trace datée à plus d'une minute dans le futur est ramenée à maintenant à la lecture : elle n'efface plus les marques et les questions posées ensuite.
- **Valeurs relues (depuis la 0.74.0).** Le fichier de mission se réécrit depuis toute discussion du projet : une valeur qui en vient n'entre dans un texte que le mod soumet seul (vague, revue du groupe, revue de sécurité) qu'avec sa forme vérifiée, puis échappée en JSON là où elle est entre guillemets : l'id de la mission et l'id du worker d'un groupe (lettres, chiffres, `_` et `-`), l'id d'un groupe (lettres et chiffres ASCII, 12 au plus). Hors forme, la demande ne part pas et l'auto se met en pause « lecture de la mission ratée », avec un toast qui dit quelle valeur ; un groupe à l'id hors forme que l'auto aurait encore à faire avancer (confié, pas fini, ou fini sans être clos) le met aussi en pause au lieu d'être écarté en silence ; un bouton qui aurait mis la demande dans le prompt (« ↗ Worker », « ⇉ en parallèle », « ◆ Revue du groupe · worker », « ⛨ Revue de sécurité ») n'y met rien et le dit, sans recopier la valeur. La branche par défaut du distant (lue de `git symbolic-ref`) n'entre dans « git merge --ff-only » que si elle a la forme d'un nom de branche ; sinon la demande dit « la branche principale », sans commande. L'id de la mission dans le brief d'un diagnostic de bug, et la référence du manager qu'un worker relit à côté du relais, s'écrivent échappés en JSON. Les titres de mission et les phases que citent les réponses de l'outil (« Dashboard: … », la reprise, l'ouverture d'une mission, la liste des missions à reprendre, les réponses d'un worker) sont neutralisés comme un texte relayé (fins de ligne « ⏎ », « · » montrés « • ») ; un id de mission hors forme s'y cite échappé en JSON. La raison d'une fermeture (« à archiver dans l'app », « fermeture arrêtée ») est bornée par un seul lecteur, à l'entrée de l'outil, dans sa réponse et dans le panneau : une ligne, 200 caractères au plus ; la réponse de l'outil la cite en JSON, neutralisée comme un texte relayé. Les ids des questions ouvertes que liste la réponse de l'outil s'y écrivent tels quels quand ils ont la forme d'un id de question (lettres et chiffres ASCII, puis `_ : # + . -`, 200 au plus), échappés en JSON sinon. Dans les consignes données avec un skill (les faits du compte rendu : titre, tickets, tâches trouvées en route, choix, fichiers, alertes du journal ; la file et les tickets en cours rappelés au chargement de `/implement`), les valeurs relues perdent leurs fins de ligne (montrées « ⏎ »), contrôles et invisibles, et gardent leurs guillemets et leurs « · » ; dans les demandes mises dans le prompt et dans les réponses de `/flow pause`, de `/flow reset` et de `/flow` sans mission active, elles montrent en plus leurs guillemets « » en “ ” et leurs crochets en ( ) ; `/flow` avec une mission active reprend la ligne « Dashboard », neutralisée comme un texte relayé.

**Tickets en cours en parallèle (depuis la 0.32.0)**
- Plusieurs tickets peuvent être « en cours » à la fois : ceux des workers des groupes, ou un ticket laissé en cours par une autre discussion. Depuis la 0.40.0, ils se lisent dans leur groupe (« ◉ en cours »), et un ticket porté par une autre discussion le dit sur sa ligne (« ⇆ autre discussion »). Pendant l'Implémentation, la carte de la phase ne les répète plus à part, et le bandeau ne les nomme plus.
- Le ticket retient la discussion qui l'a passé « en cours » (champ `by`), et l'oublie quand il en sort. Un ticket qui rejoint d'autres tickets déjà en cours ne remet pas les étapes à zéro ; un ticket qui en suit un autre, si.

**Dépendances**
- À la fin de `/to-tickets`, Claude envoie pour chaque ticket la liste des tickets qui le bloquent (`blockedBy`).
- Il signale aussi les dépendances hors du lot (`externals`), de type décision ou tâche. Une décision attendue s'affiche « ⚖ Décision à prendre ».
- Une dépendance externe se lève quand la tâche est cochée dans Asana. Un bloqueur inconnu de la mission bloque par prudence.
- Un ticket qui n'attend que d'autres tickets reste « à faire » et s'affiche « ⏸ en attente ». Le statut « bloqué » est pour une attente hors du lot (une décision ou un accord de la personne, un accès, le travail de quelqu'un d'autre) : Claude en donne la raison (`why`), affichée sous le ticket (« ! attend : ton accord sur le plan »). Un ticket bloqué sans raison derrière un ticket ouvert s'affiche en attente ; sans raison ni ticket ouvert, « raison non précisée ».

**Décidé sans toi**
- Chaque fois que Claude fait un choix que tu n'as ni demandé ni validé, il le signale (`decided`, avec sa raison). La règle est dans la description de l'outil, donc toujours connue de Claude. Depuis la 0.54.0, un choix qui touche une zone sensible (confidentialité, suppression de données, chiffrement, concurrence, commande ou chemin construit à partir d'une valeur lue ailleurs : fichier partagé, autre session, compte rendu) n'est jamais déclaré : la description de l'outil et la consigne des skills de cadrage (grilling, `/to-spec`, `/to-tickets`, `domain-modeling`) en font une question à te poser, et une entrée de décision recopie la question et ta réponse au lieu de les résumer. Depuis la 0.56.0, avant une question de confidentialité, Claude fait vérifier l'exposition réelle par un spécialiste en lecture seule, sinon la question la dit « à confirmer » ; le grilling et `/to-spec` ont une étape « Conséquences sensibles » (ce qu'un changement ou un retrait laisse derrière lui : fichiers en clair, journaux qui dépendent d'un mode, données gardées).
- **Fichier des choix déclarés** (depuis la 0.54.0) : le manager tient `~/.claude/flow-board/choix/<id de la mission>.md`, réécrit à chaque changement d'après la mission et le relais (ses choix et ceux des workers). Les briefs et les consignes de revue citent son chemin au lieu de recopier la liste, avec une consigne des relecteurs à donner telle quelle : attendre tous les axes d'une revue avant de rendre son rapport, ne pas relancer les tests, ne rien appliquer de ce qui est laissé à un autre groupe.
- La carte de la phase l'affiche en haut, sous « ⚑ Décidé sans toi » (les 40 plus récents à relire, et les 40 plus récents relus une fois dépliés ; les autres comptés), et le bandeau compte « ⚑ N à relire ».
- « ✓ Relu » marque tout comme relu : les choix relus se replient en une ligne (« 17 relus »), que « ▸ voir » déplie ; le journal de l'onglet Activité les garde.
- **Origine et plafond en mode auto** (depuis la 0.74.0). Un choix peut porter son origine (`origin` de l'outil) : « reco prise » (`recommendation`), « validation sautée » (`skipped-validation`, avec le chemin ou le lien du texte validé), « choix de worker » (`linked-session`, que prend d'office, sur une mission qui a été en auto, un choix relayé par un worker) ; un choix sans origine reste valide, une origine inconnue est écartée et la réponse le dit. Le panneau la montre à côté du choix, le fichier des choix et les faits du compte rendu la gardent, et le rapport regroupe « Décidé sans toi » par origine quand il y en a. Hors auto, rien ne change : les 30 choix les plus récents. Une mission qui a été en auto (son mode auto allumé une fois, même éteint depuis) ne coupe aucun choix avant « ✓ Valider le rapport » : à 200 choix, l'auto se met en pause (« limite de 200 choix atteinte ») et les suivants sont gardés ; au-delà de 1 000, un nouveau choix déclaré ici est refusé avec un message, jamais un ancien coupé (un remplaçant refusé laisse en vigueur le choix qu'il devait remplacer) ; les choix relayés par les workers se gardent tous (le relais en borne 200 par session) ; une fois le rapport validé par « ✓ Valider le rapport » (pas par une clôture), il garde les 200 plus récents. Au-delà de 40 choix, les faits donnés au compte rendu en disent les comptes par origine et les 40 plus récents, et renvoient au fichier des choix pour les autres. À la fusion des copies de deux discussions, ses choix s'unissent un par un (le relu, le retrait et l'origine de l'une ou l'autre copie gardés) au lieu de reprendre la copie la plus récente. Le relais d'un worker garde au plus 200 choix par session, comme avant (au-delà, refus).

**Trouvé en route**
- Les tâches créées pendant la mission (constats de revue hors du ticket, anomalies, actions pour la personne) s'affichent sous les tickets, dans « Trouvé en route » : l'état en glyphe de tête, la raison d'un blocage, « pour toi » quand la tâche est assignée, le lien Asana (au terminal, le bouton qui le copie). Celles qui t'attendent (bloquées, ou assignées à toi) viennent en tête et restent toujours visibles ; les autres s'affichent jusqu'à 4, le reste derrière « ▸ N de plus ». « × masquer » réduit toute la liste à son titre et ses comptes ; « ▸ afficher » la rouvre.
- Elles ne comptent pas dans la barre des tickets et ne retiennent pas la livraison.
- Claude fait entrer dans le lot celles dont le lot dépend, en les envoyant dans `tickets` avec leurs `blockedBy` ; elles quittent alors « Trouvé en route ». `remove` en retire une.
- Les règles des statuts et des trouvailles sont dans la description de l'outil : Claude les a même quand aucun skill n'a apporté sa consigne (par exemple `/mattpocock-skills:implement` écrit au milieu d'un message, qui n'est pas lancé).

**Lancer une sélection de tickets** (par exemple depuis une nouvelle discussion)
1. Historique, puis « Reprendre » sur la mission.
2. Dans l'onglet Mission, choisir les tickets avec ○, dans l'ordre voulu (①, ②, ③…). Un ticket bloqué n'est sélectionnable que si ses bloqueurs sont faits, ou choisis avant lui.
3. « ▶ Implémenter N tickets » met `/mattpocock-skills:implement` dans le prompt, avec la liste ordonnée. La file est enregistrée dans la mission, et Claude la reçoit au chargement du skill.
4. Pour faire avancer des tickets en parallèle, passer par les groupes et leurs workers (« Groupes et vagues » ci-dessous). Le bouton « ⇉ En parallèle » d'une sélection, qui lançait `/implement-spec`, a disparu en 0.63.0.

**Groupes et vagues**

À la fin de `/to-tickets`, Claude regroupe les tickets selon leur contexte (`groups`). Depuis la 0.60.0, **un groupe ne se fait que dans un worker** :
- les tickets d'un groupe touchent les mêmes fichiers ou s'enchaînent par leurs dépendances ; son worker les fait d'affilée avec `/implement`, en profitant du contexte déjà chargé, et la mission reste dans le manager ;
- plusieurs groupes indépendants peuvent avancer en même temps, un worker chacun ;
- un autre contexte fait un autre groupe, et un groupe d'un seul ticket convient quand son contexte lui est propre ;
- l'id d'un groupe a de 1 à 12 lettres ou chiffres ASCII (`[A-Za-z0-9]`), rien d'autre : il entre dans le nom du worktree, le titre et les commandes de la session. Un plan qui porte un autre id est refusé en entier, sans être nettoyé : la réponse nomme chaque id refusé, pour que Claude renvoie le plan, et le plan en place reste. Un id déjà enregistré dans la mission, d'avant cette règle, reste accepté tel quel, mais son groupe ne se lance pas (sa session ne se fermerait jamais d'office) : le bouton dit de le renommer dans le plan ;
- les lettres suivent l'ordre d'exécution : A part le premier, et un groupe qui en attend un autre (un ticket bloqué par un ticket de l'autre groupe, ou par une dépendance hors du lot alors qu'un autre groupe est prêt) porte une lettre plus loin. Un plan dans le désordre est gardé, et la réponse de l'outil nomme chaque écart (« B waits for C », « B waits outside the lot, C is ready ») pour que Claude renvoie le plan aux lettres remises dans l'ordre ; rien une fois un groupe confié à un worker, dont la lettre nomme déjà la session et la branche ;
- un plan renvoyé ne fait rien perdre de ce qui est en cours : un id qui ne change que de casse (« a » pour « A ») est le même groupe, qui garde son id enregistré (il nomme son worktree et sa branche), sa revue, sa sécurité, ses liens, ses fermetures et son compteur d'envois ; l'id exact passe d'abord, pour une mission d'avant qui porterait deux ids jumeaux. Deux ids d'un même plan qui ne diffèrent que de casse font un seul groupe, qui réunit leurs tickets, et la réponse le dit. Un groupe déjà confié à un worker, en cours, rendu, fermé, ou dont l'envoi a été annulé (son numéro reste pris), n'est jamais retiré : omis, il est gardé à la fin du plan, même vide, avec son lien et son compteur d'envois (un envoi suivant au même id ne reprend jamais le nom d'une branche gardée). Un groupe en cours, ou rendu sans être fermé, garde aussi ses tickets, qu'il soit dans le nouveau plan ou omis : ils quittent les autres groupes du nouveau plan (un groupe ainsi vidé part, s'il n'a jamais été confié). Un retrait de tickets (`remove`) ne retire pas non plus un groupe confié qu'il vide. Un groupe fermé, ou à l'envoi annulé, laisse le plan donner ses tickets à un autre groupe. La réponse dit chaque groupe et chaque ticket gardés. De même, un envoi des pistes d'une rétro qui omet une piste en cours, ou confiée au worker sans verdict, la garde telle quelle, et la réponse le dit ; la borne du nombre de pistes ne coupe jamais une piste confiée ou en cours ;
- **pas de groupe seul** (depuis la 0.60.0) : un lot qui n'aurait qu'un groupe n'en a pas. La consigne de `/to-tickets` dit à Claude de ne pas envoyer de groupes dans ce cas, et le mod ignore quand même un plan reçu qui, une fois ses tickets rangés, ne compte qu'un groupe (un groupe plus des tickets restés hors de lui compte aussi pour un seul) ; la réponse de l'outil le dit à Claude en une ligne. Un plan déjà en place n'est jamais remplacé ni vidé par cette règle. Un lot de rétro fait exception (depuis la 0.72.0) : son plan d'un seul groupe est gardé, et ce groupe part dans un worker comme les autres, puisque la discussion de la rétro est déjà chargée de la lecture des sessions. Un lot sans groupe qui a des tickets ouverts se lance d'un geste par « ▶ Tout implémenter ici » (pas pendant `/to-tickets`, où les groupes peuvent encore venir) : `/implement` sur tous ses tickets ouverts, dans l'ordre du lot.

Avant la 0.60.0, un groupe pouvait aussi se lancer dans la discussion courante (par un bouton sur sa ligne, ou pour ses seuls tickets prêts), un lot de groupes par `/implement-spec` (un spécialiste par groupe), et un groupe marqué `continuesHere` se gardait pour la discussion du découpage (« ↩ cette discussion »). Ces lancements et ce champ ont disparu : un `continuesHere` reçu est ignoré, celui des anciens fichiers reste sans effet. Un groupe déjà commencé ici avant ce changement garde son suivi (« Un groupe à la fois » ci-dessous). Les tickets choisis à la main, hors groupes, gardent `/implement` (« Lancer une sélection de tickets »).

Pour chaque groupe, Claude donne la raison du regroupement, les fichiers touchés (`files`) et, depuis la 0.34.0, ses **ressources** (`resources`) : ce qu'il ne peut pas partager avec un autre groupe qui travaille en même temps, comme une application pilotée à l'écran (« PowerBI Desktop »), une base, un appareil ou un compte uniques. Chaque ticket peut aussi porter ses propres fichiers (`files`), lus dans ses critères d'acceptation : ils s'ajoutent à ceux de son groupe tant qu'il est ouvert. Quand un groupe déclare un dossier qui contient un fichier nommé par un autre groupe, la réponse de l'outil le signale à Claude : un dossier bloque tous ceux qui touchent un fichier dedans. Une nouvelle liste de groupes remplace la précédente, en gardant les revues et les workers de chaque groupe ; des tickets envoyés sans groupes ne la touchent pas.

Depuis la 0.56.0, chaque ticket dit aussi « Zone sensible : oui/non (pourquoi) » et « Logique : oui/non » (pas de logique : une ressource visuelle, un document), envoyés à l'outil (`sensitive`, `logic`) et gardés avec le ticket. Le « pourquoi » de la zone sensible répond à trois questions, reposées par la session avant chaque ticket : construit-il une commande ou un chemin à partir d'une valeur lue ailleurs ? écrit-il des données gardées que d'autres discussions ou sessions écrivent aussi ? supprime-t-il des données ? Un seul oui rend le ticket sensible, un oui à la deuxième ou à la troisième très sensible ; un worker qui reclasse un ticket corrige sa ligne et le dit par une note, et le manager le renvoie avec `sensitive`. Depuis la 0.73.0, un ticket dont le texte fait lancer une commande à Claude ou construire un chemin (une règle, une procédure, un skill) se déclare « Logique : oui » : découpé sans logique, il perdrait la revue du groupe et l'avis de sécurité. Une piste de rétro en zone sensible fait un ticket à elle seule. Une écriture de `CLAUDE.md` n'entre jamais dans le « Fini quand » d'un ticket de groupe : un worker ne peut pas la faire, c'est un geste du manager. Un ticket de pistes d'une rétro fait exception : sa session écrit le fichier chargé dans toutes tes sessions (règles communes, `CLAUDE.md`) et cite chaque phrase ajoutée ou retirée dans son compte rendu, et tu relis avant la fusion.

Le mod en déduit le reste :

| Calcul | Règle |
|---|---|
| Attente | Un groupe attend un autre quand l'un de ses tickets a un bloqueur encore ouvert dans cet autre. |
| Vagues | Une vague est un ensemble de groupes qui peuvent tourner en même temps, chacun dans son worker (glossaire). Le mod range les groupes par niveau d'attente : un groupe passe dès que ceux qu'il attend sont passés. Une attente circulaire met ses groupes au même niveau, marqués « ⚠ ordre à revoir ». Depuis la 0.60.0, les titres « Vague N » ne s'affichent que si au moins un niveau a deux groupes ou plus qui peuvent avancer ensemble (sans fichier ni ressource en commun, hors attente circulaire) ; sinon les groupes se suivent dans l'ordre, chacun avec son « attend A ». |
| Lot parallèle (∥) | Les groupes **prêts** (aucun bloqueur encore ouvert), **pas encore commencés** (aucun ticket en cours ni fait) et pas confiés à un worker, pris dans l'ordre ; un groupe n'est retenu que s'il ne partage **aucun fichier ni aucune ressource** avec ceux déjà retenus ou confiés à un worker (un dossier recouvre les fichiers qu'il contient ; les fichiers d'un groupe sont les siens et ceux de ses tickets ouverts) : un fichier ou une ressource en commun retire le groupe du lot parallèle, sans créer d'attente (il part plus tard, seul ou dans un autre lot). Depuis la 0.56.0, les documents que presque tous les tickets citent (`README.md`, `DECISIONS.md`, la carte du code `carte-du-code.md` ou `CODEMAP.md`, où qu'ils soient) ne comptent pas : leurs ajouts se fusionnent sans peine. Il faut au moins deux groupes. |
| Raisons (∦) | Un groupe prêt resté hors du lot dit pourquoi : « ∦ A : tables » (le groupe, et le fichier ou la ressource en commun). Il le dit aussi face à un groupe confié à un worker ou en cours ici. |
| Autres lots | Chaque groupe prêt resté hors du lot principal en ouvre un autre, formé de la même façon à partir de lui (trois au plus) : « Autres lots possibles ». |
| Un groupe à la fois | Tant qu'un groupe est commencé ici et pas fini, aucun lot ne part : le panneau affiche « ⇉ B ∥ C en parallèle une fois A fini ». Un groupe confié à un worker n'occupe pas la mission. |
| Autres | Un ticket ajouté au lot pendant qu'un groupe s'exécute rejoint ce groupe (avant le premier de ses tickets qu'il retient), sauf si Claude renvoie lui-même les groupes. Un ticket ajouté autrement, sans groupe, rejoint la chaîne dont il fait partie : le groupe des tickets qu'il retient (placé avant le premier), sinon celui des tickets qu'il attend (à la fin). Seuls les tickets qui ne tiennent à aucun groupe, ou à plusieurs, restent dans « Autres ». Claude est aussi invité à renvoyer les groupes quand il ajoute un ticket. |
| Entre missions | Juste avant de lancer un groupe (ou le lot qu'un manager fait lui-même, qui compte comme un groupe : ses fichiers sont ceux de ses tickets non faits), le mod relit le fichier des missions : un groupe en cours d'une autre mission (confié à un worker, ou rendu et pas encore clos) ou un lot sans groupes en cours (un ticket pas fait, la file posée ou le code commencé, même en pause) qui nomme un même fichier ou une même ressource le retient, même sans COO ouvert ; les documents communs, plus `ETAT_DU_PROJET.md` et `GLOSSARY.md`, ne retiennent pas. Un groupe déjà parti n'attend jamais. La retenue n'est pas enregistrée : chaque discussion la calcule ; elle se lève seule quand le groupe attendu est clos ou annulé, ou sa mission supprimée ; une mission close ou archivée ne retient plus que par ses groupes encore confiés à un worker (ou rendus, pas clos), qui peut écrire après sa clôture. Sa ligne dit « ⏸ attend B · groupe D de « <mission> » (fichier commun) », la carte « Ensuite » et le bandeau le disent aussi ; « ⇥ Forcer » (sur la ligne, la carte, ou chez le COO) la lève pour la seule paire nommée, un autre conflit retenant de nouveau. Une lecture ratée du fichier des missions juste avant ne lance rien. En auto, seule la branche retenue attend, sans pause, et l'auto la relance quand la retenue tombe. |

Dans l'onglet Mission, les tickets sont alors rangés par niveau d'attente (titré « Vague N » quand une vague existe vraiment), puis par groupe :
- « ↗ Worker », sur tout groupe prêt, confie le groupe à un worker ;
- « ↗ xhigh » (depuis la 0.67.0), discret, juste après, confie le même groupe à un worker en xhigh : Claude ne pose aucune question sur l'effort, et la session est un worker autonome (voir plus bas) ; la carte « Ensuite » le porte aussi après « ↗ Groupe <id> · worker », jamais le lot parallèle ;
- « ⇉ A ∥ B en parallèle · workers » confie chaque groupe du lot au sien. Les groupes qui attendaient (niveau d'attente suivant) deviennent parallélisables à leur tour une fois leurs bloqueurs faits ;
- la carte « Ensuite » propose de même le worker du prochain groupe prêt, ou les workers du lot, jamais un lancement ici.

Les groupes d'un lot de rétro, faits de tickets de pistes, se lancent de la même façon, et leur session suit la même procédure : les pistes y arrivent comme des tickets.

Le fonctionnement des workers est détaillé plus bas.

**Groupes dans un worker** (depuis la 0.34.0 ; avant, le worker d'un groupe reprenait la mission)

« ↗ Worker » ou « ⇉ … · workers » met dans le prompt une demande à Claude, et le groupe passe « ↗ worker à lancer » (avec « Annuler »). La demande lui fait :
- régler d'abord avec la personne ce dont les sessions auront besoin (une décision, un accès, un geste qui lui est réservé) ;
- lancer une session par groupe, avec un titre de la forme « <mission> > Groupe <id> · <thème> » : `start_session` dans l'app (`context` « fresh », `wake_when_done`, un worktree nommé par `branch_name` « groupe-<parcours>-<id> » depuis la 0.61.0, ou le dossier s'il n'a pas de git), `claude --bg -n '<parcours> > Groupe <id> · …'` dans le CLI (`-w 'groupe-<parcours>-<id>'` dans un dépôt git ; le titre et le worktree sont cités pour le shell entre apostrophes, une apostrophe du titre écrite `'\''`, ce que la demande rappelle à Claude pour le thème qu'il y met). Depuis la 0.53.0, Claude choisit l'effort de chaque session (`effort` de `start_session`, `--effort` de `claude --bg`) : medium par défaut, high s'il reste des choix de conception ou si le groupe touche plusieurs modules de code (jusqu'à la 0.80.0, aussi s'il avait un ticket qui touche une zone sensible : depuis, le mod du worker passe la session en high pendant ce seul ticket, section « Effort d'un manager qui fait le travail d'un worker ») (depuis la 0.80.0 : dossier de premier niveau ou paquet sous `plugins/` ou `packages/`, la racine comptant pour un ; `.md`, `.txt`, `travail/` et `docs/` ne comptent pas), et il le dit en une ligne ; avant, la session prenait l'effort de la discussion (l'app ne lui en donne jamais un plus haut). Depuis la 0.80.0, le mod calcule cet effort par la même règle que pour un manager (`groupLaunchNote` de `hooks/effort.ts` : les fichiers des tickets ouverts du groupe et ceux que le groupe déclare ; un ticket sensible n'y compte pas) et l'écrit sur la ligne de chaque groupe de la demande de lancement, par exemple « effort calculé : medium » ou « effort calculé : high (plusieurs modules de code) » ; la demande dit aussi que le mod de la session la passe en high pendant un ticket sensible ; Claude lance chaque session à l'effort calculé, passe en high un groupe à qui il reste un choix de conception (le seul critère que le mod ne sait pas), et dit en une ligne l'effort pris et, s'il s'écarte du calcul, pourquoi. Les critères du calcul et l'arbitrage high / xhigh ne sont plus recopiés dans la demande : elle renvoie à la section 11 de la procédure, à lire avant de lancer. Depuis la 0.80.0 aussi, l'**option fusion** : un groupe dont chaque ticket dit « Zone sensible : non » et « Logique : non » (`isNoLogicGroup` de `hooks/model.ts` : documents, réglages, ressources) part en worker Sonnet high, que sa ligne annonce (« Sonnet high, sans logique ») : `model` à l'id de Sonnet et `effort "high"` dans `start_session`, `--model sonnet --effort high` dans `claude --bg` (l'id et l'alias sont écrits une fois, `SONNET_APP_ID` et `SONNET_CLI_ALIAS` de `hooks/effort.ts`, à revoir à la sortie d'un nouveau Sonnet ; règle du paramètre `model` de l'app : `docs/regles-app-desktop.md` du dépôt). Tout autre groupe, un groupe dont un ticket ne dit pas l'un des deux drapeaux et un groupe en xhigh (imposé par le bouton ou accepté à la question à boutons) ne reçoivent aucun modèle et héritent de celui de la discussion (Opus pour un manager sur Opus) ; manager, COO, workers de diagnostic ou de pistes et spécialistes ne changent pas. Un worker sur Sonnet lance chaque revue et chaque relecture du fond et de la forme dans un spécialiste avec le modèle opus passé explicitement, et garde le moment (c) de l'advisor même quand ses revues ont tourné (section 6 de la procédure) : l'advisor relit un modèle moins fort que lui. Sur trois tickets courts, Sonnet high avait livré le même réglage qu'Opus medium pour 0,44 fois son coût hors advisor ; sa seule erreur portait sur un texte avec logique. Depuis la 0.67.0, Claude propose aussi xhigh, sans jamais le choisir seul : quand un ticket du groupe est une tâche de jugement (un *jugement sur un existant* : une pièce dont d'autres dépendent, des conventions non écrites, ce qui ne doit pas bouger ; ou un *objectif ouvert* : des critères de fini qualitatifs, un livrable lu par d'autres, une grosse fonctionnalité peu guidée, une boucle d'essais), jamais pour une tâche d'exécution, il pose avant de lancer une question à boutons « xhigh (Recommandé) / high » par groupe concerné (quatre au plus par encadré), avec une ligne qui nomme le ticket et la sorte de jugement ; un ticket sensible qui demande du jugement sur un existant en relève aussi, sensible mais local il reste en high. Une session lancée en xhigh, ou, quel que soit son effort, par une mission en mode auto (jamais en xhigh : l'auto ne le propose pas, et le déclare), est un **worker autonome** : son prompt le dit, et il suit la section « Worker autonome » de la procédure (`reference/procedure-groupe.md`) : il tranche lui-même ses choix de conception hors zone sensible, après l'advisor (sans lui, en relisant son choix), et les déclare dans `decided` ; un choix sensible, ou dont la sensibilité est douteuse, reste une question ; ses revues gardent leur effort. Dans l'app, `start_session` plafonne la session à l'effort de la discussion (constaté en 0.53.0, à confirmer sur l'app actuelle) : la demande donne à Claude l'effort relevé de la discussion à son écriture (sur sa propre piste du registre des agents ; il a pu monter depuis, avant Entrée) et lui fait demander de la passer en xhigh avant de lancer, puis rappeler qu'elle peut redescendre une fois la session lancée. « ↗ xhigh » fait la même demande avec l'effort xhigh imposé, sans la règle de suggestion ; son message de confirmation dit « Worker pour <id> en xhigh : la demande est dans le prompt, Entrée pour la lancer », et, sur la surface desktop quand l'effort relevé de la discussion est low, medium ou high, ajoute de la passer en xhigh avant Entrée (rien au terminal, où `claude --bg --effort xhigh` n'a pas ce plafond, ni sans effort relevé). Le mod relève l'id de la session dans la réponse de `start_session` ou dans la sortie de `claude --bg`, et le range au groupe que le titre nomme (« ↗ en cours · worker » depuis la 0.56.0, « ↗ worker au travail » avant) ;
- de la 0.54.0 à la 0.59.1, avant le premier worker de la mission, te demander de renommer la discussion de son nom définitif ; depuis la 0.60.0, ce nom est fixé par la règle du titre (« Titre de la mission et de la discussion ») et ne bouge plus une fois un worker demandé ;
- rédiger le background sans y reprendre le texte des règles (depuis la 0.54.0 : écritures permises, gestes réservés, dépôt public, modèle et effort des revues se citent par leur document, une copie se périmait) ; il ne garde que ce qui varie : le projet, les tickets, ce que font les autres sessions, les décisions par renvoi, le chemin du fichier des choix déclarés ; puis le prompt de chaque session : appeler d'abord l'outil avec `{"delegate": "<id de la mission>", "group": "<id du groupe>", "main": "[ref]"}` (`main` : le manager, depuis la 0.45.0, par sa seule référence depuis la 0.56.0 ; chaque réponse de l'outil rappelle alors comment la joindre) ; puis faire les tickets du groupe dans l'ordre, chacun avec `/mattpocock-skills:tdd`, les contrôles, `/mattpocock-skills:code-review` sur le seul ticket (même pour un petit diff) et un commit ; pour un ticket qui touche une zone sensible (confidentialité, suppression de données, chiffrement, concurrence, commande ou chemin construit à partir d'une valeur lue ailleurs : fichier partagé, autre session, compte rendu), la passe « bogues » `/code-review <niveau>` (voir le tableau des revues) part dans le même message que cette revue, sur le même périmètre, avec le chemin du fichier des choix déjà déclarés (depuis la 0.54.0 ; avant, leur liste) et la consigne des relecteurs ; une fois tous commités, lancer elle-même `/code-review high --fix` sur le groupe (pas pour un groupe d'un seul ticket, depuis la 0.78.0), dans un spécialiste relecteur (general-purpose, Opus, effort high depuis la 0.52.0) qui applique lui-même ses correctifs (depuis la 0.49.0 ; le seul spécialiste qui écrit), avec cette même liste et la consigne de se concentrer sur les interactions entre les tickets (elle ne tranche pas un conflit entre la spec et une consigne : elle le remonte, depuis la 0.46.0), puis relire le diff de ses correctifs, relancer les contrôles et les commiter ; puis, si elle la juge utile, confier la revue de sécurité à un spécialiste relecteur (general-purpose, Opus, lecture seule ; effort `xhigh` jusqu’à la 0.57.1, `high` ou `xhigh` selon la méthode de la 0.58.0 à la 0.78.0, `high` depuis) limité à `git diff <base>..HEAD`, avec les critères de `/security-review`, sans corriger ses failles (depuis la 0.45.1 ; avant, elle lançait `/security-review`, qui calcule son diff contre la branche par défaut et relisait aussi les autres groupes) ; sans autre spécialiste qui écrit ; écrire chaque script par Write puis le lancer par une commande simple, avec le chemin absolu de son dossier temporaire écrit en clair (lu une fois par `printenv CLAUDE_JOB_DIR`) ; donner un délai maximal à chaque commande longue et ne jamais rendre la main en attendant un processus d'arrière-plan qui n'en a pas (le surveiller par Monitor ou l'arrêter, depuis la 0.54.0) ; et finir par un compte rendu (tickets, revue du groupe, revue de sécurité), envoyé par SendMessage et, depuis la 0.54.0, déposé aussi par l'outil (`{"report": "…"}`) dans le relais de la mission. Depuis la 0.38.0, les étapes d'`/implement` sont écrites en clair : `/mattpocock-skills:implement` est réservé à l'utilisateur, une session ne peut pas le lancer par l'outil Skill. Depuis la 0.80.0, flow-board écrit lui-même ce background, un fichier par groupe (paragraphe « Brief écrit par flow-board » plus bas) : Claude n'y ajoute que ce que le mod ne sait pas, sous « Ce qui varie », et la rédaction décrite ici ne vaut plus que pour le repli, quand le brief n'a pas pu s'écrire.
- pendant le travail, suivre chaque session par l'état git de son worktree, le tracker et `ListAgents`, jamais par `claude logs` (depuis la 0.54.0) ; un compte rendu perdu en route (discussion renommée ou redémarrée) revient par le relais : tant que son groupe n'est pas rendu, chaque réponse de l'outil dans le manager cite le compte rendu déposé, en entier la première fois et à chaque reprise, puis en une ligne qui renvoie au relais ;
- à la note de fin, dans le manager : vérifier dans le compte rendu de la session que la revue du groupe a tourné (sinon, la lui demander ; pas de revue du groupe pour un groupe d'un seul ticket, depuis la 0.78.0 : seulement son avis de sécurité ; ni revue du groupe ni revue de sécurité sans logique ni zone sensible) avant de fusionner sa branche, puis rendre le groupe (`set`, `"returned"`, et `"reviewed"` quand la revue du groupe a tourné) et envoyer l'avis et les constats de sécurité de la session (`security`).

**Brief des workers (depuis la 0.56.0).** Dans un dépôt git, le manager écrit en tête du background l'installation de worktree que le projet déclare : c'est la première commande de la session, avant toute lecture (le document des sessions déléguées manquait tant qu'elle n'avait pas tourné), ou la mention qu'il n'y en a pas ; depuis la 0.80.0, avec le brief écrit par flow-board, elle arrive sous « Ce qui varie », à la fin, et la procédure du brief la fait lancer en premier. Le manager est désigné par sa seule référence `[ref]` (aussi dans `main` de `delegate`), résolue par `ListAgents` : son nom pouvait être périmé. Le compte rendu complet va au relais (`{"report"}`) ; SendMessage et la réponse finale n'en portent qu'une ligne qui y renvoie (décision du 26/10/2026, « Le relais »). Depuis la 0.80.0, le fichier de décisions se cite par son chemin absolu dans le dossier du manager (le clone principal), que la session et ses relecteurs lisent par Read : la copie d'un worktree date du départ de sa branche, sans les décisions prises depuis ; et pour un groupe, la commande qui lit la confiance du dossier se cite par la section 3 de la procédure au lieu d'être recopiée (le brief restait ainsi sous son plafond). La session pose ses questions sensibles avant le premier ticket ; elle relance un relecteur sans nouvelles depuis 10 à 15 minutes (SendMessage, ou son axe seul) ; elle attend un spécialiste par sa notification, sans Monitor ; elle saute `/mattpocock-skills:tdd` pour un ticket sans comportement testable ; elle passe par Edit pour une modification unique, par un script au-delà de quelques remplacements liés ; pour un visuel à valider, elle produit une planche, l'intègre de façon réversible, déclare le choix et laisse la validation au retour. Au retour, une faille de sécurité corrigée après coup se renvoie à l'outil (`security`, `fixed`), sinon le tableau de bord gardait « 0 corrigé ».

**Consignes tirées de la rétro « Frise, groupes et titres » (depuis la 0.61.0).** Au découpage, un ticket qui ajoute un champ à des données persistées (un fichier ou registre gardé, un enregistrement partagé entre discussions ou sessions, une clé du store) se dit en zone sensible, nomme les chemins qui effacent ce champ et ceux qui le fusionnent ou le reconstruisent, et porte un invariant. Les consignes des revues écrivent elles-mêmes le chemin de `CODING_STANDARDS.md` quand il existe à la racine du projet (« Project judgement rules » dans le manager, « ce qui varie » du texte de délégation), ou disent qu'il n'y en a pas. Les relecteurs ne défont pas un choix déclaré par préférence, mais signalent tout cas où il produit un défaut, avec son scénario. Avant son commit, chaque critère du ticket se coche avec le test qui le couvre ; le fichier de consignes de la revue d'un ticket recopie les critères des tickets déjà faits du groupe qui touchent les mêmes fichiers. Dans un worker, la lecture d'une décision hors zone sensible se code, se déclare et la session continue ; un correctif appliqué après le compte rendu suit la procédure du ticket, et une question du compte rendu se tranche chez le manager, qui lit la branche du worker avant d'appliquer un correctif qu'il a proposé. Les règles de travail de la procédure disent ce que le garde-fou d'un worktree refuse vraiment (une boucle, un calcul, une suite de commandes où paraît le mot git), qu'un `cd` dans un sous-dossier déplace les commandes suivantes, et que `timeout` n'existe pas sur macOS.

**Consignes tirées de la rétro « Mode auto : tickets et code » (depuis la 0.77.0).** Aux étapes explore de `/to-spec` et `/to-tickets`, la question du cycle de vie d'un changement sensible couvre aussi, pour un champ persisté, la lecture ratée, l'écriture ratée, les bornes, l'effacement de ce qui est gardé, une copie forgée et chaque transition de l'objet qui porte une marque (envoi, annulation, renvoi, retour) ; les deux skills disent la même liste. Une spec ou un ticket qui écrit un appel du moteur le vérifie d'abord : le skill `plugin-authoring`, puis une question à l'explorateur plutôt qu'une hypothèse à confirmer ; une notification se spécifie avec ses surfaces, car `$.ui.notify` rend `no-surface` sans terminal, l'app desktop comprise (`docs/evenements-moteur.md` du dépôt, section « Ce que le moteur refuse »). À `/to-tickets`, l'étape explore fait lire le code de chaque ticket sensible ; l'étape des tranches dit « Logique : oui » pour un ticket qui modifie les règles communes, une référence ou un skill, et fait d'un choix de fusion d'un champ persisté une question de concurrence, jamais un choix déclaré ; l'étape de validation relit chaque critère d'un ticket sensible contre son invariant, s'il en a un, et consulte l'advisor avant la question à boutons, ou avant de déclarer la validation sautée. Le découpage des pistes d'une rétro, qui ne passe pas par `/to-tickets`, reçoit les mêmes consignes à son étape « Découpage ». Un ticket de mesure demande que chaque résultat écrit cite sa ligne de journal.

**Brief écrit par flow-board (depuis la 0.80.0).** Au lancement d'un groupe (bouton « ↗ Worker », vague du COO, mode auto), le mod écrit lui-même le brief de chaque session dans le dossier temporaire du système, un fichier par groupe et par lancement : `flow-board-brief-<mission>-<groupe>-<horodatage>.md`, un nom fait des seuls ids contrôlés et de l'heure, jamais du titre. Il a une rubrique par ligne (Background, Installation de worktree, Ton groupe, Ressource à ne pas partager, Autres sessions, Règles de travail, Décisions déjà prises, Choix déjà déclarés, Discussion principale (manager), Procédure, Ce qui varie) et porte tout ce que la demande faisait rédiger à Claude, chaque valeur relue neutralisée. La demande ne fait plus que citer son chemin et la commande qui le passe tel quel (dans le CLI, `test -s <brief> && claude --bg … "$(cat <brief> '<ajout>')"` ; dans l'app, le texte du fichier en background de `start_session` ; un brief absent au lancement ne lance pas sa session) ; Claude n'y ajoute, sous « Ce qui varie », que ce que le mod ne sait pas : sa référence et son nom du moment, la commande d'installation du worktree en clair, ce que font les autres missions, les entrées de décisions à relire, une décision toute fraîche et, pour un groupe renvoyé, ce que la session précédente a trouvé. Le dossier vient de `TMPDIR`, sinon `TEMP`, sinon `TMP` (la première posée décide), en forme, déjà là et pas lui-même un lien, cité tel que le disque le nomme (chemin résolu) ; sans lui, pas de repli sur un `/tmp` partagé. Un fichier ou un lien déjà au nom au moment du contrôle n'est pas réécrit, et le brief se relit après l'écriture (un vrai fichier, à son nom sous le dossier résolu, le texte écrit) : `$.fs.write` n'ayant pas de création exclusive, un lien posé entre le contrôle et l'écriture par un processus du même compte serait suivi, et seule la relecture le voit. Si l'un d'eux ne s'écrit pas, la demande d'avant revient telle quelle, la raison dite en mots juste avant ce que Claude rédige. Rien n'est gardé : le système nettoie son dossier temporaire (décision de la rétro « Coordinateur de parcours » : un fichier par lancement, dans le dossier temporaire du système).

**Compte rendu par son chemin (depuis la 0.80.0).** Un worker dont le compte rendu est déjà écrit dans un fichier le donne à l'outil par son chemin, `{"reportPath": "<chemin absolu>"}`, au lieu de le recoller en entier (10 à 12 ko, relus puis recollés, à la rétro « Coordinateur de parcours »). Le mod ne le lit qu'une fois, depuis le fil principal d'un worker, et seulement : un fichier ordinaire `.md` ou `.txt` (son nom donné comme son nom résolu), sous le worktree de la session (une racine `<dépôt>/.claude/worktrees/<nom>`, jamais le dossier du projet) ou sous son dossier temporaire (`CLAUDE_JOB_DIR`), une fois les deux côtés résolus (liens suivis, puis le préfixe comparé tel quel, casse comprise), sans segment caché sous ce dossier (`.git/`, `.claude/`, `.env`), de 200 000 signes au plus, pas vide, et inchangé pendant la lecture (relu après : même chemin résolu, pas un lien, même taille et même date). Un dossier temporaire autre que `CLAUDE_JOB_DIR` (une session de l'app n'en a pas) n'ouvre rien ; un lien physique garde son propre nom, et la garde par le chemin résolu ne le voit pas (un fichier du même compte). Le texte lu suit alors exactement le chemin de `report` : le fichier `.report.md` du relais, l'extrait de 8 000 signes, l'avis à la discussion principale. Un chemin refusé, ou `report` et `reportPath` envoyés ensemble, ne relaie rien du compte rendu, et la réponse dit pourquoi, sans recopier le chemin ; envoyé seul hors du fil principal d'un worker (un spécialiste, une discussion qui n'est pas un worker), le chemin n'est pas lu, et le reste de l'appel suit son cours.

**Consignes tirées de la rétro « Coordinateur de parcours » (depuis la 0.80.0).** Au découpage (`/to-tickets` et le découpage des pistes d'une rétro), un groupe dont tous les tickets sont sensibles compte 3 à 4 tickets, et un ticket sensible lourd et indépendant (sa passe « bogues » en xhigh) passe en premier, avant que le contexte du worker se remplisse. Avant de grouper, Claude vérifie le chevauchement avec les autres missions en cours : la consigne de `/to-tickets` et la demande de découpage d'une rétro donnent les fichiers qu'elles vont encore toucher. Un ticket qui s'accroche à un moment d'une procédure cite l'ordre réel de ses étapes, lu dans cette procédure ; un ticket qui écrit des données persistées pose la question de leur cycle de vie dès le découpage, pas pendant les revues ; un ticket qui remplace une règle recopiée sur plusieurs surfaces met, pour chaque copie, un fragment de son ancienne formulation dans le `termes-retires.txt` du plugin dont les contrôles la relisent. À la fin d'un cadrage (`/grill-with-docs`, `/grilling`, `/grill-me`), Claude relit ask-matt (son `SKILL.md`, qu'il ne peut pas lancer comme un skill, au chemin que flow-board trouve parmi les plugins installés et lui donne) avant de proposer un point de départ, et cite la ligne qui le justifie. `/to-spec` et `/to-tickets` tiennent en tête du `DECISIONS.md` de la mission un index court « Décisions en vigueur » (une ligne par série en vigueur : son titre, les tickets qu'elle gouverne), et un ticket recopie mot pour mot la phrase utile d'une série au lieu d'y renvoyer seulement : chaque worker relisait sinon des centaines de lignes du fichier. La passe « bogues » part avec `--max-findings all`. `snapshot.mjs --clean` cherche, fichier par fichier et fusions exclues, un commit de la branche qui amène chaque fichier de l'instantané à sa version figée : un ticket commité en plusieurs fois, ou le ticket suivant commité entre deux, ne le fait plus refuser. Les refus relevés à la rétro venaient surtout d'un correctif appliqué après le dernier instantané sans le reposer, et du travail non commité du ticket suivant, que `--clean` refuse toujours : la procédure fait donc reposer l'instantané juste avant le `git add` des correctifs d'un ticket sensible, et le ticket suivant qui touche les mêmes fichiers attend le commit.

**Consignes tirées de la rétro « Lancer un groupe en xhigh » (depuis la 0.68.0).** Ni la spec ni le découpage ne prévoient de ticket de version : la version et le CHANGELOG se posent une fois, en fin de mission, par `/project:version`, que tu lances depuis le bouton Version (un ticket de version fait par un groupe était entré en collision avec le même numéro publié par une autre discussion). Un worker de groupe ne touche ni aux versions ni aux CHANGELOG, et son compte rendu liste ce que le CHANGELOG devra dire. La consigne de `/to-spec` fait se demander, pour chaque texte écrit à un moment et lu plus tard (une demande mise dans le prompt, un brief, une valeur montrée ensuite), ce qu'il dit si la valeur a changé entre-temps : le seul défaut important d'un groupe venait de là, et aucune revue de ticket ne pouvait le voir. Dans un projet qui contient la source de flow-board (`plugins/flow-board/reference/procedure-groupe.md`), le brief cite la procédure et les fichiers de méthode du dépôt, à lire dans le worktree de la session, avant les chemins installés : une session avait suivi la procédure installée, sans la section qu'un groupe précédent venait d'ajouter. Depuis la 0.80.0, il y fait aussi lire d'abord l'« Index : concept → fichier et fonction » de ce README, puis les fichiers par fonction (aucun worker ne l'ouvrait), et dit que le mod qui tourne dans la session est sa version installée, pas celle du dépôt (un groupe avait pris son correctif pour actif). Le brief fait aussi lire chaque fichier à part, et de la spec les seules sections que cite le ticket. Dans la procédure, le fichier de consignes d'une revue se remplit d'après un gabarit, `reference/consignes-revue.md`, qui porte la consigne des relecteurs telle quelle ; la ligne `Status:` d'un ticket local dit « fait » sans hash, dans le commit du ticket ou de ses correctifs, jamais dans un commit de statut seul.

**Cycle de vie (depuis la 0.56.0).** Après un rechargement du mod (`/reload-plugins`), la première réponse de l'outil dit l'état retrouvé (« State found after a plugin reload: N tickets, M groups, phase … ; nothing to send again ») et sa description dit qu'un rechargement ne demande jamais de tout renvoyer : le 22/10, l'état était intact, mais Claude avait tout renvoyé par précaution. Le rechargement se reconnaît à un tableau de bord déjà en mémoire au démarrage des hooks, hors d'un `/clear` (que `session.start` suive bien un `/clear` reste à confirmer) ; que `session.start` passe bien à `/reload-plugins` reste à confirmer. La pause au redémarrage (0.48.0) ne change pas.

*Groupe clos, « Close now » et `closed`.* Un groupe confié s'affiche « ↗ en cours · worker » dès que l'id de sa session est relevé, et le bandeau le compte (« ↗A 0/2 ») avant même le premier signal relayé. Un groupe rendu par son worker est **clos** quand il est relu et que sa sécurité est tranchée (jugée inutile, ou chaque faille gardée corrigée ou laissée ; sans aucun avis envoyé, pour un groupe sans logique ni zone sensible depuis la 0.72.0) : la session et le worktree se ferment alors d'office. Depuis la 0.73.0, la fin d'un groupe compte aussi les tickets que le plan lui rattache après coup (un ticket trouvé en route qui attend l'un des siens), comme sa sensibilité : tant que l'un d'eux est ouvert, le groupe n'est ni dû à sa revue, ni dit relu, ni clos, ni fermé ; son compte (« ↗A 1/2 », les faits du compte rendu) le compte ; `reviewed` est refusé en le nommant, une revue déjà posée recompte une fois le groupe fini, et la réponse de l'outil dit « Not closed yet … still open, attached to it by the plan ». Un avis `security` sans `group`, quand aucun groupe n'est fini, est refusé sans rien écrire. Dans la discussion de la mission (jamais dans un worker), chaque réponse de l'outil liste, après les comptes rendus du relais, chaque groupe clos sous « Close now », avec la procédure de fermeture écrite par une fonction pure (`closing.ts`, `closingProcedure`) et ce qu'il faut renvoyer : `closed`, une entrée par groupe, `state` `closed` (avec, quand ils sont connus, `sessionId`, `branch` et `worktree`), `app` (la personne archive la session dans l'app, la ligne reste « à archiver » jusqu'au `closed`) ou `stopped` avec sa raison. Un groupe rendu pas encore clos y a une ligne « Not closed yet … lacks: … » (revue du groupe, avis de sécurité, revue conseillée pas lancée, comptes, failles non tranchées) ; une activité relayée par sa session après son compte rendu remet la fermeture (« still active »). Un état `closed` ne recule jamais : un envoi `stopped` ou `app` après lui est refusé, il survit au renvoi des groupes, au retour et à la fusion des copies (`mergeBoards` garde l'état le plus avancé, même face à une copie plus récente) ; seul l'effacement de la mission l'emporte. Une fermeture `stopped` ne se repropose pas à chaque appel : elle redevient à faire quand un appel touche le groupe (`set` d'un de ses tickets, `review`, `reviewed`, `security`, `returned`) ou sur « ↻ Relancer la fermeture », le seul bouton, montré seulement sur une fermeture arrêtée ; la ligne du groupe dit sinon « ✕ session et worktree fermés », « à archiver dans l'app », ou rien tant que rien n'a été tenté.

*« ↺ Rouvrir ».* Sur une session fermée (groupe, ou session des pistes d'une rétro) notée avec son `sessionId`, « ↺ Rouvrir » copie, par la copie du moteur, de quoi la reprendre sur sa branche gardée, jamais dans le dossier principal : pour le CLI, une commande en une ligne, `git -C '<dépôt>' show-ref --verify 'refs/heads/<branche gardée>' && git -C '<dépôt>' worktree add '<worktree noté>' '<branche gardée>' && cd '<worktree noté>' && claude --resume '<sessionId>'` (la branche vérifiée d'abord : un nom qui donnerait une HEAD détachée ne crée rien), chaque valeur citée et revérifiée à l'usage (forme du `sessionId`, de la branche, chemin `<dépôt>/.claude/worktrees/<nom>`, un nom en ASCII `[a-z0-9][a-z0-9._-]`), sans `-f`, `-B` ni `--force` (si le chemin existe ou si la branche manque, `git worktree add` échoue sans rien toucher) ; pour un chemin Windows, la même commande pour PowerShell, chaque étape dans le `if ($?) { … }` de la précédente, sans `&&`, et `Set-Location -LiteralPath` avant `claude --resume` ; le toast nomme le shell ; `claude --resume` ne reprend qu'un `sessionId` complet (un UUID), jamais un id court ni un `local_…`. Pour une session de l'app (id `local_…`), le bouton ne copie que la commande qui recrée son worktree retiré à la fermeture (`show-ref` puis `git worktree add`) ; la consigne de la désarchiver ensuite dans l'app, avec son titre, passe par le toast, qui reste 30 s : le titre de la mission, non cité, n'entre jamais dans le presse-papiers. Sans branche ni worktree sûrs, pas de bouton. Sans `sessionId` sûr, ou pour le CLI sans `sessionId` complet, pas de bouton. Le worktree recréé n'a pas les copies (`.worktreeinclude`) ni les liens que le lancement y avait mis : le toast le dit. Un toast dit ce qui est copié et rappelle qu'une session rouverte ne se referme pas d'office (l'état `closed` ne recule jamais) : il faut demander à Claude de la refermer ; sans copie possible, le toast donne le texte à recopier. Le bouton ne change aucune donnée enregistrée. Une fois la consigne de suppression des branches envoyée par « ✓ Valider le rapport », chaque fermeture dont elle visait la branche reçoit une marque (`cleanupAt`, série 24), écrite une fois le message entré dans la session (`markCleanupSent` ; un envoi refusé, `{ drop }`, ne marque rien) : « ↺ Rouvrir » disparaît pour elle, groupe comme pistes ; sa conversation reste reprenable à la main par `claude --resume <sessionId>`. Une session fermée après l'envoi, dont la branche n'était pas visée, d'une mission validée avant la 0.70.1 (la marque date de cette version : la 0.70.0 cachait le bouton d'après la phase) ou dont l'envoi a échoué garde le bouton ; un retour en arrière de phase ou un renommage de la mission ne le fait pas revenir. La marque ne recule jamais (la fusion garde la fermeture marquée) et part si la fermeture est renvoyée avec une autre branche notée ; toute marque relue, même hors forme, cache le bouton.

*Envois suivants d'un groupe.* Un groupe confié de nouveau n'est pas à fermer tant que sa nouvelle session travaille ; sa session précédente, elle, reste notée et, si elle n'est pas fermée, la réponse la liste « Close now: the previous worker of group … » pendant la nouvelle session comme après son retour (gardée dans `earlier` du lien rendu, désignée dans `closed` par `"link": <son envoi>`) ; une précédente fermée ne se refait jamais, et la nouvelle se ferme à son tour. Chaque envoi d'un groupe a son worktree : le premier `groupe-<parcours>-<id>`, les suivants `-2`, `-3`… (`seq` du lien, tiré d'un compteur du groupe qui ne recule pas, envoi annulé compris), et son titre, « Groupe A (envoi 2) · » à partir du deuxième, dans la demande de lancement (`-w` du CLI, `branch_name` de l'app) comme dans la procédure de fermeture, qui reconnaît la session de chaque envoi par son titre et ses branches : la branche gardée d'un envoi précédent, fermé ou non, ne bloque pas le suivant, et la fermeture de l'un ne vise jamais l'autre. Une session encore active après son compte rendu se débloque quand elle en redépose un, à jour. Le texte de délégation demande aussi, après le retour, de fermer le groupe s'il est clos.

*La procédure de fermeture.* Claude vérifie d'abord, une commande par étape : avant toute autre, que `git config --get core.fsmonitor` n'affiche qu'un booléen ou rien (une autre valeur est une commande que `git status` exécuterait : la fermeture s'arrête sans autre commande git et se dit ; `true` ou `false`, le démon intégré de git, sont sans danger), puis la même chose sur le worktree (`git -C '<worktree>' config`, sa config propre) dès qu'il est connu, les deux refaites après l'arrêt de la session, avant de revérifier l'arbre ; que le compte rendu de la session n'a plus de question en attente ; la branche de la session (bloc du worktree de la session dans `git worktree list --porcelain`, à défaut `worktree-groupe-<parcours>-<id>`, `groupe-<parcours>-<id>` ou `claude/groupe-<parcours>-<id>-<suffixe>` de l'app ; une branche que nomme la note de fin seulement si elle est l'une d'elles) et ses commits ; la ligne de son worktree dans `git worktree list --porcelain`, jamais un chemin deviné (un worktree encore là sans cette branche, en HEAD détachée, arrête la fermeture) ; `git branch --merged <branche de travail>` (la branche sortie dans ce dossier, lue par `git branch --show-current`), et N, le nombre de commits que le CLI dit non poussés (`git rev-list --count <branche> --not --remotes`) ; l'arbre, par `git -C <worktree> status --porcelain --untracked-files=all` (rien de modifié ni de non suivi) et `git -C <worktree> ls-files --others --ignored --exclude-standard`, dossiers jetables exclus par pathspec, dont chaque fichier doit être de la liste jetable (liens symboliques, `__pycache__/` et `*.pyc`, `.show-your-work/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `node_modules/`, `.DS_Store` ; les dossiers en entier ; les types générés d'un mod, un dossier `.claude-plugin/types/` à toute profondeur, en entier, quelle que soit leur version : ils se régénèrent ; un fichier modifié ou non suivi dessous arrête toujours la fermeture) ; les instantanés de revue `refs/worktree/flow-board/*` (un instantané identique à un commit de la branche de travail ne bloque pas) ; et que la session ne travaille pas (`claude agents --json`, son entrée retenue seulement si son `cwd` est le worktree, `"status": "idle"` ; `ListAgents` pour une session de l'app). Puis seulement il arrête la session (`claude stop <id>` ; une session de l'app, id `local_…`, s'archive par l'outil `archive_session` de l'app s'il existe, que l'app n'autorise qu'avec ton accord pour cette session : allumé par `/flow archive on`, la procédure cite cet accord donné d'avance en nommant la session et Claude archive sans redemander ; éteint, Claude te demande l'accord en une ligne, sans l'attendre pour le reste de la mission ; sans l'outil, Claude écrit le geste à la personne sans l'attendre), refait les vérifications de la fusion, de l'arbre et des instantanés, déverrouille le worktree s'il porte `locked` et que le verrou est celui de cette session, au processus disparu (il survit à `claude stop` en 2.1.312), le retire par `git worktree remove` sans option, puis, une fois le retrait constaté, lance `claude rm <id>` sans option, qui garde la conversation (`claude --resume <sessionId>`).

*Ce qui la remet à plus tard, et les valeurs vérifiées.* Une session qui travaille remet la fermeture à plus tard ; ce qui n'est pas sûr (un fichier ignoré inconnu, des commits pas fusionnés, un instantané à part) l'arrête et se dit au lieu d'être forcé ; une session déjà arrêtée ou un worktree déjà retiré comptent comme déjà faits (déjà retiré : plus de bloc dans `git worktree list --porcelain` et un dossier disparu, `test -e` en échec ; un dossier encore là sans bloc arrête la fermeture ; un worktree trouvé déjà retiré au départ ne fait pas lancer `claude rm` : la session reste dans `claude agents`, et Claude le dit). Aucune valeur n'entre dans une commande sans sa forme vérifiée : une branche vient des noms connus du groupe ou de la ligne exacte de `git worktree list` et n'a que `[A-Za-z0-9._/-]`, sans `-` en tête ; un worktree ne se retire que sous `<dossier du dépôt>/.claude/worktrees/` ; un pid n'a que des chiffres ; chaque valeur se cite pour le shell ; hors forme, la fermeture s'arrête et se dit. L'id relevé de la session, l'id du groupe et le nom attendu du worktree se vérifient dans le mod : hors forme, la procédure se réduit à « Ne ferme pas … », sans l'id du groupe ni aucun nom tiré de lui. L'id du groupe a la forme de celle de l'entrée de l'outil, lettres et chiffres ASCII, 12 au plus (depuis la 0.73.0 ; avant, seulement celle d'un nom de branche, `/` compris), et la suppression des branches à la validation du compte rendu garde, en le disant, la branche d'un groupe dont l'id est hors de cette forme. Un tel groupe, avec git comme sans, n'est jamais listé sous « Close now » ni « To archive in the app » : la réponse de l'outil le met sous « Do not close », avec le seul refus et l'arrêt à rapporter (`"state": "stopped"`), sans rien arrêter ni retirer, et le toast de « ↻ Relancer la fermeture » dit que la fermeture est refusée. Depuis la 0.73.0 : tant que sa session (ou une session précédente) travaille encore, rien ne lui est demandé, et la réponse ne promet aucune fermeture ; `closed` et `app` sont refusés pour lui, sur son lien comme sur une session précédente, seul `stopped` se note ; son id se montre échappé en JSON dans les réponses, et à la validation du compte rendu par son rang dans le plan. Les champs `sessionId`, `branch` et `worktree` de `closed` se valident à l'entrée (le `sessionId`, un UUID de `claude agents --json` ou un id `local_…` de l'app ; la branche, de la même forme, et un nom de branche, pas `refs/…`, `HEAD` ni un hash ; le worktree, chemin absolu `<dossier du dépôt>/.claude/worktrees/<nom>`, un nom en ASCII `[a-z0-9][a-z0-9._-]{0,199}`, sans apostrophe, droite ou typographique, ni caractère de contrôle, C1 et séparateurs de ligne U+2028/2029 compris) : un champ hors forme est refusé et dit dans la réponse (« closed: field refused for … »), l'état et les autres champs sont gardés.

*Textes relayés, et ce que la fermeture ne fait pas.* Un compte rendu relayé se cite entre ⟦ et ⟧, normalisé (NFKC), ses « · » et leurs sosies montrés « • », ses crochets doubles retirés, ses « ∥ » montrés « ‖ » et ses sauts de ligne « ⏎ » : il ne peut pas imiter une section de la réponse (« Close now », « Not closed yet »…) ; le fichier d'un compte rendu coupé se lit comme des données de la session. Les choix qu'un worker relaie (`decided`) passent par la même neutralisation, sans les crochets, avant le journal, la mission, le fichier des choix et le compte rendu ; ceux de la discussion de la mission restent tels quels. Un retrait (`withdrawn`) retrouve un choix relayé sous sa forme neutralisée comme sous celle qu'a écrite la session. L'en-tête « Close now » de la session des pistes ne cite l'id de session relu que s'il a une forme sûre, sinon « id de session hors forme ». La fermeture ne fusionne jamais et la branche reste jusqu'à la validation du compte rendu ; si `claude rm` refuse pour des commits non poussés, Claude ne force rien et dit que ces commits sont dans la branche de travail. Chaque compte rendu de fermeture porte la ligne « les N commits de <branche> sont dans <branche de travail> (vérifié) ; ils partiront au push de fin de mission ». Sans git, seule la session s'arrête (rien, pour un groupe à l'id hors forme). Le mod n'a pas d'API pour arrêter une session : il ne peut que le demander.

**À la validation du compte rendu (depuis la 0.70.0)**, les branches des workers fermés de la mission partent (décision de la série 18, qui remplace pour la fin de la mission le « la branche est toujours gardée » de la fermeture) : le message de « ✓ Valider le rapport » porte, dans un dépôt git et s'il y a une branche à supprimer, une consigne écrite par une fonction pure (`closing.ts`, `branchCleanupText`), et chaque fermeture visée se marque une fois le message parti (voir plus haut). Sans branche à supprimer mais avec des branches gardées, le message n'en porte que le bilan, sans aucune commande. Avec une consigne, le titre de la mission, du texte libre, n'entre pas dans le message. Elle ne vise que les branches notées (`branch`) sur une fermeture `closed` : d'un groupe, de ses envois précédents (`earlier`), de la session des pistes d'une phase (`linked`, `linkedEarlier`), chacune de forme sûre (`isSafeBranch`), citée (`shellQuote`), nommée une seule fois, et sous l'un des noms que flow-board donne à cette session (série 22) : `worktree-<worktree>`, `<worktree>` ou `claude/<worktree>-<suffixe>` (un suffixe sans « - » ni seulement des chiffres : il ne prolonge ni le nom d'un envoi suivant, ni celui d'un autre groupe ou d'une autre mission), `groupe-<id>` pour le premier envoi d'un groupe lancé avant la 0.59.0, et pour les pistes le worktree de leur envoi (tout numéro de cette mission pour la session gardée à côté du lien, qui n'a pas noté le sien) ; une branche notée sous un autre nom (`main` par erreur, une mission renommée après le lancement) est gardée, « nom de branche inattendu ». Chaque commande passe par `git -C '<dossier de la mission>'` (la racine du tableau de bord, vérifiée : absolue, sans apostrophe, guillemet « » ou sosie, chevron < > ni caractère de contrôle, un « \ » seulement dans un chemin Windows ; hors forme, rien ne se supprime et le bilan le dit), quel que soit le dossier courant de Claude, et s'écrit entre « » : aucune ne se lit comme une suite de commandes du shell.

*La consigne de suppression, commande par commande.* Claude lit une fois `git worktree list --porcelain` : une branche qu'un worktree a sortie (le dossier de la mission compris) est gardée. Pour chaque autre, la consigne écrit en entier trois commandes, lancées une à une (jamais enchaînées : le garde-fou d'une discussion dans un worktree refuse une suite de commandes git), chacune seulement si la précédente a rendu 0, chaque nom par `refs/heads/` (un tag ou un pseudo-ref du même nom ne répond pas à sa place) : `git show-ref --verify --quiet 'refs/heads/<branche>'` (code 1, absente : déjà supprimée ; un autre code, une erreur : gardée ; une commande que le garde-fou de Claude Code refuse ne se réécrit pas, ni sans `-C` : rien de plus ne se supprime, et Claude le dit), `git merge-base --is-ancestor 'refs/heads/<branche>' 'refs/heads/<branche de travail>'` (pas contenue : gardée ; la branche de travail lue par `git branch --show-current` ; `-d` seul jugerait contre l'upstream de la branche quand elle en a un), puis `git branch -d '<branche>'`, sans autre option, jamais `-D` ni de forçage : une branche que git refuse reste, et Claude dit son message. Un nom de pseudo-ref (`*_HEAD`) ou qui commence par `heads/`, `tags/` ou `remotes/` est gardé. La consigne ne nomme un groupe que par son id vérifié, jamais par son nom, du texte libre du tableau de bord. Une fermeture `stopped` ou `app`, une session pas fermée, une fermeture sans branche notée (« branche inconnue », les groupes fermés à la main avant la 0.70.0) ou à la branche hors forme gardent leur branche, sans commande, et la consigne les nomme. Claude donne la liste de ce qui est supprimé, déjà supprimé, gardé (avec la raison) et inconnu, puis la suite en une ligne. Pendant la mission, rien ne change : la fermeture garde la branche.

**Titre des workers** (depuis la 0.37.0). Tout worker (groupe, bug, pistes de la rétro) a un titre qui commence par le titre de la mission, coupé à 28 caractères (« … » au-delà), puis « > » : « Tickets lots, espace privé… > Groupe A · File d'attente ». Jusqu'à la 0.60.0, le séparateur était « › », que l'app affichait « ' » : le mod relie encore ces anciens titres à leur groupe (« › », « ' » entre deux espaces, et « â€º » d'une page de code). Dans la liste des discussions, les sessions filles d'une même discussion mère se reconnaissent ainsi. Les guillemets, `$`, `\` et accents graves du titre de la mission en sont retirés, et depuis la 0.73.0, après normalisation NFKC, ses crochets (⟦ ⟧ 〚 〛 compris), les sosies de « » (‹ › ≪ ≫ 《 》 〈 〉 ❮ ❯) et ses caractères de contrôle et invisibles, qui fermeraient sa citation dans une demande mise dans le prompt ; une session lancée avant sous un titre qui en porte n'est plus reconnue par ce titre (fermeture, rétro des sessions filles, revue d'un groupe rendu) : sa fermeture s'arrête et le dit, sans rien retirer. Le titre passe aussi dans `claude --bg -n`, cité pour le shell entre apostrophes. Le groupe de la session se lit après le dernier séparateur : un titre de mission qui nomme lui-même un groupe (« Revue du groupe P ») ne trompe pas le tableau de bord.

Confier un groupe fait passer la mission en phase Implémentation si elle n'y est pas encore (depuis la 0.35.1 ; avant, elle restait sur Tickets). `delegate` met le worker à part : ses skills n'ouvrent ni ne reprennent aucune mission, et l'outil n'y enregistre rien (il répond qu'il ne faut plus l'appeler) ; son panneau dit « ↗ Worker de la mission « … » », et son bandeau « ↗ Worker · « … » » (depuis la 0.35.1 ; avant, « Aucune mission sélectionnée »). Une session lancée dans un worktree, un worker compris, a son propre fichier de mission (sa racine est celle du worktree ; seule une discussion qui y porte une mission active du dépôt principal garde le fichier de celui-ci, voir « Données et stockage ») : `delegate` la met à part quand même, et lit le titre de la mission dans le board du dépôt principal (depuis la 0.35.0). **Avancement en direct** (depuis la 0.36.0). Le worker n'écrit pas sur la mission, mais il relaie son avancement dans un fichier à part (`~/.claude/flow-board/relais/<id de la mission>.<id de la session>.entry.json` depuis la 0.73.0, le sien seul : deux sessions qui réécrivaient un fichier commun en même temps perdaient l'une le signal de l'autre ; avant, `<id de la mission>.json`, une entrée par session) : les statuts de ses tickets d'après ses mises à jour Asana (ligne « Statut : », cochage), ses commits et ses tests, sa fin de session. Un statut changé sans mise à jour Asana peut partir par `{"set": [...]}`, un choix fait sans toi par `{"decided": [...]}` (depuis la 0.44.0), et le compte rendu final par `{"report": "…"}` (depuis la 0.54.0), ou par le chemin du fichier qui le tient, `{"reportPath": "…"}` (depuis la 0.80.0) ; le reste d'un appel de l'outil est refusé. Depuis la 0.73.0, ces champs partent au relais même envoyés avec `delegate` (ils étaient jetés sans le dire), et la réponse de l'outil dit ce que le relais n'a pas gardé, avec la raison (écriture impossible, entrée relue sans lui, fichier présent mais illisible, jamais réécrit) ; la session envoie alors aussi son compte rendu par message. Un choix relayé s'affiche aussitôt dans « ⚑ Décidé sans toi » du manager, avec « (↗ Groupe A) », et compte dans le « à relire » du bandeau. « ✓ Relu » l'enregistre relu dans la mission ; sinon, il s'y enregistre au retour du groupe (`returned`), à relire, avec une ligne au journal. Le manager relit ce fichier toutes les 5 secondes tant qu'un groupe est confié : ses tickets et le bandeau (« ↗A 1/4 ») le montrent (voir plus bas ; jusqu'à la 0.39.0, une ligne « ↗ il y a 2 min · 1/4 faits · … » et des tickets « fait ↗ à vérifier »). Une session terminée avec des tickets ouverts passe en ambre. Ces statuts restent un affichage : ils n'entrent pas dans les tickets de la mission, pour qu'un ticket fait dans une branche pas encore fusionnée ne libère pas ceux qui l'attendent. Un relais plus ancien que l'envoi du groupe (session précédente) est ignoré. Une session compte pour le groupe que nomme son `group` (« A », « Groupe A », « A · Synchro »), et pour lui seul : ni ses tickets, ni ses revues, bogues, sécurité ou choix n'entrent au retour d'un autre groupe, même pour un ticket de celui-ci qu'elle a relayé ; une session sans nom de groupe, ou dont le nom lu ne désigne aucun groupe du plan (le modèle « <id du groupe> » jamais rempli, « Group A », une faute de frappe), compte pour chaque groupe dont elle a relayé un ticket ; un groupe enregistré sous un id hors forme (avant la 0.73.0) reconnaît toujours la session déclarée sous son id exact.

**Affichage d'un groupe confié (depuis la 0.40.0).** Les tickets relayés comptent à l'affichage : le compteur du haut, celui du groupe et le bandeau les incluent. Un ticket fait dans la session prend la coche verte et le titre grisé, sans libellé ; un ticket en cours garde « ◉ en cours ↗ ». Fait ainsi, il lève ses dépendances dans son groupe, mais pas dans les autres groupes, qui travaillent sur une autre branche. La mission enregistrée, elle, n'avance qu'au retour du groupe. Le groupe confié montre tous ses tickets, ne dit plus « ↩ cette discussion », et son en-tête passe de « ↗ en cours · worker » (« ↗ worker au travail » avant la 0.56.0) à « ↗ worker terminé il y a … » (ambre) si le worker s'arrête avec des tickets ouverts, ou « ↗ worker terminé · à rendre » s'ils sont tous faits ; la ligne bleue « ↗ il y a … · 1/4 faits · … » a disparu. Tant qu'un worker travaille, l'état de l'en-tête dit « Worker au travail ».

La mission reste dans le manager, seul écrivain : à la note de fin de chaque session, Claude y vérifie le travail, puis envoie les statuts des tickets dans `set` avec `{"returned": ["<id du groupe>"]}`, qui rend le groupe au tableau de bord. Pendant ce temps, le manager peut confier d'autres groupes ou travailler sur un groupe qui ne partage rien avec ceux qui sont dehors.

**Reprise après une interruption**

Si une discussion s'arrête au milieu d'un ticket, la mission garde son état : tickets faits, ticket en cours, file lancée. Le travail commencé reste dans la copie de travail, non commité. À la reprise (« ↻ Reprendre », puis `/implement`), la consigne donnée à Claude indique l'état de chaque ticket de la file. Claude saute les tickets faits, et pour un ticket en cours, il regarde `git status` et `git diff` avant d'écrire, pour reprendre le travail déjà fait. Relancer `/implement` remet aussi les étapes à zéro.

**Étapes ticket par ticket**

Pendant `/implement`, les étapes (lire spec et ticket, boucle TDD, contrôles, revue du ticket, commit et suivi) valent pour le ticket en cours. Depuis la 0.40.0, la carte de l'Implémentation n'affiche plus l'étape en cours, ni le ticket en cours au-dessus d'elles : les groupes partent en parallèle ou dans des workers, et les vagues et les groupes disent où en est chacun. Le mod les suit toujours (consigne à Claude, reprise après interruption). Quand le ticket suivant passe en cours, elles repartent de la première. Sont comptées comme contrôles : un lint ou un typecheck au vert, et la suite de tests complète au vert ; des tests ciblés (un fichier, un filtre) restent dans la boucle TDD.

Depuis la 0.46.0, la carte de l'Implémentation montre l'ordre des choses en deux lignes grisées : « Par ticket : Lire spec et ticket › Boucle TDD › Contrôles › Revue du ticket › Commit et suivi », puis « Par groupe, ses tickets faits : Revue du groupe ∥ Revue de sécurité › Rendu du groupe » (depuis la 0.56.0, « ∥ » : la revue de sécurité part dans le même message que la revue du groupe). Le contenu de chaque étape est la consigne envoyée à Claude avec le skill (`hint` de `catalog.ts` ; `groupSteps` pour ce qui suit chaque groupe) : c'est là que vit la règle des revues ; la règle des lots (`config/rules/flow-board.md`) en résume les allègements et renvoie à ces étapes pour le reste.

**Revues sans git (depuis la 0.46.1).** Dans un projet qui n'est pas un dépôt git, aucun commit ne marque le début d'un ticket : les consignes (étapes d'`/implement`, passe « bogues », revue du groupe, revue de sécurité, brief des workers, boutons) remplacent le commit par une copie. Avant de toucher au premier fichier d'un ticket, Claude copie les fichiers qu'il va modifier dans le dossier temporaire de la session (chemin absolu), un sous-dossier par ticket qui garde le chemin dans le projet. Le point fixe d'un ticket est sa copie ; celui d'un groupe est, fichier par fichier, la plus ancienne copie parmi ses tickets. Les revues lisent la différence entre la copie et le fichier actuel (`git diff --no-index` marche hors d'un dépôt) au lieu de relire les fichiers entiers ; un fichier créé par le ticket n'a pas de copie et se lit en entier. Dans un dépôt git, les consignes ne changent pas. La mesure vient de `$.session.repo()`, prise au moment où la consigne part.

La revue d'un groupe n'est pas une phase de la feuille de route : c'est un événement de l'Implémentation. Lancer `/code-review` marque relus les groupes finis ici (depuis la 0.74.0, jamais un groupe confié à un worker, dont la revue se fait là-bas puis se rend par `reviewed`), en priorité ceux de la file lancée dans la discussion ; sans groupes, c'est le lot entier, une fois tous ses tickets faits. « Version et push » n'est proposé qu'une fois les groupes faits et relus. La consigne d'`/implement` demande à Claude la revue de chaque ticket ; avec des groupes, elle lui dit de ne lancer `/code-review` lui-même que pour la passe « bogues » d'un ticket sensible ; sans groupes, il lance aussi lui-même la revue du lot (paragraphe suivant). Un `/code-review` chargé pendant qu'un ticket est en cours dans la discussion, à son étape Contrôles ou Revue du ticket (ou, dans un worker, pendant qu'un ticket relayé l'est) est cette passe « bogues » : il ne marque aucun groupe relu (depuis la 0.46.0).

**L'Implémentation d'un lot sans groupes (depuis la 0.77.0).** Quand la mission n'a pas de groupes, la discussion de la mission fait le lot elle-même et suit la procédure d'un worker de groupe, [`reference/procedure-groupe.md`](reference/procedure-groupe.md), que la consigne d'`/implement` cite par son chemin (celui du dépôt quand le projet contient la source de flow-board, comme pour un worker) au lieu d'un texte à part : ses sections 1 à 5, 7, 8 et 9, avec leur titre. La consigne donne la correspondance de lecture (« le manager », c'est Claude, et « je » la personne ; ce que la procédure envoie au manager, il le dit à la personne, et ses questions vont en texte dans son message ; « le groupe » se lit « le lot », dont la base est le commit d'avant son premier ticket ; « au retour du groupe » se lit « au compte rendu de la mission » ; la pause vue par un worker ne le concerne pas ; un visuel à valider se montre et se demande directement), ses cinq exceptions, et rien d'autre (le relais et SendMessage, l'interdiction des questions à boutons, « ne pas lancer `/implement` », la section 10, que remplace le bloc du mode auto, et le worktree propre), et ce que la procédure attend du prompt (les commandes de ce poste, les fichiers de méthode). Le compte rendu de la section 6 est remplacé par `/flow-board:compte-rendu`, qui en reprend le contenu. Les étapes de ticket gardent leurs ids (`read`, `tdd`, `checks`, `review`, `commit`), et leurs textes renvoient aux points de la section 2. Claude lance lui-même la revue du lot une fois le dernier ticket commité et relu, et chaque ticket fait au tableau de bord (section 4 ; un `/code-review` chargé avant ne compte pour aucun passage), avec son avis de sécurité dans le même message, envoyé sans `"group"` ; le bouton « ◆ Revue » reste pour une relance à la main. Il envoie `{"complete": true}` une fois tous les tickets faits, la revue du lot faite et sa sécurité tranchée, ou le lot dispensé, et propose un groupe « durcissement » pour les constats sur du code antérieur au lot (depuis la 0.80.0, ceux de gravité moyenne ou plus, ou qui violent un invariant ; les autres vont au journal, sous « À reprendre »). La consigne fige « sans groupes » à son chargement : quand un plan de groupes s'enregistre ensuite pendant l'Implémentation, la réponse de l'outil le dit une fois (la procédure sans groupes ne vaut plus, les groupes partent dans des workers). Avec des groupes, la consigne d'`/implement` ne change pas. `procedure-groupe.test.mjs` vérifie que les sections citées existent et que les exceptions sont les cinq.

**La revue d'un lot sans groupes (depuis la 0.77.0).** Un lot fait dans la discussion de la mission, sans groupes, se relit comme un groupe, par calcul, sans rien enregistrer de plus que la date de sa dernière revue. Il est **à relire** quand tous ses tickets sont faits et qu'il n'a jamais été relu, ou qu'un ticket a fini après sa dernière revue : un ticket ajouté puis fini après la revue ouvre un nouveau passage, et la revue redevient due (pas avant sa fin ; un ticket fait sans date de fin lisible n'en ouvre pas). Il est **dispensé** quand chacun de ses tickets est dit ni sensible ni avec logique, la règle d'un groupe sans logique : ni revue du lot ni revue de sécurité, le panneau dit « ✓ relu par les revues de ses tickets » et le compte rendu suit ; un lot vide, ou dont un ticket ne dit pas l'un des deux, ne l'est jamais, et un envoi de sécurité explicite l'emporte sur la dispense. Une fois le lot relu, le compte rendu ne se propose qu'une fois sa sécurité tranchée (avis « inutile », ou failles corrigées ou laissées) : la ligne de sécurité du lot porte la suite ; sans aucun avis, elle dit « avis de sécurité attendu », et son bouton « ⛨ Revue de sécurité · spécialiste relecteur » la demande à Claude. Les faits donnés au compte rendu disent l'état du lot (« reviewed by /code-review », dispensé, ou « lot review due »). Pendant l'Implémentation, `/code-review` (hors passe « bogues ») reçoit la note de la revue d'un groupe fini, dite pour le lot : la cible exacte `/code-review high --fix <base du lot>..HEAD consignes : <chemin>` (`high` sans `--fix` quand un ticket du lot est sensible ou ne l'a pas dit ; `<base du lot>` : le commit d'avant le premier ticket du lot ; sans cible, cette plage), les interactions entre tickets, le fichier des choix déclarés et la consigne des relecteurs, pas d'arbitrage entre la spec et une consigne, puis les correctifs relus, contrôlés et commités ; et l'avis de sécurité au format d'un groupe, dans le même message, sur `git diff <base du lot>..<lancement>`, avec la règle de seconde passe sur les correctifs, envoyé sans `"group"` (il est daté, ne compte qu'après la dernière fin de ticket et la dernière revue du lot, et seul un envoi `advised` ouvre un nouveau passage ; la description du champ `security` de l'outil le dit aussi). Sans git, la note suit la méthode des copies. En mode auto, la consigne d'`/implement` sans groupes dit que flow-board relance la revue du lot et sa sécurité conseillée quand elles n'ont pas été lancées, que le compte rendu ne part qu'après le `{"complete": true}` du lot relu et tranché, ou dispensé, et qu'une faille laissée sans correctif est une question bloquante sur la phase. L'avis « tout le lot » reste pour les missions sans tickets (Relecture de branche, Revue d'une Chasse au bug ou d'un TDD). Avec des groupes, rien ne change.

**La sécurité du lot, passage par passage (depuis la 0.77.0).** L'avis de sécurité d'un lot sans groupes porte sa date (`at`), posée à chaque envoi de sécurité du lot, même un envoi qui ne change que les comptes, et au lancement de `/security-review` sans groupes. Il ne tranche la sécurité du lot que s'il est postérieur à la dernière fin de ticket et à la dernière revue du lot : un ticket ajouté puis fini après lui ouvre un nouveau passage, et un nouvel avis est dû ; un `/security-review` tapé avant le `/code-review` du lot ne compte pas, et se relance (une fois le lot relu, la ligne de sécurité du lot dit « avis de sécurité d'avant la dernière fin de ticket ou la dernière revue : celui de ce passage est attendu », avec le bouton « ⛨ Revue de sécurité · spécialiste relecteur » ; les faits du compte rendu le disent aussi, et le compte rendu attend). Seul un avis (`advised`) ouvre le nouveau passage : un autre envoi sur l'avis d'un passage précédent (des comptes ou des failles laissées arrivés en retard, une raison seule) va sur cet avis sans le dater du passage, ne tranche rien pour lui, et la réponse de l'outil le dit. Le premier avis d'un nouveau passage repart de zéro : il ne reprend ni les failles trouvées, corrigées, laissées ou proposées laissées, ni la date de lancement de l'ancien, dont les comptes vont au journal d'activité, et la réponse de l'outil le dit ; l'avis est remplacé par le nouvel avis reçu, jamais effacé ni réécrit vide. `/security-review` tapé sur un nouveau passage repart de zéro de même, en gardant son lancement. Un avis sans date, d'avant ce changement, se date par la dernière revue du lot : il compte tant qu'aucun ticket n'a fini après cette revue, et ne compte pas pour un lot jamais relu ; quand une revue du lot se charge, un avis encore sans date reçoit d'abord la date de la revue d'avant (0 sans elle), pour que la nouvelle revue ne le date pas d'un passage qu'il n'a jamais lu (seul `at` s'écrit). Quand deux discussions écrivent la même mission, la fusion garde la dernière revue du lot la plus récente des deux copies, celle de l'autre copie seulement si elle a vu chaque ticket fini de la copie gardée (fini là-bas aussi, avant elle, et pas avant la fin d'ici : un ticket rouvert puis refini ici n'est pas couvert ; sinon la copie gardée garde la sienne et le lot est à relire : au pire une revue de plus, jamais une revue manquée), et l'avis de sécurité du lot de date la plus récente, en entier : un avis daté l'emporte sur un avis sans date ; celui de l'autre copie n'est repris que si elle avait vu, avant lui, chaque ticket fini de la copie gardée, sinon la copie gardée garde le sien ; sans avis, elle reprend celui de l'autre daté 0 (rien n'est perdu, failles ouvertes comprises, mais il ne vaut pour aucun passage d'ici, et le prochain avis d'ici ouvre un nouveau passage) ; un avis sans date gardé à côté d'une revue plus récente de l'autre copie se date d'abord par la revue de sa propre copie. Un avis daté de plus d'une minute dans le futur (une horloge qui a reculé, un fichier retouché) se relit daté 0 : il ne vaut plus pour aucun passage. Une revue du lot datée de plus d'une minute dans le futur compte comme une revue à refaire : sa date est gardée, en négatif, illisible comme date de revue, rien n'est effacé ; le lot redevient à relire, sous une clé de passage qui nomme cette date (jamais `lot@0`), et la revue suivante la remplace (à la fusion, une revue lisible de l'autre copie peut aussi la remplacer, si elle a vu chaque ticket fini) ; une marque de sécurité du lot ne couvre que la revue que nomme sa clé. Avec des groupes, la sécurité des groupes ne change pas.

**Relecture de branche (depuis la 0.28.0).** `/code-review` de Claude Code lancé **sans mission en cours** dans la discussion (bouton « Relire une branche ou une PR » du lanceur, qui le met dans le prompt sans `--fix` : ajouter la cible et les options) ouvre la mission « Relecture de branche ». Pendant une mission, la même commande reste la revue du groupe.

**Avis sécurité sans groupes (depuis la 0.28.0).** Dans une mission sans groupes (Relecture de branche, et la phase Revue de Chasse au bug, TDD ou Revue de code), Claude juge si une revue de sécurité vaut la peine pour **tout le lot**, une fois la revue faite, et la lance lui-même si oui (spécialiste relecteur limité aux changements relus, depuis la 0.46.0) ; l'avis et le bouton « ⛨ Revue de sécurité » s'affichent dans la carte de la phase, puis « ⛨ sécurité relue ».

**Revues d'un groupe dans un worker (depuis la 0.38.0).** Le worker lance lui-même `/code-review --fix` une fois ses tickets commités, puis (depuis la 0.56.0 : dans le même message) la revue de sécurité s'il la juge utile (un spécialiste relecteur depuis la 0.45.1) ; il ne corrige pas les failles trouvées, qui vont dans son compte rendu. De la 0.49.0 à la 0.58.0, `/code-review --fix` tournait dans un spécialiste relecteur qui lançait la revue et écrivait ses correctifs ; depuis la 0.59.0, la session la lance elle-même par l'outil Skill (exécution dérivée, à l'effort de son niveau `high`), sans spécialiste qui l'enveloppe (il refaisait l'analyse), puis relit le diff de ses correctifs, relance les contrôles et les commite. Le chargement de ces revues dans la session part au relais : la ligne du groupe affiche « ◆ revu » et « ⛨ sécurité relue ». Quand le manager rend le groupe (`returned`), une revue relayée depuis l'envoi du groupe compte comme la sienne : le groupe est relu, et « Version et push » n'attend plus. Sans revue relayée, le groupe rendu attend sa revue, et la réponse de l'outil le dit à Claude.

**Groupe rendu sans revue (depuis la 0.39.0).** Un groupe fait par un worker garde cette trace (`delegated`) une fois rendu. S'il revient sans revue, son bouton n'est plus « ◆ Revue du groupe » qui met `/code-review --fix` dans le prompt : dans le manager, sa branche est déjà fusionnée, et `/code-review` sans cible n'aurait rien à lire tout en marquant le groupe relu. Le bouton devient « ◆ Revue du groupe · worker ». Il met dans le prompt une demande à Claude : retrouver la session (ListAgents), lui faire remettre sa branche au niveau de la branche principale, lancer `/code-review --fix` sur les seuls commits du groupe (sans `--fix` pour un groupe dont un ticket touche une zone sensible ou ne le dit pas, depuis la 0.73.0, comme depuis son bouton dans la discussion), elle-même par l'outil Skill (depuis la 0.59.0, sans spécialiste qui l'enveloppe), relire ses correctifs et les commiter, puis la revue de sécurité par un spécialiste relecteur si utile. Au compte rendu, Claude fusionne et envoie `{"reviewed": ["<id>"]}`, qui marque le groupe relu, et `security`. Depuis la 0.43.0, quand le compte rendu final de la session dit que la revue du groupe a tourné mais que le relais ne l'a pas vue, Claude envoie `reviewed` avec `returned`, dans le même appel : le groupe revient relu, sans bouton de revue. Les groupes faits dans la discussion gardent le bouton `/code-review --fix`. Un groupe rendu avant la 0.39.0 retrouve cette trace dans le journal de la mission (« ↩ Groupe A rendu par son worker »), depuis la 0.42.0. À confirmer à l'usage : que `/code-review` sans cible relise bien, dans un worktree, la branche face à sa base (le brief dit sinon de lui donner le nom de la branche) ; et, depuis la 0.49.0, qu'un spécialiste general-purpose puisse lancer `/code-review --fix` par l'outil Skill et y appliquer ses correctifs.

**Revues allégées (depuis la 0.56.0).** Un groupe dont chaque ticket est envoyé avec `"sensitive": false` et `"logic": false` (des documents, une icône) n'a ni revue du groupe ni revue de sécurité (depuis la 0.72.0 ; avant, seul un groupe d'un seul ticket était dispensé, et de la seule revue du groupe) : les revues de ses tickets suffisent, la ligne du groupe fini affiche « ✓ revu par ses tickets » (« par son ticket » pour un seul) au lieu du bouton, et sa sécurité est réputée tranchée tant qu'aucun avis de sécurité n'a été envoyé pour lui : il se clôt et se ferme d'office sans rien attendre de plus. Un envoi de sécurité explicite l'emporte, et un seul ticket avec de la logique, en zone sensible, ou qui ne dit pas l'un des deux, rend dues la revue du groupe et l'avis de sécurité. La revue d'un ticket se fait dans un seul relecteur pour les deux axes (l'axe Spec seul pour un ticket sensible, depuis la 0.78.0), quelle que soit la taille du diff (depuis la 0.59.0 ; avant, sous 100 lignes seulement) : il lit `CODING_STANDARDS.md` en plus du `CLAUDE.md` et rend ses Mineurs en un compte. La revue de sécurité, en lecture seule, part dans le même message que la revue du groupe ; depuis la 0.59.0, elle ne relit pas le diff des correctifs de la revue du groupe : depuis la 0.78.0, elle tourne une seule fois. Les constats sur du code antérieur au lot sont classés à part par les relecteurs, non corrigés, et proposés en fin de lot comme un groupe « durcissement » : depuis la 0.80.0, seuls ceux de gravité moyenne ou plus, ou qui violent un invariant ; les autres vont au journal, sous « À reprendre ». Depuis la 0.78.0, un groupe d'un seul ticket n'a pas de revue du groupe, rattachés compris et quels que soient ses drapeaux : sa ligne affiche « ✓ revu par son ticket », sans bouton de revue, et l'auto n'en envoie pas ; avec de la logique, en zone sensible ou muet, son avis de sécurité reste dû, jugé par sa session (ou la discussion, pour un groupe fait là) à la fin de son ticket.

**Constats triés (depuis la 0.57.0).** La consigne des relecteurs leur fait étiqueter chaque constat « Important », « Nit » (mineur) ou « Pre-existing » (antérieur au lot). Seuls les importants sont corrigés ; les remarques mineures (style, nommage, nettoyage sans effet sur le comportement) sont listées sans être corrigées, pour qu'elles ne coûtent ni commit ni nouveau tour de revue. Pour un défaut, le relecteur nomme sa classe, pour que toutes ses occurrences soient corrigées.

La revue de sécurité ne bloque jamais la livraison et n'est jamais la suite proposée. Avec `/code-review --fix` d'un groupe (avant la 0.56.0 : une fois passé), Claude juge si une revue de sécurité en vaut la peine (depuis la 0.79.0, seulement si les changements font franchir quelque chose à la limite du compte, une zone de la liste de sa méthode : secrets et jetons (masquage compris), dépendances et code tiers lancé, publication, réseau ou export public, droits des fichiers et accès ; un fichier sous `~/.claude` écrit par une autre session du compte n'est pas une entrée hostile, et ni une suppression de données ni la concurrence seule n'en font partie ; l'accès comprend l'authentification et les règles d'accès d'une application, et le réseau vaut dans les deux sens ; de la 0.78.0 à la 0.79.0, la liste comptait aussi une commande ou un chemin construit à partir d'une entrée, la suppression de données, et les données personnelles ou le contenu des messages sur disque), le dit en une ligne et l'envoie au tableau de bord. Depuis la 0.46.0 (décision de Mathis du 15/10/2026), il la lance alors lui-même, partout : un spécialiste relecteur (general-purpose, Opus, lecture seule ; effort `xhigh` jusqu’à la 0.57.1, `high` ou `xhigh` selon la méthode de la 0.58.0 à la 0.78.0, `high` depuis) limité à `git diff <base du groupe>..HEAD`, qui ne corrige rien ; avant, la personne lançait `/security-review`, qui relit toute la branche face à la branche par défaut. Claude dit ce que le spécialiste a trouvé, ne corrige qu'avec ton accord et crée une tâche pour chaque faille laissée ouverte. Un `/security-review` tapé à la main reste reconnu. Le compte rendu donne, groupe par groupe, ce qu'il en est. Depuis la 0.80.0, la revue se désactive par projet (bascule « ⛨ Sécurité ») : Claude juge et envoie l'avis quand même, sans lancer de relecteur (un worker l'apprend dans la réponse de l'outil `flow` à son avis) ; un groupe ou un lot conseillé sans revue compte alors comme tranché, l'auto ne lance rien, et le compte rendu écrit « revue de sécurité désactivée pour ce projet ; le groupe touchait : <zone> ». L'avis reçu revue désactivée porte une marque (`offAt`) ; un groupe fermé pour la première fois alors qu'elle l'est le garde dans sa fermeture (`securityOff`) et garde cette ligne quel que soit le réglage ensuite ; réactivée, la revue redevient due pour tout autre groupe conseillé sans revue. Un réglage illisible vaut « activée ». Le bouton « ⛨ Revue de sécurité » reste pour une revue ponctuelle, comptée comme toute revue.

**Méthode de la revue de sécurité (depuis la 0.58.0).** Le relecteur suit une méthode fixe, `reference/revue-securite.md` dans le dossier du mod, dont le chemin va dans son prompt à côté de son fichier de consignes ; les consignes du mod (avis après la revue d'un groupe ou du lot, brief des workers, bouton « ⛨ Revue de sécurité ») la citent sans la recopier. Elle reprend celle de `/security-review` de Claude Code (catégories, gravité, exclusions, une recherche puis une vérification par faille, seuil de confiance 8/10, rapport `fichier:ligne` avec scénario et recommandation) et garde la plage exacte du groupe, le contexte du projet, les choix déclarés et la lecture seule. Les dépendances et les données sensibles sur disque restent cherchées ; l'absence de durcissement, les failles notées 5 à 7 et celles de gravité basse vont dans une liste « à surveiller ». Depuis la 0.78.0, elle ne se conseille que si les changements touchent une zone de la liste de sa section 1 (depuis la 0.79.0, ce qui franchit la limite du compte, sa frontière de confiance : la liste ci-dessus ; son précédent 13 ne tient plus un fichier sous `~/.claude` écrit par une autre session du compte pour une entrée hostile), et tourne en `high`, en une seule passe ; le rapport dit en tête la zone qui a décidé la revue. Depuis la 0.80.0, le relecteur cherche et vérifie lui-même, sans lancer d'agent, dans son propre contexte : une revue coûtait 2 à 5 agents, chacun avec environ 70k de contexte de départ. Depuis la 0.79.0, la revue d'un groupe ou d'un lot (le fichier de consignes `reference/consignes-revue.md`, et la consigne du mod pour toute revue qui juge un avis de sécurité : un groupe fini, un lot, une mission sans groupes) signale comme un bogue une valeur relue qui entre dans une commande shell ou un chemin, sauf là où un contrôle du projet la vérifie déjà (ici `check.sh`, pour les hooks de flow-board). Le critère `high` ou `xhigh` (l'enjeu, la taille) ne sert plus qu'à la passe « bogues » d'un ticket sensible. Le scénario d'une faille se décrit par la garde, le trou, la source et l'effet, jamais par une chaîne d'attaque prête à l'emploi. Chaque faille gardée arrive numérotée (F1, F2…) avec un correctif prêt : une réponse comme « corrige F1 et F3 » suffit pour que Claude les applique, les teste et les commite. `findings`, envoyé à l'outil flow, ne compte que les failles gardées, pas la liste « à surveiller ».

**Comptes de sécurité relus.** Les comptes `findings`, `fixed` et `dismissed` sont des entiers de 0 à 10 000, sans arrondi. Un envoi dont un compte sort de là (texte, `null`, négatif, décimal, trop grand) est refusé en entier, dans la discussion de la mission comme dans un worker (rien n'est relayé), et la réponse le dit (« security: refused, counts out of range »). Relu du tableau de bord ou venu du relais, un compte hors forme ne tranche jamais la sécurité du groupe : il reste ouvert, n'est pas à fermer, et la ligne « Not closed yet » nomme les comptes illisibles et demande de les renvoyer ; au relais, un `findings` ou un `fixed` hors forme n'est plus lu 0, il est gardé illisible (-1), et un `dismissed` hors forme est écarté. Un compte illisible ne s'affiche jamais comme un nombre (le panneau dit « comptes relus hors forme (—) »). Le renvoi demandé répare l'avis : un `fixed` illisible non renvoyé vaut 0, un `dismissed` illisible non renvoyé ne compte plus. Rien n'est réécrit à la relecture. Au relais, un avis de sécurité remplace le précédent (ses comptes peuvent redescendre), sauf un compte de sécurité gardé illisible dans l'entrée de la session (ou un avis gardé qui n'est pas un objet), jamais écrasé : l'avis qui l'enverrait est refusé, la revue du même appel part seule, et la réponse dit de donner les comptes de sécurité dans le compte rendu ; un avis qui ne l'envoie pas le laisse tel quel, et un avis gardé qui n'est pas un objet fait refuser tout nouvel avis. Un envoi `security` qui nomme un groupe inconnu, ou dont `group` n'est pas un id (un booléen, `null`, une liste), est refusé : la réponse nomme l'id et la liste des groupes, et aucun groupe n'est touché (une fermeture arrêtée n'en redevient pas à faire) ; sans `group`, l'avis va comme avant au dernier groupe fini, ou au lot sans groupes. Les autres valeurs relues qui décident qu'un groupe est relu ou à fermer sont bornées de même : une date de revue hors forme ne compte pas comme une revue ; une date de relance infinie ou hors forme ne relance pas une fermeture arrêtée ; une fermeture ou un lien relus d'un autre type ne sont ni à faire ni une exception ; au relais, une date de compte rendu, de dernier signal ou de fin hors forme laisse la session comptée active, une entrée sans début ni tickets lisibles est écartée, et un choix, un retrait ou un compte rendu sans texte aussi. Une date relue abîmée s'écrit « date inconnue » au lieu de faire tomber la réponse.

**Relecture du fond et de la forme (depuis la 0.67.0).** Les axes Standards et Spec relisent les règles de code et la conformité au ticket, pas un document pour celui qui le lira. Au découpage, la consigne de `/to-tickets` fait porter à un ticket dont le livrable est un document lu par d'autres (un rapport, un guide, un document pour des utilisateurs) une ligne « Lecteur : <qui> », à côté de « Zone sensible » et « Logique » ; ni un ticket de code ni un document interne de travail ne la portent, et rien de nouveau n'est envoyé au tableau de bord. Cette ligne déclenche, quel que soit l'effort, une relecture par un spécialiste Opus en effort `high`, en lecture seule, qui suit une méthode fixe, `reference/relecture-fond-forme.md` dans le dossier du mod, dont le chemin va dans son prompt à côté de son fichier de consignes : le lecteur visé, le fond, la forme, des constats numérotés (R1, R2…) avec une correction proposée, les mineurs en un compte. Elle tourne partout où tourne la revue du ticket : dans un worker de groupe (procédure, étape « Revue du ticket ») comme dans le manager (consigne d'`/implement`). Un ticket ancien sans cette ligne mais dont le livrable est clairement un document pour d'autres est relu aussi : Claude nomme le lecteur et le déclare dans `decided`.

**Procédure d'un worker de groupe (depuis la 0.61.0).** Ce que fait un worker de groupe (questions sensibles d'abord, chaque ticket avec ses revues et son commit, règles de travail, revue du groupe, revue de sécurité, compte rendu au relais, consigne des relecteurs, cas sans git) est écrit une fois dans `reference/procedure-groupe.md`, dans le dossier du mod. Le texte de délégation la cite par son chemin installé (dans le dépôt de flow-board, depuis la 0.68.0, par celui du dépôt d'abord) au lieu de la recopier (il passe d'environ 15 000 à 8 000 signes, que le manager ne recopie plus dans le prompt de la session) et ne garde que ce qui varie : la mission, le groupe et ses tickets, la référence du manager, les commandes du poste, le fichier de méthode de sécurité, celui de la relecture du fond et de la forme (depuis la 0.67.0), le fichier des choix déjà déclarés, si le dossier est un dépôt git, et, dans le dépôt de flow-board, le renvoi à l'index de ce README et la version installée du mod (depuis la 0.80.0). Depuis la 0.80.0, la procédure a aussi une section 11, adressée au manager et non au worker : l'effort des workers et ce qui suit leur compte rendu, auxquels la règle des lots renvoie. La demande « Revue du groupe · worker » cite aussi la consigne des relecteurs par ce chemin.

## Livraison et synchronisation

**Livraison**
- Avant la pull request, la phase **Version et push** combine `/project:version` puis `/project:push`. Lancer directement `/project:push` ouvre la phase à l'étape push, avec les étapes de version marquées sautées.
- **Version et push côte à côte** (depuis la 0.61.0) : une fois le compte rendu validé, la carte propose `/project:version` et `/project:push`, au choix. Le mod compare la branche à la branche distante (la branche suivie, sinon `origin/main`) : quand chaque plugin ou paquet changé a déjà une nouvelle version dans son manifeste (`.claude-plugin/plugin.json`, `package.json`, `pyproject.toml`, `Cargo.toml` ; dans un dépôt de marketplace, ceux de ses seuls plugins publiés), `/project:push` passe en tête et la carte dit « version déjà posée ». Depuis la 0.65.0, `/project:version` reste toujours proposé à côté de `/project:push`, y compris pendant la phase, version faite et push à venir.
- **Bouton Version et aperçu de la version** (depuis la 0.68.0) : la version d'une mission se pose toujours en fin de mission par `/project:version`, jamais par un ticket ni un worker. La carte met Version en tête tant qu'une partie changée n'a pas sa nouvelle version, Push en tête quand la version est déjà posée ou que le projet n'a pas de fichier de version (« pas de fichier de version dans le projet »), l'autre toujours à côté ; tant que la mesure n'a pas tourné, Version reste en tête. Sous les deux boutons, un aperçu grisé, une ligne par plugin ou paquet changé : « flow-board 0.67.0 → 0.68.0 · mineure : 3 feat, 2 fix » d'après les commits faits depuis son dernier changement de version (hors fusions), selon les règles de `/project:version` (un commit cassant donne une majeure, sous la 1.0.0 une mineure ; `feat` une mineure ; `fix` et le reste un correctif ; une pré-version comme `1.3.1-mathis.2` avance son dernier nombre), ou « déjà posée : 0.65.1 → 0.67.0 » ; trois lignes au plus, puis « + N autres ». Ce n'est qu'un aperçu : `/project:version` garde la décision et demande confirmation.
- **Clore la mission à côté du push et de la PR** (depuis la 0.65.0) : pendant la phase « Version et push », la carte propose « ✓ Clore la mission » à côté de `/project:push` puis de `/project:pr`, et plus seulement une fois la phase close.
- Un push fait avant l'implémentation (les documents du découpage, par exemple) enjambe la phase Implémentation, qui passe sautée. Depuis la 0.35.1, elle n'est pas perdue : lancer `/implement` ou confier un groupe à un worker y ramène la même mission, et la livraison redevient à faire.
- La phase **Pull request** suit `/project:pr`. `/mattpocock-skills:pr` reste disponible pour rédiger le corps.
- **Sans GitHub**, la phase « Pull request » disparaît de l'affichage et n'est plus proposée : le mod lit l'adresse de `origin`, et seule une adresse github.com garde la PR. Après « Version et push », la mission peut alors être close. La mission stockée garde la phase, qui revient si le projet passe sur GitHub.
- Les commandes `/project:*` n'ouvrent jamais de mission à elles seules. Elles sont réservées à la personne : le mod les met dans le prompt sans les lancer, sauf sur le clic « ▶ Livrer » chez le COO (ci-dessous).
- **« ▶ Livrer » chez le COO.** Une fois un rapport validé, la carte de livraison du COO (« Ce qui t'attend ») dit ce qui partira : les commits de la branche absents du distant, rangés par mission d'après la fenêtre de temps de chaque mission (« hors mission » sinon), et recommande d'attendre quand une mission pas finie a déjà des groupes fusionnés. Une mission dont la discussion livre déjà elle-même (phase de livraison en cours) n'y est pas, ni une mission déjà livrée sur ce rapport validé (la dernière livraison finie le garde). Rien ne part sans le clic « ▶ Livrer », qui ne vaut que pour ce que la carte montrait (une mission validée ou des commits arrivés depuis : « relis la carte ») ; les gestes de la livraison passent un à un, deux clics ne se croisent jamais. Le mod lance alors lui-même, dans la discussion du COO, `/project:version`, puis `/project:push`, puis `/project:pr --auto` (projet sur GitHub, hors de sa branche par défaut, où `/project:pr` refuse), puis un message qui demande à Claude les étapes que le `CLAUDE.md` du projet ajoute après une livraison, en laissant à la personne ce que le projet lui réserve. Claude rend l'issue de chaque étape par le champ `delivery` de l'outil flow (seul dans son appel) ; le mod ne lance l'étape suivante que sur une réussite, siège relu avant chaque étape. Une étape échouée arrête la suite : la carte dit laquelle et propose « ↻ Réessayer » (cette étape seule, jamais une étape réussie) ou « ✕ Abandonner » (le push déjà fait, les missions se closent avec ce qui est parti et ne se relivrent pas). Sans fichier de coordination lisible, rien n'est proposé ni lancé. Une seule livraison à la fois : l'état de la livraison est gardé par le poste du COO (`$.store`, `coo-delivery:<projet>`), et une livraison pas finie en refuse une autre. Après un rechargement, la carte dit où elle en était : « ▶ Reprendre à <étape> » lance l'étape suivante, et une étape lancée dont l'issue n'est pas revenue (rechargement, tour coupé) se fait vérifier par Claude (« ↻ Demander l'issue », refusé pendant un tour de Claude), jamais relancer : vérifiée, l'étape suivante attend « ▶ Reprendre ». Livrée, chaque mission ouverte dans une discussion reçoit une clôture avec le résultat (version, push, adresse de la PR) : son mod marque ses phases de livraison faites, note le résultat au journal, puis la clôt et l'archive ; une mission ouverte nulle part est archivée par le COO, et le résultat va dans la feuille de route (« Jalons »).

**Synchronisation avant de modifier le code**
- Le mod lance `git fetch` en arrière-plan : au démarrage, au début d'une phase qui touche au code, puis toutes les 5 minutes.
- Il compte ensuite les commits de `origin/main` et de la branche distante suivie qui manquent à la branche locale. Les modifications locales ne comptent pas, `/project:sync` s'en charge.
- **Là où l'on code** (depuis la 0.59.1) : l'encadré mesure le worktree de la session quand elle travaille dans un autre worktree du dépôt que la racine du projet (par exemple `.claude/worktrees/dev`, le dossier principal restant sur `main` pour un service), et le nomme (« À jour avec origin/main dans .claude/worktrees/dev ») ; sinon, la racine du projet. Le refus, lui, se juge sur le worktree du fichier modifié (`git rev-parse --show-toplevel` depuis son dossier) : un worktree dont la branche contient déjà `origin/main` ne déclenche ni avis ni refus, même si le dossier principal est en retard.
- Si le distant a avancé :
  - un encadré l'indique, avec la commande à lancer ; son bouton dit ce qu'il prépare, sans la commande (depuis la 0.70.0) : « Préparer la synchro » (`/project:sync`), « Préparer la synchro avec la base » (`/project:sync base`) ou « Préparer l'avance rapide » (`git pull --ff-only`) ;
  - la première modification de code est refusée **une fois par avancée du distant**, pour que Claude demande le sync. Une seconde tentative passe.
- La commande proposée :
  - `/project:sync` d'abord, si la branche distante a bougé ;
  - `/project:sync base` ensuite, seulement si main est encore en avance après ce premier sync ;
  - sur main, sans aucun commit local en avance sur `origin/main` : une mise à jour en avance rapide, `git pull --ff-only` dans ce dossier, au lieu de `/project:sync`. Le bouton met dans le prompt une demande à Claude ; le refus lui dit de la proposer et d'attendre l'accord. Quand l'avance ne se mesure pas, `/project:sync` reste proposé.
- Sans dépôt git, sans distant ou sans réseau, rien n'est demandé. Sans distant `origin`, l'encadré « À jour » n'est pas affiché non plus : il n'y a rien à quoi se comparer.
- flow-board fonctionne avec n'importe quel hébergeur git (GitHub, GitLab, Bitbucket, serveur maison) : seule la phase « Pull request » est propre à GitHub.

## Plusieurs discussions sur un même projet

- Le stockage est partagé : chaque discussion fusionne sa copie au lieu de l'écraser. Pour chaque mission, la version la plus récente l'emporte, et une suppression est mémorisée : sa trace efface les copies de la mission qui ne sont pas plus récentes qu'elle. Depuis la 0.74.0, seule une trace bien formée (un id, une vraie date) et datée au plus une minute dans le futur s'applique ; une trace plus loin dans le futur (fichier retouché, horloge reculée) ou mal formée tombe à la lecture, sans rien effacer. La mission active dans une discussion y garde sa copie, sauf si une autre discussion l'a reprise (sa copie, active, à son nom et plus récente) : la discussion n'a alors plus de mission active, et la réponse suivante de l'outil le dit. Une copie en pause n'a pas d'auteur lisible (la pause efface le nom de la discussion qui le tenait) : celle d'une discussion qui l'a reprise, y a fait un envoi puis a fini avant la relecture suivante ne l'emporte pas, et cet envoi peut se perdre (question ouverte au porteur). Un état de fermeture « closed » ne recule dans aucun sens de la fusion. L'état du mode auto (depuis la 0.74.0) se fusionne date par date, chacune la plus récente des deux copies : une copie en retard ne le rallume jamais. Une lecture ratée du fichier commun (fichier présent mais illisible, ou qui n'est pas le board du projet ; un fichier absent ne compte pas) éteint le mode auto de chaque mission de la copie de la discussion, au chargement, à la sauvegarde (avant d'écraser le fichier) et à la relecture des 5 secondes, raison « lecture de la mission ratée ». Les questions bloquantes s'unissent une par une, retraits tracés, les marques d'envoi du mode auto marque par marque, traces de « ↻ Renvoyer » comprises (pour une mission dont l'auto est allumé au nom de la discussion, la date du clic gardée là, même mise en pause par l'ouverture d'une autre mission, seules les traces qu'elle a écrites retirent : voir « Traces de retrait écrites ici »), et, pour une mission qui a été en auto, les choix « décidé sans toi » aussi (voir « Mode auto » et « Décidé sans toi »). La délégation d'un worker (`delegate`) n'est jamais écrite dans le fichier commun : elle est gardée à part, par session.
- Les missions enregistrées par les autres discussions sont relus toutes les 5 secondes.
- Chaque discussion a sa propre mission en cours. Celle d'une autre discussion apparaît « ⇆ autre discussion », et « Reprendre ici » la récupère.
- **Une mission n'est suivie que par une discussion à la fois.** « Reprendre ici » la retire à l'autre discussion, qui n'enregistre plus rien sur elle. Pour faire avancer plusieurs groupes en même temps, passer par « ⇉ … en parallèle » : des workers qui travaillent pour le manager sans écrire sur la mission. Un ticket qu'une autre discussion a laissé « en cours » s'affiche « ⇆ autre discussion ».
- Une discussion sans mission active n'enregistre rien tant que le projet a une mission en pause ou suivie ailleurs : l'outil et `/flow` nomment ces missions, pour reprendre le bon.
- À la fin d'une discussion, sa mission passe en pause, sauf après un `/clear`, et son mode auto s'éteint. Au chargement, une mission abandonnée depuis plus de 30 minutes passe aussi en pause, même tenue par une autre discussion encore ouverte (un skill ne la reprend d'office que dans la discussion où elle est née, et jamais tant qu'une autre la tient : la mise en pause est la seule écriture qu'une autre discussion y fait, avec la coupure de l'auto sur une lecture ratée) ; son mode auto reste allumé, mais n'envoie que de la discussion qui l'a allumé.

## Effort d'un manager qui fait le travail d'un worker

**Selon le rôle et la phase (depuis la 0.80.0).** Le mod impose l'effort de chaque requête du fil principal (hook `turn.step`, fonction `leadEffort` de `hooks/effort.ts`), recalculé à chaque requête : la discussion qui tient le siège du COO part en medium (high et low ramenés à medium ; xhigh et max laissés, un choix délibéré de la personne) ; le manager d'une mission à groupes part en medium de la fin du découpage (la phase « Tickets » faite) au début du compte rendu, phase d'implémentation comprise, qu'une compaction ait eu lieu ou non (high ramené à medium ; xhigh et max laissés) ; le manager en cadrage (grilling et ses variantes, spec, découpage), en compte rendu, en rétrospective ou dans toute autre phase part en high au moins ; un lot sans groupes et un diagnostic gardent la règle des workers (paragraphe suivant) ; un worker de groupe ne l'est que pendant un ticket sensible (paragraphe « Un worker pendant un ticket sensible ») ; un spécialiste et une discussion sans mission active ne sont jamais touchés. Le bandeau dit l'effort imposé et sa raison quand la règle change l'effort de la discussion, relevé sur sa propre piste du registre des agents, qui garde l'effort d'origine (« effort : medium, règle du COO », « effort : medium, suivi des groupes », « effort : high, cadrage », « effort : high, compte rendu », « effort : high, rétrospective », « effort : high, règle du manager ») ; rien tant que cet effort est inconnu (avant la première requête), ni quand il est déjà celui de la règle, ni sur xhigh ou max laissés. Le lot et le diagnostic se disent toujours (paragraphe suivant).

Quand un manager fait lui-même le travail d'un worker, le mod applique à chaque requête de son fil principal (hook `turn.step`) l'effort que la règle de ce worker donnerait, par la même fonction que le brief d'un worker (`hooks/effort.ts`) : la règle d'un worker de groupe pour un lot sans groupes, un départ `/implement` ou `/tdd` (medium ; high pendant un ticket « doing » de la mission sensible ou qui ne le dit pas, depuis la 0.80.0, quand tout ticket ouvert sensible comptait avant, ou si les tickets ouverts touchent plusieurs modules de code, comptés par `codeModuleOf` avec la même définition que le brief), celle d'un worker de diagnostic pour `/diagnosing-bugs` (high au moins, sans jamais baisser un effort plus haut ; une deuxième tentative en xhigh passe par un worker de diagnostic, « 🐞 Bug · worker »), le détour en cours comptant d'abord ; un lot dont tous les tickets sont faits n'est plus le travail d'un worker. Les choix de conception qui restent, que la règle d'un worker de groupe compte aussi, ne se calculent pas : le mod les compte absents. Le bandeau le dit (« effort du lot : medium, règle des workers »). Hors de ce travail, l'effort suit la phase (paragraphe précédent) : une mission partie en medium revient en high au moins pour son compte rendu, et un effort plus haut de la discussion reste tel quel. Le mod n'y monte jamais en xhigh : un lot qui relève de xhigh (une tâche de jugement) passe par un worker de groupe, où xhigh se propose par la question de la règle des workers, jamais en auto. Les spécialistes gardent l'effort que leur donne leur lanceur.

**Un worker pendant un ticket sensible (depuis la 0.80.0).** Le mod d'un worker de groupe (`delegate`) passe chaque requête de son fil principal en high au moins (un effort plus haut de la session reste) pendant qu'un ticket sensible du groupe est en cours, puis la laisse à l'effort de la session, celui de son lancement (`workerEffortRule` de `register.tsx`, `workerTicketEffort` de `hooks/effort.ts`). Le ticket en cours est celui que la propre entrée du relais du worker dit « doing » (le worker le passe « en cours » en le commençant : point 2 de la section 2 de la procédure) ; sa sensibilité se lit dans la mission, sur le board d'ici ou, depuis un worktree, sur celui du dépôt principal (`workerMission`), lue seulement quand un ticket est en cours. Un ticket muet, absent de la mission, une mission ou un relais illisible comptent comme sensibles. Un ticket que le worker reclasse sensible en route (point 2 de la section 2 de la procédure) n'y compte qu'une fois renvoyé par le manager avec `"sensitive": true` : l'outil ne relaie pas ce drapeau d'un worker. Aucun ticket en cours, ou seulement des tickets dits non sensibles : rien d'imposé. Les revues gardent leur effort (elles tournent dans des spécialistes). Le bandeau du worker le dit quand la règle change l'effort de la session : « effort : high, ticket sensible <id> en cours », « effort : high, ticket <id> en cours, sensibilité inconnue », « effort : high, ticket en cours illisible » (un id hors forme n'est pas écrit). Avant, un seul ticket sensible faisait lancer tout le groupe en high : dans les groupes ainsi lancés, 39 % des tickets ne l'étaient pas. L'effort réécrit ne se lit ni dans `CLAUDE_EFFORT` ni dans les hooks (`docs/evenements-moteur.md`, essai 2) : seul le bandeau le montre.

## Le COO

Le COO (directeur des opérations) est une discussion qui suit toutes les missions du projet sur ce poste : elle dit à la personne ce qui l'attend et propose la suite, sans coder, sans cadrer et sans porter de mission. Le travail d'une mission reste à son manager.

**L'ouvrir.** `/flow-board:coo`, ou « ◆ COO » au bandeau d'accueil d'une discussion sans mission. Le skill porte les consignes du rôle (sources citées, « à confirmer » sinon, ton) et, à son chargement, le mod prend le siège. Le COO s'ouvre à la racine du dossier principal du dépôt (le fichier des missions, donc le siège, y est celui du projet) : une discussion dans un worktree ou dans un sous-dossier, une discussion qui porte une mission et un worker ne le prennent pas.

**Le siège.** Il n'y a qu'un COO à la fois par projet et par poste. Le siège est un champ du fichier des missions (`coo` : qui l'a pris, quand, vu vivant pour la dernière fois, libéré quand) ; chaque discussion le fusionne, la prise la plus récente l'emportant, et un rafraîchissement ou une libération ne touche jamais la prise d'une autre discussion.

- Un siège libre, libéré ou abandonné (titulaire muet depuis plus de 30 minutes) se prend à l'ouverture. Tenu par une autre discussion vivante, il ne se prend pas seul : le bandeau dit « siège tenu par une autre discussion » et propose « ↻ Reprendre ici », qui relance `/flow-board:coo` (ses consignes reviennent à Claude) et reprend le siège à son chargement. Une prise se relit deux fois, à une seconde et demie d'écart : deux prises presque simultanées finissent sur la plus récente, et l'autre discussion l'apprend avant de se dire COO.
- Le titulaire se montre à chaque écriture du fichier des missions et au moins toutes les 5 minutes. Quand une écriture croisée a recouvert sa prise d'une prise plus ancienne, il la réécrit aussitôt, à sa relecture suivante. Un siège daté au-delà d'une minute dans le futur est ramené à maintenant ; un siège mal formé ne s'applique pas ; ni l'un ni l'autre n'est effacé.
- Chaque écriture du siège relit d'abord le fichier : une discussion qui a perdu le siège ne le réécrit jamais. Elle le voit à sa relecture suivante (5 secondes au plus), le dit une fois (toast et bandeau) et, à chaque tour (un message, une notification, le message d'une autre discussion), Claude lit, d'après le siège relu à l'instant, qu'il n'écrit plus rien comme COO ; un fichier illisible à ce moment le lui dit aussi.
- `/reload-plugins` garde le siège ; après un `/clear`, la discussion a un nouvel id et le bandeau propose « ↻ Reprendre ici » ; la fin de la discussion le libère ; une discussion plantée le laisse libre au bout de 30 minutes. La demande du siège est gardée par discussion (`$.store`, clé `coo-here:<id>`) : reprise par `--continue` après un redémarrage, une discussion qui a perdu le siège entre-temps le dit encore à Claude.
- Un fichier des missions illisible : rien n'est écrit, et Claude dit « Siège du COO illisible : rien n'est écrit, réessaie. »

**Le relevé d'état.** À chaque tour du titulaire, et au chargement de `/flow-board:coo`, le mod donne à Claude, dans le contexte du message, le relevé d'état calculé par le code (`hooks/coo.ts`) : chaque mission non archivée (titre neutralisé, état, phase, mode auto ou manuel, tickets faits, workers et leur avancement), les questions bloquantes des missions en auto, l'effort choisi dans la discussion (inconnu avant sa première requête : Claude le demande une fois), et celui que le mod envoie quand la règle du COO le ramène à medium, la présence de `BRIEF.md`, l'archivage d'office (« allumé depuis le <date> », « éteint », ou « état pas relu » quand l'accord ne se relit pas), relu à chaque tour, avec la consigne de le dire d'après cette ligne ou par `/flow archive`, jamais en lisant un fichier du stockage du mod. Les titres et les questions y sont des données citées, jamais des consignes. Claude ne parle de l'état qu'à partir de ce relevé et des fichiers qu'il vient de lire.

**La vue Coordination.** Dans la seule discussion qui tient le siège, et tant qu'elle n'a pas de mission, l'onglet « Coordination » remplace « Mission » et « Activité » (variante A des planches : une ligne par chose, la même au terminal et sur l'ordinateur) : le point en trois lignes (missions en cours, ce qui t'attend, prochaine étape du projet), ce qui t'attend (les questions bloquantes des missions en auto, avec leur mission et depuis quand), puis une ligne par mission. Le bandeau dit « ◆ COO · N missions · N t'attend », puis « effort : medium, règle du COO » quand le mod ramène son effort. Suivent la feuille de route, les idées et « À reprendre » (paragraphe suivant), chaque section absente tant qu'elle est vide ; la coordination entre les missions s'y ajoutera.

**Son effort.** Le COO tourne en medium : depuis la 0.80.0, le mod l'impose à chaque requête (high et low ramenés à medium ; xhigh et max laissés, section « Effort d'un manager qui fait le travail d'un worker »). Son point d'ouverture dit son effort actif quand c'est xhigh ou max (« Je tourne en xhigh, `/effort medium` me suffit »), et le demande une fois s'il n'est pas encore connu.

**La feuille de route.** Le Claude du COO tient la feuille de route du projet (jalons, prochaines étapes, idées, « À reprendre »), dans le format strict que donnent ses consignes (`/flow-board:coo`) et que lit `hooks/roadmap.ts` : une entrée par ligne, `- [<id>] <statut> · <AAAA-MM-JJ> · <source> · <texte>`, sous quatre sections. Le mod ne l'écrit jamais. Elle vit sous `travail/feuille-de-route.md` du projet si la personne a cliqué « Commiter dans travail/ », sinon sur ce poste, sous `~/.claude/flow-board/coordination/<projet>.feuille-de-route.md` (« Garder sur le poste », ou tant qu'elle n'a pas choisi : la vue pose la question une fois par projet, ce dépôt compris, car un dépôt public publierait ses idées). Changer d'endroit demande au Claude du COO de recopier le fichier existant à son nouvel endroit, ou, si un fichier y est déjà, de lui ajouter seulement les entrées qui lui manquent, l'ancien restant en place ; sans choix ici, une feuille de route déjà commitée dans le projet est signalée. Le titulaire du siège la relit toutes les 5 secondes et à chaque tour, et garde chaque entrée vue avec sa dernière version, jamais effacée : une entrée qui disparaît (fichier vidé ou supprimé, ligne retirée) paraît en alerte dans la vue, avec « ↺ Remettre », qui demande au Claude du COO de la remettre exactement (sa section et sa dernière version, en chaîne JSON), et dans le relevé, qui la donne entière. Le mod garde aussi chaque texte déjà vu de chaque entrée : quand le Claude du COO change le texte d'une entrée sous le même id, l'ancien texte qui n'est plus nulle part dans le fichier (sous aucun id : un texte passé sous un autre id n'alerte pas comme texte changé ; un id retiré reste une entrée disparue) paraît en alerte de la même façon, une fois par texte, par sa version vue le plus récemment, avec l'id qui la portait et sa section (sauf quand l'alerte d'une entrée disparue en montre une version au moins aussi récente), et « ↺ Remettre » demande de le remettre comme une nouvelle entrée sous un id neuf, sauf s'il est déjà revenu dans le fichier ; aucun bouton ne le laisse partir : on le retire en écartant l'entrée remise. Un fichier hors format n'est pas montré : la vue le dit, avec « ↺ Réparer », et le relevé donne les dernières versions connues ; une lecture hors format ne change rien de ce qui est gardé, une lecture ratée (le fichier, ou ce que le mod en garde) ne montre ni ne propose rien. Les demandes des boutons ne partent que quand Claude est au repos ; elles ne demandent un commit que si la feuille de route vit dans le projet. La vue montre le jalon en cours, les prochaines étapes, les idées (« Plus tard », « Écarter », qui demande d'abord la raison) et ce qui est à reprendre ; le point prend sa prochaine étape. Une discussion qui ne tient pas le siège ne garde rien.

**Commits hors mission sur un groupe en cours (depuis la 0.80.0).** Le COO relit la branche de travail du projet (sa `HEAD`) à chaque relecture de son fichier, quand elle a bougé : ses commits de première lignée depuis le départ du plus ancien groupe chez un worker, avec leurs fichiers (une fusion y compte pour un commit, avec les fichiers qu'elle apporte face à son premier parent : un commit hors mission arrivé par une fusion se voit), et les commits de la branche du worker de chaque groupe (sous un des noms que flow-board donne à sa session, `worktree-<worktree>`, `<worktree>` ou `claude/<worktree>-<suffixe>`, reconnue dans la liste des branches que git rend, puis relue par son sha) : une fusion en avance rapide met ses commits dans la première lignée, et ils ne comptent jamais pour leur propre groupe. Pour chaque groupe chez un worker (d'une mission même close ou archivée : son worker écrit encore), il compte ceux faits depuis son départ qui touchent un de ses fichiers (les `files` du groupe et de ses tickets, comparés comme les retenues : barres obliques, « ./ » et casse, sans les documents communs que les retenues ignorent aussi, `README.md`, `DECISIONS.md`, `carte-du-code.md`, `codemap.md`, `ETAT_DU_PROJET.md` et `GLOSSARY.md` ; un dossier couvre ce qu'il contient ; un renommage compte pour ses deux chemins), hors des commits des managers, reconnus à leur ligne « ⎇ Commit » ou « ⤞ Merge » du journal d'une mission (de 2 minutes avant à 2 secondes après, une ligne pour un commit, le plus proche ; une ligne « Commit : <sujet> » n'excuse qu'un commit de ce sujet, sauf un message composé par le shell, et une ligne « Merge » qu'une fusion). La vue Coordination, sous les retenues, et le relevé de son Claude disent alors « ⚠ main a reçu N commit(s) hors mission sur des fichiers du groupe <g> de « <mission> » », sans notification (rétro « Coordinateur de parcours » : un diagnostic et une étude hors mission avaient commité sur des fichiers de groupes en cours, et la coordination ne l'avait appris que par message). Aucune valeur du fichier des missions n'entre dans les commandes git, hors la date de départ (un entier) : les chemins des groupes ne servent qu'à comparer ; 2 000 commits au plus sont relus, et une commande ratée ne montre rien. Un commit hors mission qu'un worker a fusionné dans sa branche (en y fusionnant `main`) ne compte plus pour ce groupe-là : son worker l'a déjà intégré.

**Le fichier de coordination.** Le COO parle aux managers par un fichier du poste (`~/.claude/flow-board/coordination/<projet>.json`), qu'il écrit seul : son Claude y pose ses consignes par le champ `coordinate` de l'outil `flow`, et le mod les écrit, une entrée par consigne, après avoir relu le siège (une discussion qui l'a perdu n'écrit rien) et le fichier (une écriture qui perdrait une autre entrée est refusée). Le mod de chaque manager le relit toutes les 5 secondes et applique lui-même, une fois, ce qui vise sa mission (une demande de clôture ; un forçage, lui, compte dans chaque calcul des retenues tant que son entrée existe, et ne compte plus quand le fichier ne se lit pas). Une entrée ne part qu'avec la suppression de sa mission (seule exception : la marque « recopiée » d'une chose À reprendre, attachée à sa déclaration, part quand plus aucune boîte ne la porte) : « Supprimer », depuis n'importe quelle discussion, pose déjà la trace d'effacement de la mission ; tous les lecteurs ignorent aussitôt ses entrées, et le COO les retire à sa relecture suivante, une fois la mission absente du fichier des missions. Un fichier qui ne se lit plus (écriture coupée, retouche à la main) n'est jamais réécrit : le COO en garde une copie à côté, le dit dans la vue et à son Claude, et ne repart d'un fichier neuf que sur le clic « Repartir d'un fichier neuf » ; chez un manager, rien ne s'applique, et l'auto ne lance rien, le bandeau disant « fichier de coordination illisible », jusqu'à la relecture suivante réussie. Ses consignes : la clôture et l'archivage d'une mission livrée, le plan des vagues du projet validé (voir plus bas), et le forçage d'une retenue entre missions (« ⇥ Forcer » de la section « Retenues entre missions » de la vue, qui montre qui attend qui et signale deux groupes en cours de deux missions sur un même fichier, lancés presque ensemble). Une mission en pause ou close est archivée tout de suite par le mod du COO ; une mission ouverte reçoit l'entrée, son mod la close puis l'archive (une fois : l'id de l'entrée est noté dans son stockage) ; passée en pause entre-temps (mise de côté, discussion fermée), le mod du COO l'archive lui-même. Une demande faite, sa mission archivée d'après le fichier des missions relu, est notée faite dans le fichier (`doneAt`) : elle ne referme jamais une mission reprise ensuite. Quand le Claude d'un manager doit agir, le COO le réveille par un texte fixe, « Le COO a mis ta mission à jour : relis le tableau de bord. », envoyé à la discussion qui porte la mission, relue dans le fichier des missions au moment de l'envoi (id contrôlé) : par le mod, sinon (le moteur refuse cet envoi quand la discussion du COO tourne en « auto mode » de Claude Code) par le `SendMessage` de son Claude, à la référence du manager relue à côté du relais.

**À reprendre.** Rien de ce qu'une mission met de côté ne se perd. Un manager le déclare au moment où il le note, par le champ `setAside` de l'outil `flow` (le texte tel qu'écrit et sa source) : la déclaration va dans la boîte de sa discussion. Le relevé du COO la donne à recopier dans la section « À reprendre » de la feuille de route, sa source commençant par « boîte <id> » ; dès que le mod du COO l'y voit, sous cette source et avec son texte tel quel (une copie résumée ou fusionnée ne compte pas), il la note recopiée, et le mod de la discussion déclarante la retire de sa boîte, et seulement elle. À la clôture d'une mission, le relevé demande au COO de relever les sections « Pistes » des comptes rendus de ses workers et ses pistes de rétro non choisies, de montrer à la personne ce qui n'avait pas été déclaré, puis de noter la mission relevée ; à sa première ouverture dans un projet, une seule fois, il relève le journal d'`ETAT_DU_PROJET.md` et les comptes rendus, et les montre à la personne avant d'écrire. Une chose « À reprendre » ne sort de la liste que par la décision de la personne : la vue Coordination lui donne « Lancer », « Rattacher », « Plus tard » et « Écarter », qui demandent au Claude du COO de changer son statut (jamais de la retirer). « Supprimer » une mission dont le COO n'a pas encore relevé les comptes rendus le dit : « N comptes rendus pas encore relevés par le COO ».

**Une mission qui t'attend.** Une mission en manuel, ou en auto mis en pause, dont le tour est fini et dont la suite te demande (une question, une validation par boutons, l'étape suivante proposée, le rapport à valider) le dit au COO : sa vue montre « La mission <titre> t'attend : <quoi>, depuis <heure> » dans « Ce qui t'attend », le bandeau la compte, et le COO la notifie une fois par attente, « Mission <titre> : elle t'attend ». En auto actif, la mission envoie elle-même sa suite : seules ses questions bloquantes attendent, et elle garde seule leur notification. Une mission dont l'auto se met en pause (lot bloqué, quota atteint en fin de tour, lecture ratée) t'attend aussi. Le signal s'efface dès que le travail reprend (le tour suivant, la reprise de la mission, l'allumage de l'auto), à la pause, à la clôture, à l'archivage et avec la mission ; une mission en pause paraît « en pause, à reprendre ».

**Questions et gestes chez le COO.** Les questions bloquantes de toutes les missions en auto paraissent dans « Ce qui t'attend » du COO, avec leur mission et depuis quand (aussi quand l'auto s'est mis en pause parce qu'elles bloquent tout), et la personne y répond sans aller dans la discussion du manager. Le manager peut donner à une question son geste (champ `gesture` d'une question de `waiting` : `spend`, une dépense ; `external`, une action externe ; `flaw`, une faille à laisser sans correctif, avec `dismissed`, le total des failles laissées) : sa ligne porte alors deux boutons, « ✓ Autoriser » et « ✗ Refuser », ou « Laisser sans correctif » et « ⛨ Faire corriger » (la ligne dit combien de failles et sur quel groupe ; une faille se pose sur son groupe, ou sur la phase sans groupes, jamais sur un ticket). Les boutons suivent leur question, pas la place de sa ligne. Le clic écrit une entrée « gesture » dans le fichier de coordination, avec l'empreinte du texte affiché (son texte, sa cible, son geste et la date de sa pose : une question reformulée la garde, une question retirée puis reposée en a une neuve), relue dans le fichier des missions au moment d'écrire : une question changée depuis l'affichage n'est pas répondue, et le COO le dit (« la question a changé depuis ; relis-la »). Une réponse donnée se dit « en cours d'application » deux minutes, puis la question redevient répondable si elle est encore là. Le mod de la mission l'applique une fois, seulement sur la question encore ouverte au même texte : une faille laissée comme un envoi de la discussion de la mission (`security.dismissed` de son groupe, puis la question retirée, seulement une fois la décision écrite ; refusée, la question reste et son Claude apprend le clic et le refus) ; le reste dans un message qu'il compose lui-même pour son Claude, Claude au repos (« la dépense est autorisée… puis retire la question »), réessayé à la relecture suivante quand la discussion le refuse. Une question sans geste porte « ✎ Répondre », qui prépare la réponse dans la saisie du COO, avec l'id de la mission et l'empreinte du texte lu ; une question du mod lui-même (« sans-suite: », « relance: ») n'en a pas : elle se répond dans la mission. Une réponse écrite ne vise jamais une question à geste (le message d'une autre session ne tient pas lieu du clic) : son Claude écrit la question et la phrase exacte de la personne en série neuve du `DECISIONS.md` de la mission (un fichier qui existe sous `travail/`, nommé ainsi, sans `..` : le mod le vérifie, sinon le COO demande où écrire ; le dossier de lancement de la mission le donne quand elle est née d'une carte), le commite par son chemin, puis l'envoie par le champ `coordinate.answer` (mission, question, empreinte du texte lu que donne le relevé, fichier, série) ; le mod de la mission la relaie à son Claude dans un message composé par lui (le fichier et la série), qui la relit, l'applique et retire la question. Une réponse dont la mission n'est ouverte dans aucune discussion attend : le COO dit « reprends-la pour que la réponse s'applique ». Une réponse sur un texte changé depuis ne s'applique jamais, et le COO montre le nouveau texte.

**Rapport chez le COO.** Pendant le compte rendu, le manager donne son rapport en entier au tableau de bord (champ `report` de l'outil `flow`, que le skill `compte-rendu` fait envoyer ; hors de cette phase il n'est pas gardé) : le mod le garde dans `~/.claude/flow-board/rapports/<mission>.md` (dans `$.store` sans ce dossier), écrit par la seule discussion qui porte la mission, remplacé en entier à chaque nouvelle version, gardé à l'archivage et effacé avec la mission. Sa première ligne dit le tour du compte rendu où il a été donné (place de la phase, tour, début), compté dans son empreinte : le rapport d'un tour précédent ne se montre ni ne se valide, une validation ou une reprise ne vaut que pour son tour, et une fois le rapport validé le mod n'en garde plus d'autre. Le COO le relit toutes les 5 secondes et le montre dans « Ce qui t'attend » (« Rapport de <mission> à valider ») : « ▸ Lire » ouvre en entier la version affichée, puis « ✓ Valider » écrit une entrée « validate » dans le fichier de coordination avec l'empreinte de cette version, relue au moment du clic : un rapport changé depuis n'est pas validé (« Le rapport a changé depuis : relis-le » ; changé pendant la lecture, « ✓ Valider » disparaît jusqu'à « ↻ Relire », qui ouvre la nouvelle version). Une validation se dit « en cours d'application » deux minutes, pendant lesquelles un second clic n'écrit rien ; passé ce délai, une validation que la mission n'a pas appliquée laisse revenir le bouton. Une mission ouverte dans aucune discussion n'a pas de « ✓ Valider » : « Rapport prêt, mission en pause : reprends-la pour valider ». Le mod de la mission applique la validation une fois, seulement si son rapport gardé a la même empreinte et que le compte rendu est en cours : c'est alors la validation de « ✓ Valider le rapport » (phase close, choix relus, message de validation à son Claude avec le nettoyage des branches). « ✎ À reprendre » met dans la saisie du COO le début de la demande ; son Claude écrit la phrase de la personne en série neuve du `DECISIONS.md` de la mission (mêmes règles de chemin qu'une réponse écrite), puis l'envoie par `coordinate.redo`, notée pour le tour du compte rendu en cours ; le mod de la mission la relaie à son Claude, qui réécrit le rapport. Le relevé d'une mission close lit aussi ce rapport (« Trouvé », « Bloqué par moi »).

**Décisions opposées entre missions.** Le relevé du COO liste, par le code, les décisions nouvelles de chaque mission non archivée depuis son relevé précédent : les séries de son `DECISIONS.md` (celui de son dossier de lancement, pour une mission née d'une carte) et ses choix « décidé sans toi », chacun avec sa source ; ce qui est déjà vu est gardé par le poste du COO (`$.store`, `coo-decisions-seen:<projet>`), et un état illisible fait tout relever de nouveau. Son Claude juge si deux portent sur le même sujet et s'opposent (c'est du texte), puis l'écrit : `coordinate.contradiction` (les deux décisions, source et texte mot pour mot, et le sujet), une entrée que le mod de la mission qui a décidé en second applique une fois en posant une question bloquante sur sa phase en cours, au texte composé par lui (titres et textes neutralisés), seule cette partie attendant ; `coordinate.compatible`, une ligne « A et B décident tous deux sur X, compatibles » ; `coordinate.decisionsSeen`, le relevé jugé : seules les décisions que ce relevé a montrées à Claude se marquent vues (30 au plus par relevé ; le reste et ce qui arrive entre-temps reviennent au suivant). Le relevé donne aussi, pour comparer, le `DECISIONS.md` de chaque mission et ses choix déjà vus, et l'empreinte de la question d'une opposition pour sa réponse écrite. La vue Coordination montre les oppositions en cours (l'autre mission archivée depuis : la question reste posée) ; si c'est la mission qui portait la question qui est archivée avant la réponse, le COO écrit l'opposition inverse et la question passe à l'autre, encore en cours. La question va toujours à une mission en cours : celle qui a décidé en second, sinon l'autre ; une décision d'une mission archivée vaut toujours, et deux missions closes ou archivées n'ont rien à demander (le COO montre les deux décisions). Le Claude de la mission ne pose, ne change ni ne retire cette question : la réponse passe par le `DECISIONS.md` comme une réponse écrite (dans les deux, et « remplacée le … » sur la décision non gardée, jamais avant la réponse), et le mod la retire lui-même une fois la réponse relayée entrée. « decisionsSeen » ne marque rien tant qu'une opposition ou un sujet compatible n'a pas été écrit depuis le dernier relevé.

**La rétro d'une mission livrée.** Quand la livraison lancée chez le COO finit, ou s'arrête par « ✕ Abandonner » après le push, son mod pose dans « Lancements » une carte « Rétrospective · <mission> » par mission livrée qui n'a pas encore sa rétro (`hooks/retro-coo.ts`) : départ `/retro`, auto, effort high, recommandée quand le rapport gardé a une section « Ce qui s'est mal passé » qui n'est pas « Rien. » ou que la mission a eu des workers, facultative sinon ; « ✕ Pas de rétro » la retire. Seul le mod pose une telle carte : le champ `card` de Claude refuse le départ `retro`. Le clic la lance comme une autre carte, et son enregistrement de lancement porte l'id de la mission close (`of`), que le rattachement garde dans `Run.launch.of` (posé une fois, jamais changé, effacé avec la mission). À la consommation du lancement, le mod de la rétro donne à son Claude la mission close, le titre à prendre et les transcripts de ses discussions (celle où elle est née, la dernière qui l'a portée, ses workers) trouvés sous le dossier des projets de Claude, jamais un chemin construit d'une valeur relue ; ceux qui manquent sont nommés, avec les fichiers de relais de ses workers pour les retrouver, et la rétro dit ce qu'elle n'a pas trouvé. Le dossier de la rétro porte une marque tirée de l'id de la mission, pour que deux rétros n'aient pas le même ; une carte de rétro ne part jamais pour faire de la place à une autre carte. Ses pistes se cochent chez le COO, une case par piste (une piste prise ailleurs s'affiche sans case), avec « Tout cocher » et « ✂ Découper la sélection », qui écrit une entrée `pick` (les cochées, les autres, l'empreinte des pistes montrées). Une sélection envoyée ne se recoche pas tant qu'elle tient (appliquée, ou en attente sur les mêmes pistes encore à faire) : ses pistes quittent les cases, et seule une piste ajoutée depuis se coche ; une sélection rejetée par la rétro (pistes changées) rend ses pistes à cocher. Le mod de la rétro l'applique une fois, sur les mêmes pistes seulement, une piste marquée prise ailleurs entre-temps n'étant ni découpée ni recopiée : il écrit d'abord les non cochées dans sa boîte « À reprendre » et les écarte, puis envoie (en auto) ou met dans la saisie (en manuel) la demande d'écrire la sélection dans le `DECISIONS.md` de la rétro et de découper les seules cochées. Les cases cochées vivent en mémoire du COO : un rechargement les décoche, rien ne part sans clic. Une rétro lancée à la main (`/retro`) reste telle quelle.

**Pistes prises ailleurs.** Quand une rétro présente ses pistes, le relevé du COO les donne avec ce que les autres missions non archivées ont déjà choisi (pistes en cours ou faites d'une rétro) ou mis en tickets ; son Claude juge sur le texte. Un recoupement net devient une marque (champ `coordinate.taken` : la mission de la rétro, la piste, la mission et le ticket qui la portent), une entrée « taken » du fichier de coordination ; un recoupement partiel est une question à la personne ; un apport nouveau part dans « À reprendre », au statut « à décider », son texte nommant la mission et le ticket (la personne décide où il va). Seule une piste encore « à faire » de la rétro (sa dernière phase de rétro commencée) se marque. Une marque garde le libellé que le COO a jugé : elle suit sa piste quand la rétro renumérote, et part quand la mission de la rétro ou celle qui a pris la piste est supprimée. Le mod de la rétro montre la piste « déjà prise par « <mission> », ticket N » et la retire de ce qu'on peut sélectionner et découper (le fichier relu juste avant « ✂ Découper ») ; un appel de l'outil qui la ferait avancer (« en cours », « faite »), sous son id ou sous son libellé, est refusé en entier, tickets et fin de phase compris, même quand l'appel reprend la rétro (`resume`) ; en auto, il le déclare une fois dans « Décidé sans toi ». Une marque qui ne se lit pas, ou un fichier de coordination illisible, laisse la piste découpable, et la vue le dit.

**Le plan des vagues du projet.** Le COO range les départs des groupes de toutes les missions non archivées en vagues du projet, calculées par le code (`hooks/plan-projet.ts`) : la première vague garde ce qui est déjà parti ; chaque vague prend, parmi les groupes (ou les lots sans groupes) dont les attentes de leur mission sont passées, d'abord ceux qui ont le moins de conflits, chacun seulement s'il n'a ni fichier ni ressource en commun avec ceux déjà pris (mêmes exclusions que les retenues) ; la composition des groupes ne change jamais ; une mission dont le dernier groupe part dans une vague se livre après elle. Sa vue le montre vague par vague (« mission 1 : A, B · mission 2 : D, E »), avec les livraisons. Le plan se recalcule seulement à la fin du découpage d'une mission, à la clôture d'un groupe et à une livraison, et n'est reproposé que s'il change l'ordre validé (« Plan du projet proposé », bouton « ✓ Valider le plan ») ; pour une mission en auto, il s'écrit d'office. Validé, il devient l'ordre de départ, dans le fichier de coordination : une entrée « plan » par attente (le groupe retenu, et le groupe d'une autre mission qu'il attend), que le plan suivant validé remplace en entier. Chez chaque manager, la carte « Ensuite », le bouton de l'étape suivante et l'auto ne proposent ou n'envoient que les groupes que le plan fait partir maintenant ; la ligne d'un groupe qui attend dit « ⏸ attend groupe D de « <mission> » (plan du projet) », la carte et le bandeau aussi. L'attente se lève d'elle-même, même sans COO ouvert, quand le groupe attendu est clos (ses tickets faits, aucun worker en vol ni rendu sans être clos), retiré du plan de sa mission, ou sa mission close, archivée ou supprimée ; un envoi annulé ne la lève pas. « ⇥ Forcer » (dans la mission ou chez le COO) fait partir un groupe malgré le plan, pour la seule paire nommée ; les retenues de fichiers restent en dessous. Un plan illisible (le fichier de coordination présent mais illisible, ou qu'on ne peut lire dans un projet qui a un COO, ou une entrée de plan hors forme qui vise la mission) ne lance rien, même à la main : « Plan du projet illisible : aucun départ, retenues gardées », que disent aussi la carte « Ensuite » et, en auto, le bandeau (« ⚡ Auto en pause : plan du projet illisible ») ; tout repart à la relecture réussie. Chez le COO, une entrée de plan hors forme fait reproposer le plan, que « ✓ Valider le plan » réécrit (d'office quand l'entrée nomme une mission en auto). Un « ⇥ Forcer (plan) » lève une attente du plan, un « ⇥ Forcer » une retenue de fichier : chacun la sienne.

**Lancer la prochaine vague, découper en sachant.** La vue du COO montre la prochaine vague du projet : pour chaque mission ouverte dans une discussion, les groupes que sa carte « Ensuite » propose maintenant, plan du projet et retenues compris (« « mission 1 » : A, B · « mission 2 » : D, E »), avec « ⇉ Lancer la vague » ; deux groupes de missions différentes qui touchent un même fichier n'y sont jamais ensemble (le premier proposé garde sa place), et un plan illisible chez le COO (fichier de coordination, ou entrée de plan hors forme d'une mission) n'y fait rien proposer. Le clic écrit une entrée « wave » par mission dans le fichier de coordination, avec les seuls groupes affichés ; tant qu'une vague se lance, la vue dit « lancement en cours » et n'a plus de bouton. Le mod de chaque manager lance lui-même ses groupes de la vague, une seule fois (l'entrée notée appliquée avant l'envoi), comme « ↗ Worker » mais en envoyant le texte lui-même (`$.prompt.submit`, comme l'auto ; l'app Desktop y refusant `start_session`, la même demande revient alors dans la saisie, comme pour une vague de l'auto), à l'effort de la règle des workers : seulement la discussion au repos (sinon il réessaie à chaque relecture, dans les 10 minutes du clic), et seulement les groupes que sa carte « Ensuite » propose toujours (plan, retenues et groupes déjà partis de la mission relus juste avant) ; un plan illisible chez lui n'y fait rien partir, sans toast. Un groupe que le plan ou une retenue ne fait plus partir, le COO le dit aussitôt (« groupe A de « M » retenu par le plan ou un fichier en commun : il partira à son tour ») ; un groupe dont la mission n'est plus ouverte, ou dont la discussion est restée occupée 10 minutes, ne part pas, et le COO le dit (« groupe A de « M » n'est pas parti : reprends la mission pour le lancer ») ; un groupe compte parti s'il a été lancé depuis le clic. Les groupes restent lançables un par un dans chaque mission. Au découpage (`/to-tickets`), la consigne donne au manager les fichiers que les autres missions non archivées vont encore toucher (calculés à ce moment, jamais gardés ; 40 au plus, neutralisés), une information pour faire des groupes qui les croisent le moins possible : le découpage reste le sien. À l'entrée d'une phase de code (Implémentation, TDD, Chasse au bug, Prototype), la consigne du skill nomme de même les fichiers des groupes que les autres missions du projet ont confiés à un worker et pas encore rendus, avec leur groupe et leur mission (lus sur le tableau de bord relu toutes les 5 s, plus, dans un worktree dont le tableau de bord n'est pas celui du dépôt principal, le fichier des missions de ce dépôt relu sans écriture ; jamais gardés ; chaque fichier une fois, 40 au plus, le reste compté, neutralisés), et dit de travailler dans un worktree quand le travail les recoupe (dans le worktree où elle tourne déjà, le cas échéant), puis de prévenir la discussion de cette mission avant de fusionner ; sans tel groupe, rien n'est ajouté. Depuis un worktree, un fichier du dépôt principal illisible au chargement d'un skill se dit dans sa consigne.

**Aucune mission chez le COO.** Dans la discussion qui tient le siège, l'outil `flow` refuse d'ouvrir ou de reprendre une mission, « ↻ Reprendre » du panneau ne reprend rien, et un skill de départ n'en ouvre pas : Claude lit, avec le texte du skill, qu'il ne le suit pas ici et en propose une carte de lancement.

**Lancer une mission.** Quand la personne parle d'une chose nouvelle, le Claude du COO propose une carte de lancement (champ `card` de l'outil `flow`, seul dans son appel) : le titre, l'idée de la feuille de route qu'elle lance, le point de départ et la ligne d'`ask-matt` qui le justifie (le relevé donne le chemin du skill `ask-matt` du plugin `mattpocock-skills` installé, lu dans le registre des plugins de Claude Code), les autres départs possibles, le mode et l'effort recommandés avec leur raison, et le dossier `travail/<sujet>/` (lettres, chiffres et tirets seulement ; jamais xhigh en auto). La vue Coordination la montre dans « Lancements », avec les boutons ▶ « Lancer en auto » et ▶ « Lancer en manuel » (le mode recommandé en tête, jamais en auto une carte en xhigh) et un bouton par autre départ ; une idée « à lancer » de la feuille de route a son bouton ▶ « Lancer », qui demande la carte au Claude du COO. Le clic écrit dans le stockage du mod un enregistrement de lancement (`$.store`, clé `coo-launch:<id>`, id tiré au hasard) et met dans le prompt du COO le texte qui lance la nouvelle discussion (`start_session` dans l'app, `claude --bg` au premier plan dans le terminal, à l'effort de la carte ; pour un manager en xhigh dans l'app, le COO demande d'abord `/effort xhigh`, puis rappelle de redescendre) : son premier message est le skill de départ, le sujet, et une ligne qui ne porte que l'id du lancement. À son premier appel de l'outil `flow` (champ `launch`), la nouvelle discussion contrôle l'id, relit le fichier des missions et l'enregistrement, le prend à son nom, le relit une seconde et demie plus tard, rattache sa mission à la carte (champ `launch` de la mission), l'écrit, relit le fichier des missions (deux missions passées en même temps : celle ouverte la première l'emporte, l'autre marque son rattachement perdu et reste en manuel), puis efface l'enregistrement ; une lecture ratée en route ne consomme rien, et Claude renvoie l'id. Ce premier message ouvre toujours une mission neuve : il ne reprend pas une mission en pause qui aurait la même phase. Une carte ne lance qu'une mission : pendant le lancement elle dit « lancement en cours » et n'a plus de bouton ; elle se dit lancée dès qu'une mission du fichier la porte (ou porte son dossier), et revient 11 minutes après le clic sans mission (les 10 minutes du lancement, et une de grâce) ; un second lancement d'un dossier dont un lancement est encore valable est refusé. L'enregistrement ne sert qu'une fois, dans les 10 minutes, à une seule mission ouverte après le clic : un id inconnu, périmé, déjà porté par une mission ou pris par une autre discussion laisse la mission en manuel, sans rattachement, et Claude le dit (« Accord de lancement périmé : la mission est en manuel, allume l'auto ici si tu veux »). Le COO et la mission tournent dans le même mode (app ou terminal), le stockage du mod différant de l'un à l'autre. Une carte lancée dont l'idée n'a pas encore son statut « devenue mission <titre> » le fait écrire par le Claude du COO.

Donne (`on`) ou retire (`off`) d'avance ton accord pour archiver les sessions de l'app Desktop que la fermeture d'un groupe ou des pistes a vérifiées ; sans argument, dit l'état. Pas la session d'un diagnostic de bug (« 🐞 Bug »), dont l'accord se demande chaque fois. L'accord, daté, est commun aux projets du poste (stockage du mod), relu à chaque fermeture (une date illisible, ou dans le futur de plus d'une minute, vaut « pas d'accord ») ; `on` ne vient que de ton geste (Entrée au prompt, message par Remote Control ou par l'app) : lancé par un plugin, une tâche programmée, une autre session, ou sans origine connue, il est refusé ; `off`, qui ne fait que retirer l'accord, est accepté de partout. Allumé, la procédure de fermeture le cite en nommant la session, et Claude l'archive par `archive_session` sans redemander, comme `claude stop` dans le CLI ; éteint, Claude te demande l'accord pour chaque session. |

**Dès le premier message : `/flow-board:flow`.** `/flow` est déclaré par le mod au démarrage de la session. Sur le desktop, ce démarrage n'a lieu qu'à l'envoi du premier message : avant, `/flow` n'apparaît pas dans le menu. `/flow-board:flow`, déclaré par le fichier `commands/flow.md`, est disponible tout de suite et accepte les mêmes arguments (`/flow-board:flow history`…). Le mod y répond lui-même, sans passer par le modèle. Une fois le mod démarré, `/flow` sort du menu pour éviter le doublon, mais reste utilisable tapée en entier : les deux font la même chose.

Pourquoi un fichier à part : `$.store` range ses données selon la façon dont le mod est chargé. Le desktop passe ses plugins aux sessions (`inline`), le CLI charge le plugin installé (`mathis-plugins`) ; chacun avait son propre stockage, et une mission créée dans l'un n'existait pas dans l'autre. Le fichier commun est trouvé à partir de l'emplacement du mod, toujours sous `~/.claude`. Au premier démarrage de chaque mode de chargement, son ancien `$.store` est fusionné dans le fichier commun (marque `migrated:board:<racine>` dans `$.store`).

Une mission n'est plus supprimée : elle est archivée. Les archives ne comptent pas dans les 15 missions d'un projet (jusqu'à 100 archivées gardées), ne sont ni proposées à la reprise ni reprises par un skill ; « Reprendre » sur une archivée la désarchive. À la fusion entre discussions, une ancienne trace de suppression n'efface plus une mission touchée après elle.

Limites appliquées : 15 missions par projet ; par mission, 150 tickets, 40 tâches trouvées en route, 30 choix « décidé sans toi » (en auto : aucune coupe avant le rapport, 1 000 au plus, 200 ensuite), 12 groupes (12 fichiers chacun), 80 lignes de journal, 40 livrables, 50 questions bloquantes ouvertes (refus au-delà) et 100 traces de leurs retraits, les marques d'envoi du mode auto (aucune coupe) et 100 traces de leurs retraits.

**Conservation et effacement des agents** (depuis la 0.58.0) : l'historique des agents n'a ni limite de nombre ni d'âge, et archiver une mission n'y touche pas. Supprimer une mission efface ses agents, ceux de ses workers, ses lancements, son relais et ses choix ; « ✗ Oublier » efface une discussion passée et ses workers reconnus sûrement (pas ceux reconnus par leur seul titre). Un fichier effacé est d'abord réécrit vide, puis supprimé par `rm` (`del` sous Windows) ; sans commande, ou si elle échoue, le fichier vide reste. Une session encore ouverte n'est jamais touchée par une autre : elle relit les traces avant chacune de ses écritures et se compacte elle-même ; une fois fermée (30 min sans écriture ni spécialiste au travail, ou fin connue), ce qui reste se reprend. Si les traces ne peuvent pas toutes s'écrire, celles déjà posées sont retirées et l'effacement est annulé ; une session ouverte a pu se compacter d'après elles entre-temps, et le message le dit (si le retrait échoue aussi, il dit « effacement partiel »). Pendant l'effacement, la discussion qui efface affiche « ⏳ Effacement en cours » ; un second effacement de la même mission ou de la même discussion ne fait rien tant que le premier tourne. Avant d'effacer une mission, « Supprimer » relit les transcripts des discussions qui l'ont portée, pour qu'un spécialiste manqué parte aussi ; un transcript illisible n'arrête rien et se dit. Les transcripts de Claude Code ne sont jamais touchés. « Supprimer » efface la mission et ses propres données, pas ce que les autres missions en disent : une ligne de leur journal, un choix déclaré ou un forçage qui la nomme restent tels quels. Les copies `.illisible-` du fichier de coordination et des boîtes « À reprendre » restent aussi : elles ne partent que par un geste de la personne.

**Confidentialité des agents** : le registre garde les descriptions, les prompts (8 000 caractères au plus) et des arguments courts d'outils, jamais un rapport ni un texte de message ; les secrets reconnaissables (en-têtes `Authorization` et `Cookie`, `Bearer x`, `--token`, `password=`, `token: …`, `curl -u`, `mysql -p`, blocs PEM, jetons) y sont masqués (« ‹masqué› »), une valeur entre guillemets en entier. Sur Mac et Linux, le dossier `~/.claude/flow-board/agents/` est fermé aux autres comptes (`chmod 700`, retenté à l'écriture suivante s'il échoue) ; sous Windows, ou sans `$.process.run`, ce réglage n'est pas fait. Le rattrapage ne lit que les transcripts rangés sous `<dossier de Claude>/projects/` (`CLAUDE_CONFIG_DIR`, sinon le dossier d'où le mod est installé), par un chemin absolu. Rien de ce dossier ne quitte le poste.

Le mod n'écrit ni dans les projets, ni dans Asana, ni dans git. Il ne fait que lire : `git fetch` met seulement à jour les références distantes. Pour le coût estimé, il lance `npx -y ccusage@20.0.30` (une fois par jour au plus, depuis le dossier du mod, registre npm officiel).

## Développement

```bash
claude plugin validate plugins/flow-board
claude plugin test plugins/flow-board
```

- Les tests montent le panneau et le bandeau sur les surfaces `terminal`, `desktop`, `vscode` et `mobile`. Ils simulent le stockage, git et une seconde discussion.
- Les modules qui touchent au moteur hors de `register.tsx` (`registry-file.ts`, `catch-up.ts`, `erase-run.ts`) suivent deux règles du chargeur de Claude Code : une fonction qui reçoit `$` et franchit un import s'écrit `function nom($, …) { … }`, jamais `const nom = ($, …) =>` (sinon le module ne charge pas) ; un fichier qui lit ou met à jour un atome le déclare lui-même, avec un plugin et une clé littéraux (le défaut partagé de l'interface est `EMPTY_UI`, dans `model.ts`). Un `let` importé ne s'écrit que par une fonction de son module (`markRebuildNeeded`, `clearHistoryShown`).
- Dans le kit de test, un hook qui remplace une opération du moteur (`store.get`, `session.id`, `process.run`…) doit rendre `{ value }`.
- Les versions précédentes sont dans l'historique git du dépôt ; celles d'avant le passage à git restent dans `~/.claude/mods-archives/flow-board-<version>` sur le PC Windows.

---

**Rétro de l'onglet Agents (depuis la 0.59.0).**
- **Instantané d'un ticket sensible** : avant sa passe « bogues », la session fige le ticket sur `refs/worktree/flow-board/<ticket>`, une référence propre à son worktree (`git add` de ses fichiers, index vérifié par `git diff --cached --name-only`, `git write-tree`, `git commit-tree -p HEAD`, `git update-ref`, chaque commande seule) ; les deux revues relisent `<ref>^..<ref>` et les fichiers à cette référence, et la session avance pendant ce temps ce qui ne touche aucun fichier du ticket (pas d'autre dossier : le garde-fou d'un worktree y refuse git). Au commit, chaque fichier du ticket se ré-ajoute, correctifs compris.
- **Fichiers à côté du relais** (`~/.claude/flow-board/relais/`) : `<parcours>.main.json`, la référence du moment du manager, écrite par lui seul à la reprise (`{"resume": …, "main": "[<ref>]"}`) et relue par chaque worker à son appel de l'outil flow ; `<parcours>.<session>.report.md`, le compte rendu entier d'un worker, écrit par lui seul ; `<parcours>.<session>.entry.json` (depuis la 0.73.0), l'entrée de relais d'un worker, écrite par lui seul. Supprimer la mission efface les trois, leurs chemins calculés d'après les ids, et retrouvés aussi par le dossier. Sans le dossier, la référence passe par `$.store` (`relay-main:<parcours>`) et le compte rendu reste coupé à 8 000 caractères, ce que la réponse dit.
- **`review`, `security` et `withdrawn` dans un worker** : relayés ; au retour du groupe, les constats s'ajoutent aux statistiques de l'implémentation et la revue de sécurité vaut celle du groupe, sauf si le manager en a déjà envoyé une.
- **Rétro** : lancée pendant la mission de la discussion, elle ouvre sa propre mission, « Rétrospective · <mission> », au lieu de reprendre une autre mission en pause qui aurait une phase Rétro.
- **`/implement` d'un groupe déjà passé** : quand ses arguments nomment un groupe (« groupe B ») ou un id de ticket de la mission de la discussion, la mission revient à son implémentation (nouveau tour) et son compte rendu redevient à faire.

## Limites connues

- **Animations.** Les dessins sont des images : sur le desktop, les animations SVG ne tournent probablement plus. Le mode interactif tournait, mais il donnait un fond blanc qui clignotait à chaque redessin.
- **Demande de sync.** Un fichier de code modifié par une commande shell, et non par l'outil d'édition, échappe au refus. La consigne donnée à Claude couvre ce cas. Depuis la 0.59.1, l'encadré suit le dossier de la session (`$.session.cwd()`) : qu'il suive un `cd` du shell vers un worktree reste à confirmer à l'usage, et un `cd` seul ne relance pas la mesure (elle attend la vérification suivante, toutes les 5 minutes, ou un `git fetch`, `pull`, `rebase` ou `merge`). Le refus « une fois par avancée du distant » garde une seule mémoire : des modifications qui alternent entre deux worktrees en retard tous les deux sont refusées une fois à chaque changement de worktree.
- **Ligne compacte de l'outil `flow`.** Claude Code ne dit pas à un mod si la vue détaillée (ctrl+o) est ouverte sur une ligne d'outil : la ligne compacte y reste, sans le JSON de l'appel.
- **Données de suivi.** Elles dépendent en partie des comptes rendus de Claude : étapes, éléments suivis, dépendances.
- **Trouvé en route.** Seules les créations par `create_tasks` d'Asana et `gh issue create` sont vues. Une tâche créée autrement (interface d'Asana, autre outil) n'apparaît que si Claude l'envoie au panneau.
- **Une discussion par mission.** Deux discussions ne peuvent pas suivre la même mission en même temps : un seul écrivain à la fois, sinon deux discussions qui cochent des tickets de la même mission s'écraseraient (la fusion garde la mission la plus récente en entier). Le parallélisme des groupes passe par des workers qui n'écrivent pas sur la mission (`delegate`).
- **Groupes dans un worker.** Le panneau ne suit pas les étapes d'un worker (lecture, TDD, revue…). Depuis la 0.36.0, ses tickets, commits et tests s'affichent en direct, relayés ; les tickets de la mission n'avancent qu'au moment où Claude, dans le manager, rend leurs statuts à sa note de fin. Le relais compte sur les mises à jour Asana de la session : un projet sans suivi Asana n'en montre que les commits et les tests, sauf `set` envoyé par la session. Chaque worker écrit son propre fichier de relais depuis la 0.73.0 : deux sessions qui écrivent en même temps ne se font plus perdre de signal (avant, elles réécrivaient un fichier commun, et la dernière écriture effaçait le signal de l'autre). Un manager encore sur une version d'avant ne lit que l'ancien fichier commun : il ne voit ni les sessions lancées après la mise à jour, ni les signaux qu'une session lancée avant envoie une fois rechargée (à recharger elle aussi, `/reload-plugins`). Le mode `delegate` est propre à la discussion ; depuis la 0.56.0, il est gardé par session (`$.store`, clé `delegate:<session>`, trois jours au plus, jamais sur une mission finie, lu dans le board du dépôt principal quand la session est dans un worktree) et revient quand le mod recharge le tableau de bord (à confirmer à l'usage avec `/reload-plugins` dans un worker). Le mod ne connaît pas l'id d'application d'une discussion (`$.session.id()` donne celui de sa transcription) : pas de lien cliquable vers la discussion de découpage.
- **Découpage des pistes.** La demande de découpage n'enregistre rien et le clic vide la sélection : si elle quitte le prompt avant d'être envoyée, il faut recocher les pistes. Un appel de découpage envoyé pendant un détour (un skill lancé pour régler une décision) range ses pistes dans le détour et clôt le détour, pas la Rétro : finir le détour avant l'appel.
- **Pistes dans un worker** (affectations d'avant la 0.73.0). Le worker ne touche pas au tableau de bord : les pistes avancent dans le panneau quand Claude, dans le manager, rend leur statut à la note de fin de la session, pas au fil de son travail. Une session lancée qui s'arrête sans note laisse ses pistes « en cours » : « ↻ Reprendre les pistes » demande à Claude de les rendre (faites ou écartées) pour pouvoir clore la rétro.
- **Discussion d'un ticket en cours.** Le mod ne lit le titre d'une discussion que dans ses propres hooks (`session_title`) : pour un ticket porté ailleurs, il dit « ici » ou « autre discussion », pas laquelle.
- **Stockage.** Le fichier dépend de la façon dont le plugin est chargé. Une session lancée autrement, par exemple en terminal, peut ne pas voir les mêmes missions. Il est aussi propre à chaque machine : une discussion du PC ne peut pas confier un groupe à une session du Mac, même si les deux se parlent par `SendMessage`.
- **Heredocs.** Depuis la 0.35.1, le corps d'un heredoc n'est pas lu comme des commandes (un brief en prose cachait le `claude --bg` qui le suit) : des tests lancés dans un heredoc (`bash <<EOF` … `pytest` … `EOF`) ne sont donc pas relevés.
- **Workers dans le CLI.** L'id n'est relevé que si `claude --bg` tourne au premier plan (une commande lancée en arrière-plan n'a pas de sortie lisible) ; sans id, le groupe reste « worker à lancer » avec « Annuler », qui le rendrait relançable alors que la session travaille. Le mode de permission de la fille doit être celui du manager, sinon ses messages attendent ton accord.
